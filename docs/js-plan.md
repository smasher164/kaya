# The JS/TS binding — build record

The rulings live in docs/deferred.md's ninth-binding entry (KEY: js
binding); this file records how they were built and the mechanics a
later session needs. Every ruling below cites the entry; everything
else here was decided at build time, 2026-09-01, and is the maintainer's
to re-spell.

## §1 Shape

`bindings/js/` — `kaya/wire.ts` (GENERATED by tools/kaya-bindgen's
ninth emitter, src/js.rs), `kaya/runtime.ts` (loading, the function
floor, the two threads), `kaya/index.ts` (the ambient sugar, the Python
binding's twin), `kaya_app_checks.ts` (the negatives, run by the
`js-app-checks` gate), `package.json` (npm name `kaya-gui`, ruled), a
strict `tsconfig.json`. `guests/js/*.ts` are the scene guests, one per
Python guest, importing `kaya-gui` through the workspace link
`guests/js/node_modules/kaya-gui -> bindings/js` that `npm install
--offline` writes (tools/js-typecheck.py makes it; node_modules is
ignored). The guests are TypeScript run DIRECTLY by node 24 — type
stripping is on by default there, `erasableSyntaxOnly` keeps every
source inside what it strips, and there is no build step and no
artifact to go stale. tsc is the typecheck gate and nothing else.

Toolchain: `nodejs_24` and `typescript` from the pinned nixpkgs;
`@types/node` and its one dependency pinned as npm tarballs in flake.nix
(`nodeTypes`), exported as `KAYA_NODE_TYPES` — nixpkgs carries no
@types packages, and the store's content addressing is the hash check.

## §2 libkaya IS the addon

No node-gyp, no node headers, no napi-rs, no second artifact:
`crates/kaya/src/node.rs` exports `napi_register_module_v1` from libkaya
itself, and `process.dlopen(holder, "…/libkaya.dylib")` is the whole
load (the extension is irrelevant to dlopen; only `require`'s
extension dispatch cares about `.node`). Node's own API is resolved AT
REGISTRATION out of the host process's symbol table — `dlsym` over
`dlopen(NULL)` on unix, `GetProcAddress(GetModuleHandle(NULL))` on
Windows — the trick napi-rs uses on Windows, applied everywhere, so the
dylib has no undefined symbols and no link-time dependency on node.
cbindgen excludes the symbol from kaya.h.

The floor is the same call set runtime.py binds through ctypes:
specHash, capabilities, run, submit, blobRegister, occurrenceBlob, the
six asset calls, openPicked, startPump, exit. Bytes cross as
`Uint8Array` copies both ways (V8's pointer compression forbids an
external buffer over native memory, and the core's bytes are borrowed
until the next call anyway). Handles and ids cross as JS numbers: they
are counters, and the root refuses anything past 2^53 before it can get
here (spec.rs MAX_SAFE_INTEGER).

Measured at build: the whole floor answered from node 24.19 on the first
load; the spec hash read back as the generated constant.

## §3 The two threads (ruled: the worker-thread model)

`import "kaya-gui"` on the process main thread NEVER RETURNS. runtime.ts
spawns a `worker_thread` on the same entry module (`process.argv[1]`,
argv and execArgv passed through) and enters `kaya_run`, which becomes
the platform loop; when it returns the process exits with its code. The
guest's own module body therefore runs only in the worker, which IS the
kaya-app thread. The worker's stdout/stderr are re-pointed at the
descriptors (a worker's stdio is a stream posted to the parent, whose
loop is inside kaya_run forever), and an uncaught exception there ends
the PROCESS through the addon's `exit` — `process.exit` in a worker ends
only the worker, and a blank window with no app behind it is the
failure that would replace the traceback.

THE PUMP. The worker's JS thread cannot block in `kaya_next_occurrence`
without freezing its own event loop (timers, promises, fetch), so
node.rs spawns a native thread that blocks there for it and hands each
record over through a threadsafe function — ONE AT A TIME, waiting on a
condvar for the JS callback to return before it takes the next. That
wait is what keeps the stall watchdog honest: a wedged handler leaves
the next click UNCLAIMED in the ring, exactly as a wedged Python app
thread does, so tools/scenes/stall.steps reads the same stall and the
same recovery (the JS stall guest blocks with `Atomics.wait`). A
free-running pump would have drained the ring into a JS queue and the
watchdog would have reported a healthy app that was gone.

`app.post(fn)` is the way back into a transaction from an async
continuation. Posted work is drained at the top of every occurrence
callback and from a `setImmediate` when the loop is idle, so it runs
before the next occurrence exactly as Python's `_drain_posted` does. An
ASYNC handler's transaction ends at its first `await` (the function
returns there); the no-transaction refusal says so and names `app.post`
(ruled).

## §4 Spellings (ruled AMBIENT; JSX DROPPED)

Plain JS, options objects, bodies last:

    app.window({ title: "todos" }, () => { ... });      // scene scope
    app.window({ dirty: true });                        // live, inside a handler
    kaya.column({ spacing: 12 }, () => { ... });
    kaya.button("Add", { onClick: onAdd });
    kaya.label({ bind: itemsLeft });
    for (const todo of todos) { kaya.row(() => { ... }); }   // the For trace
    kaya.forEach(feed, (cases) => { cases.case(Note, (note) => ...); });
    kaya.when(sig, () => ...);
    const Todo = kaya.record({ title: String, done: Boolean }, "Todo");
    todos.insertFresh(Todo({ title, done: false }));
    todos.patch(key, { done: checked });
    kaya.collection([Note, Todo])                       // the sum
    count.fmt((n) => `${n} items`)                      // fmt takes a function

The reference ports are guests/js/todos.ts, gallery.ts, feed.ts and
menus.ts; every other guest under guests/js is a line-for-line port of
its Python twin, so the two directories read as the spelling table.

ONE HANDLE CLASS FOR BOTH ZONES. Python returns `Widget` or `Node` from
one constructor set by zone; JS returns one `Widget` with `isNode`, and
the one-shot commands and dynamic setters refuse a node at run time
with the sentence the missing method implied. The reason is the
guest's type: a constructor that returned a union forced a cast on
every `field.clear()`, which is the ergonomics the ruling asked for
first. `contextMenu` takes a body (live) or a catalog (node) and refuses
the other.

THE NUMBER RULE. JS has one number type, so the wire tier carries an
`I64` wrapper and a bare number is an F64 on the wire. The sugar puts
I64 where an integer is a FACT of the schema: collection KEYS that are
integer numbers, record fields declared `kaya.Int`, draw-op codes and
enum operands, breakpoint setters. A SIGNAL's number is always F64 —
no prop takes an I64, and every integer derivation (`eq`, `fmt`) is
computed binding-side, so `signal(0)` and Python's `signal(0.0)` are
one thing and no scene can tell them apart (verified against every
python guest: no int record field, and every int signal only feeds
derivations). Decoded I64s arrive as plain numbers, the root having
refused anything past 2^53 (the contract).

WHAT JS CANNOT REFUSE (the honest residue, DESIGN.md's "plain host
variable" clause one language over): `if (sig)` and `if (row.done)` in
a template body are silently true — an object is truthy and nothing can
intercept a statement branch. Python raises from `__bool__`; JS
documents it. `kaya.when` is the conditional.

Record types: `kaya.record(schema, name)` returns a function that both
calls and constructs, whose `prototype` is typed as the fields so
`instanceof` narrows a sum's entries; a one-variant collection also
accepts plain objects.

## §5 Gates and lanes

`tools/js-typecheck.sh` (strict tsc over bindings/js and guests/js,
with a printed census and floors; makes the workspace link) and
`js-app-checks` (`node bindings/js/kaya_app_checks.ts`, the negatives,
run in a worker so the import does not surrender the main thread) join
tools/gates.py; their keyed inputs are in tools/build-id.py. The mac
lane gains `js` in tools/lib/lanes/mac.py's LANGS and a `node
guests/js/<stem>.ts` arm in tools/validate-mac.py; check-steps'
sweep_guests gains the `guests/js/{s}.ts` row, so a scene in SCENES
without a JS guest is red by construction.

Portfolio and varied stay Python-only apps (hand-queued, not sweep
scenes); editor stays Go. The iOS and Android lanes carry no JS legs —
node does not run on the phones (ruled desktop-first). The Linux and
Windows lanes are the breadth left after the mac lane: node in the
docker image and on the VM.

## §6 Open

- Picked-file redemption on Windows: the core hands back a HANDLE and
  node links its own CRT, so an fd from libkaya's `_open_osfhandle`
  would belong to the wrong CRT. runtime.ts refuses by name until the
  windows lane's JS legs exist; the local_path route works meanwhile.
- `PickedFile.open` blocks the app thread: Python hands it to a thread
  and posts back; the worker has no thread to hand it to short of a
  second Worker. The JS guests open in the handler and read through
  node:fs; an `openAsync` over napi's async-work queue is the upgrade if
  a cloud-provider open ever measures slow.
- Distribution (npm publish of kaya-gui with the platform dylibs) stays
  deferred with the packaging milestone (2026-08-28 ruling).
