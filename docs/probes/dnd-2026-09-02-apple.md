# Drag and drop on the two Apple platforms — research for a kaya design pass

Research only. Nothing in the repo was edited; no process was started.
Written progressively; sections appended as they were learned.

## §0 — what kaya has already ruled (read first, it constrains everything below)

Sources: DESIGN.md, docs/clipboard-plan.md, docs/deferred.md, the SwiftUI
interpreter, all read 2026-09-02.

- **DESIGN.md:3044 "Drag and drop"** (a case analysis, NOT built):
  - Hover acceptance is answered from a PRE-PUSHED vocabulary of accepted
    types and operations — "which matches platform convention anyway, since
    fetching drag content mid-hover is discouraged everywhere".
  - Dynamic hover policy is app-updated state; staleness "mislabels a cursor
    badge, which is cosmetic".
  - The drop verdict is a BOUNDED WAIT whose expiry rejects the drop and
    snaps the drag back — "a fail-safe and retryable default".
  - Source-side data provision (`IDataObject::GetData`, pasteboard promises)
    is "demand with a generous deadline; the blocked party is the receiving
    process, and platforms have long normalized slow providers."
  - Side benefit claimed: "app logic keeps running inside the drag and resize
    modal loops that stall single-threaded apps."
- **DESIGN.md:2988-3014, the blocking policy** the above rests on. Bounded
  waits on DECISIONS are allowed only when the expiry default is fail-safe
  and retryable; the drop verdict is named as the qualifying case, and
  "accepting a 'move' drop causes the source to delete the original" is named
  as the case a wait may NOT cover. Unbounded waits are prohibited.
- **DESIGN.md:3300 degradation table**: "Drop verdict misses its deadline →
  Drop rejected; drag snaps back (retryable)"; "Stale hover policy → Wrong
  cursor badge until the next refresh (cosmetic)". The table's own preamble
  (3293) says drag and drop is one of the rows that describes a subsystem
  "not built yet".
- **DESIGN.md:2312 Clipboard, "A clip is not a string"**: the representation
  set is CLOSED — `text`, `html`, `image`, `files` — plus `custom(id, bytes)`.
  The custom id is MIME-shaped (contains a slash, lowercase, no spaces),
  validated at the root; on Apple the id "reaches each platform's own
  registry unchanged — a UTI on Apple". Copy takes a RECORD, paste returns a
  SUM. kaya derives nothing between representations; the one exception is a
  file list, which also gets the platform's text rendition of the paths.
  Wire order is DESCENDING CLIP VALUE: custom (16), files (8), image (4),
  html (2), text (1).
- **docs/clipboard-plan.md:207 "Paste and drop are the same event"**: "So
  `on_paste` is the same payload arriving through a third trigger when drag
  and drop lands later, not a second data model." (Android's
  `onReceiveContent` is the cited precedent; Wayland's `wl_data_offer` the
  structural one.)
- **docs/clipboard-plan.md:220 "Deliberately out — Lazy rendering."** Every
  platform lets a producer defer rendering until asked; kaya declined,
  because it "would add a callback the platform can block on, arriving on
  the app thread at a moment kaya does not control", interacting with the
  persistence handoff and the stall watchdog. NOTE THE TENSION: DESIGN's
  drag paragraph EXPECTS pasteboard promises on the source side. Whether
  drag re-opens lazy rendering is a live ruling (see §4 and §9 below).
- **docs/clipboard-plan.md:228 "Multiple items per clip" is out**: one clip;
  "three files" lives inside ONE representation. This is a direct constraint
  on Apple drag, where a session legitimately carries several
  `NSDraggingItem`s / `UIDragItem`s (see §4).
- **`accepts`** is a space-separated ACCEPT LIST per widget (closed kinds by
  name plus custom ids), not a mask. `read_clipboard` takes the same string.
  This is exactly the shape a pre-pushed drop-acceptance vocabulary needs.
- **Order is data** (DESIGN.md:3541): `collection_move` repositions an entry
  before an anchor ENTRY, by KEY, never index — "an index would race the very
  deltas that change it". It lands as `move_child` on the apply side
  (docs/probes/undo-recon-surface.md:40 records the recon shape
  `CollectionMove { id, path, key, before }`). A reorder drag therefore has
  a landing op already; what is missing is the occurrence that requests it.
  (Grep note: no `reorderable` prop and no `MoveRequested` occurrence exist
  in the tree today — the ledger names drag and drop only inside the
  system-integration floor entry, docs/deferred.md:1729/1742: "**drag and
  drop** — the most divergent, and it interacts with window management on
  both mac and Windows".)
- **The harness drives the MODEL, not the OS input stream.** In
  swift/KayaSwiftUI.swift the `click` verb (line 5853) resolves the target
  node and calls `KayaHost.emit(node.tag)` on the main thread — no synthetic
  mouse event anywhere. `toggle`/`set_value`/`choose` write the model inside
  `kayaUserWrite` and emit. The ONE exception is `type` (line 13312), which
  builds real `NSEvent.keyEvent`s and sends them through `NSApp.sendEvent`,
  with a comment recording WHY it is in-process: "CGEvent posting into the
  HID stream would type at whatever is frontmost, which under a five-lane
  matrix is rarely this process, and it charges the accessibility permission
  besides." That sentence is the precedent that decides §7.
- **docs/deferred.md:10168 CHORE — SYNTHESIZING A PAN INTO THE iOS
  SIMULATOR** (measured 2026-08-30): synthetic CGEvents reach the
  Simulator's mac chrome but the DEVICE CONTENT VIEW ignores clicks, drags,
  wheel and keys alike (macOS 26 / iOS 26.5 sim); nixpkgs' idb-companion
  NSException-crashes on attach; simdrive's HID `swipe` (down + interpolated
  down-state + up, idb's own encoding) is accepted but does NOT pan SwiftUI;
  `IndigoHIDMessageForScrollEvent`'s shape was reverse-read and no
  permutation moved content. "THE GUARANTEED PATH if pan synthesis is ever
  needed: a resident XCUITest driver (XCUICoordinate press/drag), the
  industry answer — a small runner app in tools/ios beside simdrive."
- **API floor**: tools/check-symbols.py pins macOS 13.0 / iOS 16.0 ("one
  Swift file serves both"). Everything below is annotated against that.

## §1 — macOS: the SwiftUI surface and the AppKit floor beneath it

All API facts below are from developer.apple.com's own documentation JSON
(`https://developer.apple.com/tutorials/data/documentation/<path>.json`,
which is what the SPA renders from; the HTML page itself fetches empty).

### 1.1 The SwiftUI drop surface, three tiers, and their floors

| API | Introduced | Note |
|---|---|---|
| `onDrag(_:)` / `onDrag(_:preview:)` | macOS 10.15 / iOS 13.4 (preview: macOS 12 / iOS 15) | returns an `NSItemProvider` you build by hand |
| `onDrop(of:isTargeted:perform:)` — `[UTType]` overload | macOS 11.0 / iOS 14.0 | the two `[String]` overloads are deprecated |
| `onDrop(of:delegate:)` + `DropDelegate` | macOS 10.15 / iOS 13.4 | the only tier with a hover verdict |
| `draggable(_:)` / `dropDestination(for:action:isTargeted:)` + `Transferable` | **macOS 13.0 / iOS 16.0** | exactly kaya's floor |
| `dropDestination(for:isEnabled:action:)` with a `DropSession` | macOS 27 / iOS 27 | NEW; the 2026 replacement — see 1.4 |

`dropDestination(for:action:isTargeted:)` is **deprecated as of macOS 27.0 /
iOS 27.0** in favour of the `DropSession` form. Since kaya's floor is macOS 13,
the deprecated call is still the only one available across the supported range;
a `#available` fork would be needed to adopt the new one.

Sources:
- https://developer.apple.com/documentation/swiftui/dropdelegate
- https://developer.apple.com/documentation/swiftui/view/dropdestination(for:action:istargeted:)
- https://developer.apple.com/documentation/swiftui/view/ondrop(of:istargeted:perform:)

### 1.2 `DropDelegate` — the full protocol, and every return is synchronous

`@MainActor protocol DropDelegate` (macOS 10.15+ / iOS 13.4+):

```swift
func validateDrop(info: DropInfo) -> Bool          // default: true
func dropEntered(info: DropInfo)                   // Void
func dropUpdated(info: DropInfo) -> DropProposal?  // default: nil (= system default op)
func dropExited(info: DropInfo)                    // Void
func performDrop(info: DropInfo) -> Bool           // REQUIRED, the only required member
```

`DropInfo` carries `location: CGPoint`,
`hasItemsConforming(to: [UTType]) -> Bool` and
`itemProviders(for: [UTType]) -> [NSItemProvider]`. The TYPE list is available
synchronously; the DATA is not — `NSItemProvider` loads asynchronously.
`hasItemsConforming` is exactly the "answer hover from a pre-pushed vocabulary
of types" call that DESIGN.md:3044 describes, and it needs no round trip to the
app at all if kaya holds the accept list core-side.

`DropProposal` (macOS 10.15+/iOS 13.4+) is
`init(operation: DropOperation)` plus, in the newer SDKs,
`init(withinApplication:outsideApplication:)` and
`operationOutsideApplication`. `DropOperation` cases: `cancel`, `copy`,
`move`, `forbidden`, plus (newer SDKs) `delete` and `alias`, and a
`DropOperation.Set`. The four original cases map 1:1 onto UIKit's
`UIDropOperation` — that is the shape kaya's "operation" vocabulary should
take, and it is the intersection with Windows'/GTK's masks minus `link`.

### 1.3 The AppKit floor

`NSDraggingDestination` (a view/window opts in with
`registerForDraggedTypes(_:)`):

```swift
func draggingEntered(_ sender: any NSDraggingInfo) -> NSDragOperation   // SYNC
func draggingUpdated(_ sender: any NSDraggingInfo) -> NSDragOperation   // SYNC
func draggingExited(_ sender: (any NSDraggingInfo)?)                    // Void
func wantsPeriodicDraggingUpdates() -> Bool                             // SYNC
func prepareForDragOperation(_ sender: any NSDraggingInfo) -> Bool      // SYNC
func performDragOperation(_ sender: any NSDraggingInfo) -> Bool         // SYNC
func concludeDragOperation(_ sender: (any NSDraggingInfo)?)             // Void
func draggingEnded(_ sender: any NSDraggingInfo)                        // Void
func updateDraggingItemsForDrag(_ sender: (any NSDraggingInfo)?)        // Void
```

`NSDragOperation` is an OptionSet: `.copy`, `.link`, `.generic`, `.private`,
`.move`, `.delete`, `.every` (`.all` deprecated), and `NSDragOperationNone` for
"nothing". So the mac floor has a genuine MASK, where SwiftUI's `DropProposal`
carries ONE operation. kaya's protocol should carry the mask (the mac and
Windows floors both have one; SwiftUI collapses it) and let each backend
narrow.

`NSDraggingSource` (the source side):

```swift
func draggingSession(_:sourceOperationMaskFor context: NSDraggingContext)
    -> NSDragOperation                                  // REQUIRED, SYNC
func draggingSession(_:willBeginAt: NSPoint)
func draggingSession(_:movedTo: NSPoint)
func draggingSession(_:endedAt: NSPoint, operation: NSDragOperation)
func ignoreModifierKeys(for: NSDraggingSession) -> Bool
```

`NSDraggingContext` is the "within my app" vs "outside my app" distinction —
the same split SwiftUI later exposed as
`DropProposal(withinApplication:outsideApplication:)`.

A session starts with
`NSView.beginDraggingSession(with: [NSDraggingItem], event: NSEvent, source:)
-> NSDraggingSession`. **The `event` must be a mouse event** (Apple: the method
returns immediately and the drag begins at the next turn of the run loop).
That single requirement is what makes programmatic drag synthesis on mac
possible at all — see §7.

`NSDraggingSession` exposes `draggingPasteboard`, `draggingSequenceNumber`,
`draggingLocation`, `draggingFormation`,
`animatesToStartingPositionsOnCancelOrFail` (this is literally the
"snaps back" affordance DESIGN.md's degradation row names — it is a real
platform behavior, on by default, not something kaya has to draw),
`draggingLeaderIndex`, `numberOfValidItemsForDrop` and
`enumerateDraggingItems(options:for:classes:searchOptions:using:)`.

`NSPasteboardItem` + `NSPasteboardItemDataProvider` is the mac promise for
NON-file data:

```swift
func pasteboard(_ pasteboard: NSPasteboard?, item: NSPasteboardItem,
                provideDataForType type: NSPasteboard.PasteboardType)
func pasteboardFinishedWithDataProvider(_ pasteboard: NSPasteboard)
```

Note the shape: **void return, no completion handler.** The provider must have
called `item.setData(_:forType:)` by the time it returns. That is a
*synchronous* callback into the source app, invoked when a receiver asks for
that type — which is exactly DESIGN.md's "source-side data provision ...
demand with a generous deadline; the blocked party is the receiving process".
kaya's ring can serve it with a bounded wait; the platform gives no async
escape hatch here.

### 1.4 What the SwiftUI interpreter could actually use

kaya's mac widgets are SwiftUI views in an `NSWindow`, so all three tiers are
reachable. The ranking, given that every backend must lower the SAME
semantics:

1. **`onDrop(of:delegate:)` with a kaya-owned `DropDelegate` is the right
   destination tier**, and it is the ONLY SwiftUI tier that exposes a hover
   verdict (`dropUpdated -> DropProposal?`) and a type test without loading
   data (`DropInfo.hasItemsConforming`). GTK's
   `GtkDropTarget::accept`/`::motion` (returning a `GdkDragAction`), WinUI's
   `DragOver` (setting `AcceptedOperation`) and Android's `DragEvent`
   `ACTION_DRAG_ENTERED`/`_LOCATION` are the same shape. `dropDestination`'s
   `action: ([T], CGPoint) -> Bool` has NO hover verdict at all and hands you
   already-decoded `Transferable` values, so a backend built on it could not
   express kaya's hover-acceptance semantics and could not carry
   `custom(id, bytes)` without a `Transferable` type per id.
2. **`onDrag`/`NSItemProvider` is the right SOURCE tier** for the same reason:
   `Transferable`/`draggable` wants a Swift type per representation, while
   kaya's clip is a closed sum of byte payloads plus an open `custom(id,
   bytes)` — `NSItemProvider.registerDataRepresentation(forTypeIdentifier:
   visibility:loadHandler:)` takes a raw UTI STRING and hands back bytes
   through a completion handler, which is the only tier that can express an
   app-chosen id decided at run time. (`Transferable` conformances are
   compile-time types; kaya's ids are data.)
3. **Dropping to AppKit is available but should not be needed** for the
   destination: `NSViewRepresentable` wrapping a view that
   `registerForDraggedTypes` gives the full `NSDragOperation` mask and
   `draggingUpdated`'s per-motion verdict. The one thing it buys over
   `DropDelegate` today is the MASK and `NSDraggingContext`; the one thing it
   costs is that the interpreter's hit-testing would have to agree with
   SwiftUI's layout. Recommendation: `DropDelegate` first, and treat the
   mask-vs-single-operation gap as a lowering narrowing (kaya carries the
   mask, mac picks one) rather than a representable.
4. **`NSFilePromiseProvider` (macOS 10.12+) is the only tier for "drag a file
   OUT that does not exist yet"** — see §5.

### 1.5 What arrived AFTER kaya's floor (macOS 26 / iOS 26, WWDC 2025)

Worth knowing because it shows where Apple thinks the model belongs, and
because the mac lane already runs macOS 26 (docs/deferred.md:10176 records the
lane host as macOS 26 / iOS 26.5 sim):

- `dropDestination(for:isEnabled:action:)` with
  `action: ([T], DropSession) -> Void` — **macOS 26.0+ / iOS 26.0+**. The old
  `dropDestination(for:action:isTargeted:)` is **deprecated at macOS 27 /
  iOS 27**.
- `DropSession` (struct, macOS 26+): `id`, `phase` (`DropSession.Phase`),
  `itemsCount`, `location`, `size`, `suggestedOperations: DropOperation.Set`,
  `localSession: DropSession.LocalSession?`, and
  `reorderDestination(for:in:)` / `reorderDestination(for:itemID:in:)`.
- `dropConfiguration(_ configuration: @escaping (DropSession) -> DropConfiguration)`
  — macOS 26.0+, iOS 27.0+. `DropConfiguration(operation:)` is the hover
  verdict, re-derived per location.
- Apple's own note on that closure is the best external support for kaya's
  pre-pushed-vocabulary ruling: **"The configuration closure is called
  frequently for different drop locations — avoid expensive calculations."**
  A cross-process round trip per motion event is exactly what Apple is
  telling you not to do.
- `reorderDestination` is Apple's 2025 answer to the reorder problem, and it
  is KEY-shaped, not index-shaped: it resolves the destination "value" for a
  reordering operation in a container, generic over Item and CollectionID,
  with a `KeyPath` overload for item ids. That is the same choice
  DESIGN.md:3541 made ("keys, never indices — order is data").

Sources:
- https://developer.apple.com/documentation/SwiftUI/Adopting-drag-and-drop-using-SwiftUI
- https://developer.apple.com/documentation/swiftui/view/dropdestination(for:isenabled:action:)
- https://developer.apple.com/documentation/swiftui/dropsession
- https://developer.apple.com/documentation/swiftui/view/dropconfiguration(_:)

## §2 — iOS: what is the same and what is different

### 2.1 The APIs

SwiftUI's `draggable` / `dropDestination` / `onDrag` / `onDrop` / `DropDelegate`
are the SAME declarations on both platforms with the same availability
(`DropDelegate` iOS 13.4+, `onDrop` [UTType] iOS 14.0+, `draggable` /
`dropDestination` / `Transferable` iOS 16.0+). One Swift source really can
serve both, which matters because kaya's KayaSwiftUI.swift is one file for mac
AND iOS (tools/check-symbols.py's comment says so explicitly).

Beneath it, UIKit, not AppKit:

`UIDragInteraction` + `UIDragInteractionDelegate` (iOS 11+). Every method is
`@MainActor` and SYNCHRONOUS. The one required member is

```swift
func dragInteraction(_:itemsForBeginning session: UIDragSession) -> [UIDragItem]
```

and **returning an empty array means no drag starts** — that is the source
side's veto, and it must be answered in the callback, with no wait available.
Optional members that matter for kaya: `previewForLifting:session:`,
`willAnimateLiftWith:session:`, `sessionWillBegin:`, `sessionDidMove:`,
`session:willEndWith:` and `session:didEndWith:` (both take a
`UIDropOperation`, so the source learns copy vs move), `itemsForAddingTo:`
(a second finger adds items to a live session — a shape mac does not have),
`sessionAllowsMoveOperation:` and
`sessionIsRestrictedToDraggingApplication:`.

`UIDropInteraction` + `UIDropInteractionDelegate` (iOS 11+):

```swift
func dropInteraction(_:canHandle: UIDropSession) -> Bool                     // SYNC
func dropInteraction(_:sessionDidEnter: UIDropSession)                       // Void
func dropInteraction(_:sessionDidUpdate: UIDropSession) -> UIDropProposal    // SYNC
func dropInteraction(_:sessionDidExit: UIDropSession)                        // Void
func dropInteraction(_:performDrop: UIDropSession)                           // Void — async work allowed
func dropInteraction(_:concludeDrop: UIDropSession)                          // Void
func dropInteraction(_:sessionDidEnd: UIDropSession)                         // Void
func dropInteraction(_:item:willAnimateDropWith: UIDragAnimating)            // Void
func dropInteraction(_:previewForDropping:withDefault:) -> UITargetedDragPreview?
```

`UIDropProposal(operation:)` with `isPrecise` and `prefersFullSizePreview`;
`UIDropOperation` is `cancel`, `forbidden`, `copy`, `move` — Apple's own
abstracts: `.cancel` "no data should be transferred, thereby canceling the
drag"; `.forbidden` "although a move or copy operation is typically legitimate
in this scenario, the drop activity isn't allowed" (this is the "cursor badge"
distinction — `forbidden` draws the no-entry badge, `cancel` draws nothing);
`.copy`; `.move`. **There is no `link`/`alias`/`generic`/`private` on iOS**,
so the intersection of the two Apple platforms' operation vocabularies is
{copy, move, forbidden, cancel} — which is also the intersection with WinUI's
`DataPackageOperation` minus `Link`, and with GTK's `GdkDragAction` minus
`ASK`/`LINK`. **Recommended kaya vocabulary: copy, move, link, none** with
`link` documented as unrepresentable on iOS/Android (a stated carve-out, per
invariant 1).

`UIDragDropSession` (the shared base of `UIDragSession`/`UIDropSession`) gives
`items`, `hasItemsConforming(toTypeIdentifiers: [String]) -> Bool`,
`canLoadObjects(ofClass:) -> Bool`, `location(in: UIView) -> CGPoint`, and two
properties Apple documents verbatim as:
- `allowsMoveOperation` — "A Boolean value that indicates whether the drag
  session permits moving drag items **within the same app**."
- `isRestrictedToDraggingApplication` — "A Boolean value that indicates
  whether the drag session is confined to the app that started the drag
  activity."

`UIDropSession` adds `progressIndicatorStyle`, `localDragSession:
UIDragSession?` (non-nil exactly when the drag started in this app — the
within/outside distinction mac spells as `NSDraggingContext`), and

```swift
func loadObjects(ofClass: any NSItemProviderReading.Type,
                 completion: ([any NSItemProviderReading]) -> Void) -> Progress
```

which is asynchronous and returns a `Progress` — iOS is the platform that
BUILT the async transfer in, complete with a system progress indicator.

### 2.2 The differences that matter to a design pass

1. **Lift.** iOS has an explicit lift phase: a long press lifts the item into
   a floating preview before any movement counts as a drag. mac has no lift —
   a drag begins on mouse-down + threshold movement. Consequence for kaya's
   harness: a synthetic iOS drag must hold, then move, then release, and the
   hold duration is a platform-tuned constant nobody publishes.
   `previewForLifting:session:` and `willAnimateLiftWith:session:` are the
   hooks; the default lift preview is derived from the view, so kaya can ship
   without touching it.
2. **Multi-item sessions.** `itemsForAddingTo:withTouchAt:` lets a second
   finger add items to a running drag. That is a genuine iOS-only shape, and
   it collides head-on with docs/clipboard-plan.md:228's ruling that a clip
   carries ONE item. See §4.
3. **No cursor badges.** iOS draws the drop badge on the floating preview
   itself (a green plus for copy, nothing for move, a no-entry for forbidden)
   and has no pointer to badge; on iPadOS with a trackpad the pointer takes
   the badge instead. Nothing kaya has to lower differently — the
   `DropOperation` value drives both.
4. **App-to-app is a platform policy, not an app one.** On iPad, drag between
   apps works in Split View/Slide Over and, since iPadOS 15, between any two
   apps via the Home bar. On iPhone, drag and drop was in-app only through
   iOS 14; iOS 15 added dragging content between apps by holding the item and
   switching apps with the other hand. Either way the app cannot control it:
   `isRestrictedToDraggingApplication` only lets a source OPT OUT.
5. **Spring loading is a separate API on each.** mac:
   `NSSpringLoadingDestination` (hover or force-click over a destination
   activates it — the Finder folder idiom), with
   `springLoadingEntered/Updated -> NSSpringLoadingOptions` and
   `springLoadingActivated(_:draggingInfo:)`. iOS:
   `UISpringLoadedInteraction` (iOS 11+), a `UIInteraction` you attach with
   an activation handler, plus `UISpringLoadedInteractionSupporting` on
   built-in controls. Both are separate opt-ins, neither is required for a
   correct drag, and NEITHER has a GTK/WinUI/Android analogue that kaya could
   lower uniformly. **Recommendation: out of scope, stated as a deliberate
   cut with its trigger** (an artifact that needs hover-to-navigate).

## §3 — THE DROP VERDICT: what must be synchronous, and what may not be

This is the section the maintainer's doctrine turns on. The short answer:
**the hover verdict is hard-synchronous on both platforms and cannot be
deferred at all; the PERFORM step is where deferral is legal, and it is legal
in a different shape on each platform.**

### 3.1 The hover verdict — SYNCHRONOUS, no exceptions

| Platform / tier | Callback | Returns | Deferrable? |
|---|---|---|---|
| AppKit | `draggingEntered(_:)` | `NSDragOperation` (mask) | **No** |
| AppKit | `draggingUpdated(_:)` | `NSDragOperation` (mask) | **No** |
| AppKit | `prepareForDragOperation(_:)` | `Bool` | **No** |
| SwiftUI | `DropDelegate.validateDrop(info:)` | `Bool` | **No** |
| SwiftUI | `DropDelegate.dropUpdated(info:)` | `DropProposal?` | **No** |
| SwiftUI (26+) | `dropConfiguration` closure | `DropConfiguration` | **No** |
| UIKit | `dropInteraction(_:canHandle:)` | `Bool` | **No** |
| UIKit | `dropInteraction(_:sessionDidUpdate:)` | `UIDropProposal` | **No** |
| UIKit | `dragInteraction(_:itemsForBeginning:)` | `[UIDragItem]` | **No** |

Every one of these is a plain value-returning `@MainActor` method. There is no
completion-handler variant, no `async` variant, no "I'll tell you later"
token, and no documented API for re-asking. On mac,
`wantsPeriodicDraggingUpdates() -> true` makes AppKit re-call
`draggingUpdated` roughly every 100 ms even when the mouse is still, which is
the ONLY re-ask mechanism either platform offers — and it is a re-ask, not a
deferral: each call still needs an answer now.

**This validates DESIGN.md:3044 exactly.** A hover answer computed from a
pre-pushed vocabulary is not a kaya convenience; on Apple it is the only
implementable design. A kaya backend that round-tripped the app thread inside
`draggingUpdated` would either block the main thread (Apple's own
`dropConfiguration` note warns against expense here) or answer stale — and
DESIGN already rules stale-here is cosmetic.

**The one refinement worth a ruling:** the pre-pushed vocabulary needs TWO
axes, not one. `hasItemsConforming(to:)` answers *types*; the *operation*
(`copy` vs `move`) is a second decision the destination makes per hover, and
on mac it is a MASK intersected with the source's
`draggingSession(_:sourceOperationMaskFor:)` mask and the modifier keys.
kaya's `accepts` list gives the type axis for free (it already exists for
paste); the operation axis needs a companion — a per-widget declared
operation set, defaulting to `copy`.

### 3.2 The perform step — where deferral IS available, and how far

- **AppKit `performDragOperation(_:) -> Bool` is synchronous**, but its Bool
  means "I have taken responsibility", not "I have finished". The classic
  Apple pattern is to read the pasteboard synchronously (`readObjects`,
  `data(forType:)` — the pasteboard content is already materialised by the
  time the drop happens for non-promised types) and return true; for
  PROMISED files you call `NSFilePromiseReceiver.receivePromisedFiles(
  atDestination:options:operationQueue:reader:)`, which is asynchronous, and
  still return true immediately. So the mac shape is: **decide now, finish
  later**.
- **UIKit `dropInteraction(_:performDrop:)` returns Void** and is explicitly
  designed for asynchronous completion — you call
  `session.loadObjects(ofClass:completion:)` and get a `Progress`, and the
  system draws a progress indicator (`UIDropSession.progressIndicatorStyle`).
  iOS is therefore *more* permissive than mac here.
- **SwiftUI `DropDelegate.performDrop(info:) -> Bool` is synchronous**, and
  the item providers it hands you are asynchronous loaders. Apple's guidance
  on the `onDrop` closure is to START the load inside the closure; the
  `NSItemProvider`s are only guaranteed valid for the scope of the call.
- **`dropDestination(for:action:isTargeted:)` is the outlier**: SwiftUI does
  the async load ITSELF and calls your action only after the payload has been
  transferred, handing you decoded `[T]`. There is no hover verdict and no
  chance to reject on content. This confirms recommendation 1.4.1 — kaya
  cannot use it.

### 3.3 What this means for kaya's bounded wait

DESIGN's bounded wait survives, but it lands in a different place than the
paragraph implies. Precisely:

- **Hover acceptance: NO WAIT AT ALL is needed or possible.** Answer from
  core-side state (the widget's `accepts` list ∩ the session's advertised
  types, and the widget's declared operation set ∩ the source mask). This is
  strictly better than a bounded wait: zero deadline, zero degradation, and
  the "stale hover policy → wrong badge (cosmetic)" row is the only residue.
- **The drop VERDICT is where the bounded wait lives**, and both platforms
  support parking it — but with a caveat that must be ruled on. Parking
  inside `performDragOperation` / `performDrop` means parking the MAIN
  THREAD, because both are `@MainActor` and the drag is running inside
  AppKit's/UIKit's own tracking loop. A main-thread park that outlives a
  couple of frames earns the beachball, which DESIGN.md:3007 itself names as
  a hazard of unbounded waits. Two honest shapes:
  1. **Accept optimistically, reconcile after** (the platform-idiomatic one):
     return `true`/`.copy` immediately, hand the payload to the app as an
     occurrence, and let the app's later transaction be the visible effect.
     The drag "succeeds" from the source's point of view; the app's rejection
     shows as "nothing changed". This is what every async-modelled toolkit
     does, and it is what iOS's `Progress` UI was built for.
  2. **Bounded wait on the main thread** (DESIGN's stated design): park the
     drop callback for a deadline chosen well under the beachball threshold
     (Apple's watchdog and the spinning wheel start around 2 s of an
     unpumped main run loop, so a deadline in the low hundreds of ms is the
     honest budget), and reject on expiry.
  DESIGN.md:3003 already forbids a wait "where expiry silently commits an
  irreversible branch; accepting a 'move' drop causes the source to delete
  the original" — which rules OUT shape 1 for `move` and leaves it available
  for `copy`. **A defensible ruling: bounded wait for `move`, optimistic
  accept for `copy`**, with the deadline stated and the expiry rejecting.
  This wants the maintainer's decision; it is not derivable from the docs.

## §4 — PAYLOADS: multiple representations, laziness, and kaya's closed sum

### 4.1 How Apple carries several representations

Both platforms carry a drag as **items**, each item holding several
**representations** keyed by type identifier, with the receiver taking the
richest it understands — structurally identical to
docs/clipboard-plan.md's model and to DESIGN.md:2320's "ONE item available in
several types".

- **mac, AppKit floor**: `NSPasteboardItem`, several `setData(_:forType:)` /
  `setString(_:forType:)` calls, one per `NSPasteboard.PasteboardType`. Types
  are ordered; earlier = preferred. A drag carries `[NSDraggingItem]`, each
  wrapping one pasteboard writer.
- **both, modern**: `NSItemProvider`, with
  `registerDataRepresentation(forTypeIdentifier: String, visibility:,
  loadHandler: ((Data?, Error?) -> Void) -> Progress?)` — **and the load
  handler is lazy by construction**: it is only invoked when a consumer asks
  for that type, it hands back bytes through a completion handler, and it may
  return a `Progress` for cancellation. `registerFileRepresentation(...)` is
  the file twin (`(URL?, Bool, Error?) -> Void`). `NSItemProviderRepresentationVisibility`
  is `.all` / `.team` / `.ownProcess` — a per-representation scope control
  with no analogue in kaya's clip model, and the mechanism behind "this
  representation is only for my own app".
- **both, macOS 13 / iOS 16 tier**: `Transferable` with
  `CodableRepresentation`, `DataRepresentation`, `FileRepresentation`,
  `ProxyRepresentation`, listed in preference order, and the exporting
  members are `async throws`. Apple's own guidance: "order representations
  by preference — the most accurate first, increasingly compatible
  alternatives after".

### 4.2 How that maps onto kaya's clip grammar

It maps almost exactly, and the wire order already agrees:

| kaya representation | mac pasteboard type | iOS type identifier |
|---|---|---|
| `text` | `.string` (`public.utf8-plain-text`) | `public.utf8-plain-text` |
| `html` | `.html` (`public.html`) | `public.html` |
| `image` | `.png` / `.tiff` | `public.png` |
| `files` | `.fileURL` (`public.file-url`), one item per file on mac | `public.file-url` |
| `custom(id, bytes)` | the id as a raw `NSPasteboard.PasteboardType` | the id as a raw type identifier string |

kaya's descending clip value (custom 16, files 8, image 4, html 2, text 1) IS
Apple's preference order, so a backend that offers representations in enum
order is idiomatic on both. **Nothing about drag needs a second data model —
docs/clipboard-plan.md:214's claim holds up.**

Three real charges, though:

1. **`custom` ids and UTType.** kaya's id is MIME-shaped by ruling (a slash,
   lowercase) and macOS was measured round-tripping such an id
   byte-identically through the pasteboard (clipboard-plan §1b). Drag adds a
   wrinkle: the SwiftUI destination tier's live API is
   `DropInfo.hasItemsConforming(to: [UTType])` /
   `itemProviders(for: [UTType])`, and a `UTType` for an undeclared
   MIME-shaped id is either nil or a `dyn.` dynamic identifier depending on
   which initializer is used. **The safe path exists and should be the
   ruling**: `NSItemProvider.registerDataRepresentation(forTypeIdentifier:
   String, ...)` takes a RAW STRING, `DropInfo` still carries the
   (deprecated but present) `[String]` overloads, and the AppKit floor's
   `registerForDraggedTypes([NSPasteboard.PasteboardType])` is raw strings
   too. So kaya can keep the id verbatim on both tiers.
   **UNKNOWN WORTH A PROBE, not an assertion:** at least one developer report
   says a custom UTI needs `UTExportedTypeDeclarations` in Info.plist before
   SwiftUI drag on macOS will carry it
   (https://developer.apple.com/forums/thread/649451). kaya's mac guests run
   as UNBUNDLED binaries on the lane, which have no Info.plist at all — so
   this is exactly the shape of the clipboard milestone's own "measure the
   platform before writing an arm" and it should be probed the same way
   tools/mac/clipprobe was, bundled and unbundled.
2. **Multiple items per drag.** docs/clipboard-plan.md:228 ruled ONE item per
   clip, because Windows/X11/Wayland cannot do more. Drag makes this louder,
   not quieter: mac's `beginDraggingSession(with: [NSDraggingItem], ...)` and
   iOS's `itemsForBeginning -> [UIDragItem]` plus `itemsForAddingTo` are
   genuinely multi-item, `NSDraggingInfo.numberOfValidItemsForDrop` is a
   count the destination sets, and iOS draws a badge with that number.
   The clipboard ruling's own remedy applies unchanged — "three files lives
   INSIDE one representation" — and a one-item drag is what
   `files` already encodes. **Recommended: hold the one-item ruling, lower a
   multi-file drag as one item whose `files` representation is a list, and
   state the carve-out** (a receiving kaya app sees one clip; the badge count
   is the file count).
3. **Lazy rendering was ruled OUT for clipboard, and drag argues for
   re-opening it — but only on the SOURCE side, and DESIGN already says so.**
   clipboard-plan.md:220 declined promises because they add "a callback the
   platform can block on, arriving on the app thread at a moment kaya does
   not control". DESIGN.md:3050 nevertheless names "pasteboard promises" as
   part of the drag design, as "demand with a generous deadline". The two are
   reconcilable and the reconciliation is worth stating explicitly in the
   ruling: **for a drag the source app is ALREADY inside a user gesture it
   started, so the moment is not arbitrary** — unlike a clipboard write,
   whose promise can be redeemed hours later by any app.
   **Recommended: keep clipboard eager; allow drag promises for `files`
   ONLY** (that is the case with a real payoff — a file that does not exist
   until dropped), through `NSFilePromiseProvider` on mac and
   `registerFileRepresentation` on iOS, and keep `text`/`html`/`image`/
   `custom` eager everywhere. That keeps kaya's one promise path on the one
   API that is asynchronous with a completion handler on BOTH platforms,
   instead of on `NSPasteboardItemDataProvider`, which is synchronous and
   has no completion handler at all.

Sources:
- https://developer.apple.com/documentation/foundation/nsitemprovider
- https://developer.apple.com/documentation/coretransferable/transferable
- https://developer.apple.com/documentation/appkit/nspasteboarditemdataprovider

## §5 — FILES: out of the app, and into it

### 5.1 Files OUT — the promise

- **mac**: `NSFilePromiseProvider(fileType: String /* a UTI conforming to
  public.data or public.directory */, delegate:)`, macOS 10.12+. Write it to
  the pasteboard as a dragging item. The delegate:
  ```swift
  func filePromiseProvider(_:fileNameForType:) -> String
  func filePromiseProvider(_:writePromiseTo url: URL,
                           completionHandler: @escaping (Error?) -> Void)
  var operationQueue: OperationQueue { get }   // where the write runs
  ```
  **The write callback is asynchronous with a completion handler and runs on
  a queue the delegate chooses**, so it is the one Apple drag API that fits
  kaya's ring without any main-thread park: the interpreter can post a
  demand, park the OPERATION QUEUE (not the main thread) on a bounded wait,
  and call the completion handler when the app answers or the deadline
  expires with an error.
- **iOS**: no `NSFilePromiseProvider`. The equivalent is
  `NSItemProvider.registerFileRepresentation(forTypeIdentifier:fileOptions:
  visibility:loadHandler:)`, whose load handler is invoked on demand and
  answers `(URL?, Bool /* coordinated */, Error?)` through a completion
  block. Same shape, different name — so one kaya semantics, two spellings,
  which is what invariant 1 asks for.
- The destination side of a mac promise is
  `NSFilePromiseReceiver` (macOS 10.12+), found with
  `draggingPasteboard.readObjects(forClasses: [NSFilePromiseReceiver.self],
  options: nil)`, then
  `receivePromisedFiles(atDestination:options:operationQueue:reader:)` —
  asynchronous, `reader` called per file with `(URL, Error?)`.

### 5.2 Files IN

- **mac**, unsandboxed (which is what kaya's lane guests are today): the
  pasteboard carries `public.file-url` items; `readObjects(forClasses:
  [NSURL.self], options: [.urlReadingFileURLsOnly: true])` gives real paths
  that open with plain POSIX calls. kaya's existing answer already fits —
  DESIGN's file-dialog ruling hands guests **handles redeemable for open
  descriptors, not paths**, and a dropped file is the same capability
  arriving through a different door (clipboard-plan.md:695 says exactly this
  about `files` on the clipboard).
- **mac, sandboxed**: Apple documents that "certain other user interactions,
  such as dragging items to your app or choosing items from the Open Recent
  menu, **automatically expand your sandbox** to include those items"
  (Enabling App Sandbox, Entitlement Key Reference). No entitlement is needed
  for the drop itself; `com.apple.security.files.user-selected.read-only` /
  `.read-write` cover the panel route, and persistent access past the session
  needs a **security-scoped bookmark**.
  **MEASURED TRAP WORTH RECORDING**: reading a dragged file URL off the
  pasteboard DURING the hover (before the drop) can prevent the sandbox
  extension from being issued at drop time, and the app then fails with
  "Operation not permitted" (POSIX 1) on a file the user really did drop.
  The reported workaround is the undocumented reading-option key
  `NSPasteboardURLReadingSecurityScopedFileURLsKey`
  (https://wadetregaskis.com/mac-app-sandboxing-interferes-with-drag-drop/).
  This is a second, independent argument for DESIGN.md:3044's rule that
  hover is answered from types alone and never by fetching content: on a
  sandboxed mac, fetching content mid-hover does not merely cost time, it
  **breaks the drop**.
- **iOS**: `NSItemProvider.loadFileRepresentation(...)` copies to a temporary
  URL the system deletes after the callback returns;
  `loadInPlaceFileRepresentation(...)` may open in place, and Apple's own
  wording is "**in either case, you must access the returned URL using an
  `NSFileCoordinator` object**" — plus "if the system created a local copy of
  a file, it will be automatically deleted after your file coordinator
  relinquishes its read access". iOS 11+/macOS 10.13+. A document drop from
  Files.app arrives this way.
  **This forces a design point**: on iOS a dropped file's bytes are only
  reachable inside a coordinated read that ends when the callback returns, so
  kaya cannot hand the guest a long-lived path. It CAN hand a descriptor —
  which is precisely the handle-not-path ruling the file dialogs milestone
  already made. **Drag's `files` should redeem through the same
  `kaya_open_picked` door**, with no new vocabulary.

## §6 — REORDER WITHIN A LIST

### 6.1 What Apple offers

- **SwiftUI, at kaya's floor**: `DynamicViewContent.onMove(perform: ((IndexSet, Int) -> Void)?)`,
  iOS 13 / macOS 10.15. It is **INDEX-based** — a source `IndexSet` and a
  destination `Int` offset "relative to the dynamic view's underlying
  collection of data". On iOS it needs edit mode (or a long press on a `List`
  row) to expose the grab handles; on macOS a `List` row drag works directly.
  `.moveDisabled(_:)` opts a row out.
- **SwiftUI, macOS 26+/iOS 26+**: `DropSession.reorderDestination(for:in:)`
  and `reorderDestination(for:itemID:in:)` — **key/ID-based**, generic over
  Item and CollectionID, with a `KeyPath` overload. Apple moved from indices
  to ids in the same direction kaya already went.
- **AppKit floor**: `NSTableView`/`NSOutlineView`/`NSCollectionView` are
  themselves `NSDraggingSource`s.
  `tableView(_:pasteboardWriterForRow:)` supplies the item;
  `tableView(_:validateDrop:proposedRow:proposedDropOperation:) -> NSDragOperation`
  is the sync hover verdict with an `.above`/`.on` distinction;
  `tableView(_:acceptDrop:row:dropOperation:) -> Bool` performs it.
- **UIKit floor**: `UITableViewDragDelegate`/`UITableViewDropDelegate` and the
  collection-view twins, with `UITableViewDropProposal(operation:intent:)`
  where `intent` is `.insertAtDestinationIndexPath` /
  `.insertIntoDestinationIndexPath` / `.unspecified` — the same
  between-rows vs onto-a-row split mac spells as `NSTableView.DropOperation`.

### 6.2 What kaya should take from it

- The **between-rows vs onto-a-row** distinction is real on all four
  platforms and has no kaya spelling today. A `reorderable` prop plus a
  move-request occurrence must carry it, or a drop "onto" a row is
  indistinguishable from a drop "before" it. Cheapest shape that stays
  key-based: the occurrence carries the ANCHOR key and a flag for
  before/onto, which is exactly `collection_move`'s `(key, before)` pair with
  one bit added.
- **`collection_move` already is the landing op** and it is key-based
  (`CollectionMove { id, path, key, before }`, docs/probes/undo-recon-surface.md:40),
  so the request/confirm shape DESIGN uses for window close applies
  unchanged: the platform proposes, kaya emits an occurrence, the app issues
  `collection_move`, the core reorders and the backend's `move_child` runs.
  Nothing new is needed on the apply side.
- **Do NOT lower reorder onto `List.onMove`.** It is index-based, which
  DESIGN.md:3543 explicitly refuses ("an index would race the very deltas
  that change it"), and it would need a second, index-shaped occurrence that
  the other three backends have no reason to want. Lower reorder as an
  ordinary drop whose destination is a row-anchor within the same For, and
  let the backends draw the insertion affordance.
- **iOS edit mode is a real divergence to state**: a `List` on iOS shows
  reorder handles only in edit mode by default, where mac lets you drag a row
  directly. If kaya declares `reorderable`, the iOS lowering has to decide
  between always-on long-press drag (a custom `UIDragInteraction`-shaped
  answer, which the SwiftUI interpreter's synthesized table tier can do) and
  edit mode. That is a visual ruling for the maintainer.

Sources:
- https://developer.apple.com/documentation/swiftui/dynamicviewcontent/onmove(perform:)
- https://developer.apple.com/documentation/swiftui/dropsession
- https://developer.apple.com/documentation/appkit/nstableviewdatasource
- https://developer.apple.com/documentation/uikit/uitableviewdropproposal

## §7 — HARNESS OBSERVABILITY (the hard part)

### 7.1 macOS: four candidate paths, ranked

**(a) CGEvent into the HID stream — REJECT, and the repo already wrote down
why.** swift/KayaSwiftUI.swift:13316 (the `type` verb): "CGEvent posting into
the HID stream would type at whatever is frontmost, which under a five-lane
matrix is rarely this process, and it charges the accessibility permission
besides." A drag is many events over a second or more, with the drop's
correctness depending on the cursor being over the right window the whole
time — every objection is strictly worse. A developer report of exactly this
attempt shows `.leftMouseDown` and `.leftMouseUp` landing while
`.leftMouseDragged` does not reach some destinations
(https://developer.apple.com/forums/thread/746133, unanswered).

**(b) Synthetic `NSEvent`s through `NSApp.sendEvent` — STARTS a drag, cannot
FINISH one.** This is the `type` verb's own shape and it would correctly
deliver `.leftMouseDown` / `.leftMouseDragged` to the view under the point.
But the moment SwiftUI (or kaya) calls
`beginDraggingSession(with:event:source:)`, AppKit takes over with its own
tracking, driven by the window server's real cursor, not by `sendEvent`.
Apple documents that the method "returns immediately and the drag begins at
the next turn of the run loop" — after which the synthetic stream is no
longer the input. So (b) is a dead end for a full drag, though it remains the
only way to test that a SOURCE widget starts a session at all.

**(c) A fake `NSDraggingInfo` handed straight to the destination — WORKS,
in-process, no permissions, and it is a REAL platform-code exercise.**
`NSDraggingInfo` is a **protocol**, not a class. A test double can conform to
it (`draggingPasteboard`, `draggingSourceOperationMask`, `draggingLocation`,
`draggingSequenceNumber`, `numberOfValidItemsForDrop`, `draggingSource`,
`draggingFormation`, `animatesToDestination`, `springLoadingHighlight`, plus
no-op `enumerateDraggingItems` / `slideDraggedImage` / `resetSpringLoading`),
put real bytes on a real `NSPasteboard(name:)`, and call the destination's
`draggingEntered(_:)`, `draggingUpdated(_:)`, `prepareForDragOperation(_:)`,
`performDragOperation(_:)` and `concludeDragOperation(_:)` in order. Every one
of kaya's real verdict computations runs; only the window server's tracking
loop is absent. This is the same trick the repo already uses for
`check-empty-child`, `check-pane-ladder` and `check-table-tier` — compile the
interpreter's own source with a probe and run it against real AppKit objects.
**The catch, and it is a design-forcing one:** this path exists only if
kaya's mac drop destination is an `NSView` conforming to
`NSDraggingDestination` (i.e. an `NSViewRepresentable`), because SwiftUI's
`DropInfo` is a struct with **no public initializer**, so a `DropDelegate`
cannot be driven with a fabricated info. **So the observability requirement
argues for the AppKit floor over `DropDelegate` on mac, reversing §1.4's
provisional ranking. That is a ruling for the maintainer** — it is the same
trade the table tier already made (native `NSTableView` under a SwiftUI
surface).

**(d) Drive kaya's own drag state machine directly — the primary recommended
path, and the one consistent with every existing verb.** kaya's `click` verb
does not synthesize a mouse click; it resolves the node and calls
`KayaHost.emit(node.tag)` (KayaSwiftUI.swift:5853). `toggle`, `set_value`,
`choose` all write the model inside `kayaUserWrite` and emit. The uniform
answer for drag is the same: put kaya's hover/verdict/payload logic in ONE
function per backend that the platform callback calls, and let the harness
verb call that same function with a synthesized session. Then the verb is
implementable identically in all four backends (which is what invariant 6
needs, since one .steps file feeds all five lanes) and the scene's assertions
are byte-identical because they read the MODEL, not the platform.

**Recommended macOS shape: (d) as the lane verb + (c) as a gate.** The lane
legs use (d) on all five platforms; a mac-only gate in the
`check-pane-ladder` family compiles the interpreter's own drop source with a
probe, runs a real `NSPasteboard` through the real
`NSDraggingDestination` arms, and proves that the platform wiring the lane
verb bypasses is actually connected. That is the repo's own answer to "a gate
that can be satisfied without exercising the real thing is a bug in the gate"
(invariant 4).

### 7.2 iOS simulator

**Do not re-attempt HID synthesis.** docs/deferred.md:10168 already measured
that simdrive's `swipe` (down + interpolated down-state + up, idb's own
encoding) is accepted by the runtime and **does not pan SwiftUI**, that
`IndigoHIDMessageForScrollEvent` was reverse-read and no permutation moved
content, and that synthetic CGEvents reach the Simulator's mac chrome but not
the device content view. A drag is a pan with a long-press prefix, so it is
strictly harder than the thing already measured not to work. That entry's own
conclusion stands: "THE GUARANTEED PATH if pan synthesis is ever needed: a
resident XCUITest driver (XCUICoordinate press/drag)".

If XCUITest is ever built, the API is
`XCUICoordinate.press(forDuration:thenDragTo:)` (and
`press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)`, whose HOLD
is reported not to fire — https://developer.apple.com/forums/thread/705304),
with `click(forDuration:thenDragTo:)` as the macOS spelling. Reported
caveats: coordinate accuracy off by several pixels, and long-press gesture
recognizers ending early under automation (the common workaround is swizzling
`UILongPressGestureRecognizer`, which kaya would not accept).

**Recommendation for iOS: path (d) only.** It costs nothing, it is the same
code the other four lanes run, and it needs no new runner app. Record in the
ledger that the iOS leg does NOT exercise `UIDragInteraction`'s own gesture
recognizer, and name the trigger for building the XCUITest driver (a defect
that could only be caught by a real touch).

### 7.3 What a scene can assert byte-identically on all five lanes

Everything platform-drawn is off the table: the cursor badge (mac has one,
iOS has none), the lift animation, the drag preview, the snap-back animation,
the iOS item-count badge, the insertion caret. What IS uniform:

- **the occurrence the app received** — its tag, its clip kind, and its bytes.
  This is already the `pasted` record's shape (clipboard-plan.md:577, a click
  tag followed by the clip kind and its values, `path_len` deciding live vs
  stamped), so a `dropped` occurrence can be byte-identical to `pasted` and
  the scene can assert on it with existing readers.
- **the OPERATION the destination proposed and the one the source was told**
  — a `copy`/`move`/`none` string, which every platform has. `move` is the
  interesting one because it is the branch DESIGN forbids a wait from
  committing.
- **the model consequence**: rows after a reorder (`expect_rows`), a label
  the guest wrote on drop, a count.
- **the REFUSAL**: a drop that misses the deadline, asserted as "nothing
  changed" plus a guest-visible reason. Since the whole point of the bounded
  wait is its expiry, the scene must be able to FORCE an expiry — an
  app-thread stall the harness can request — or the fail-safe path is never
  watched failing, which invariant 3 forbids.

Sketch of a shared .steps fragment (spelling to be ruled):

```
drag button#0 to list#1 row "b"
expect label#status "drop copy text 'alpha'"
expect rows list#1 "a,alpha,b,c"
drag_stall 400
drag button#0 to list#1 row "b"
expect label#status "drop copy text 'alpha'"     # unchanged: the drop was rejected
expect rows list#1 "a,alpha,b,c"
```

## §8 — CROSS-PROCESS DROPS (Finder and other apps)

- **mac, unsandboxed** (what kaya's lane guests are today — nix-built
  binaries, no bundle): nothing is required. `registerForDraggedTypes`
  (AppKit) or `onDrop(of: [.fileURL], ...)` (SwiftUI) is the whole opt-in,
  and a Finder drag delivers `public.file-url` items whose paths open with
  plain POSIX calls.
- **mac, sandboxed** (what a distributed kaya app would be): Apple documents
  that "certain other user interactions, such as **dragging items to your
  app** or choosing items from the Open Recent menu, automatically expand
  your sandbox to include those items" — so the drop itself needs NO
  entitlement. `com.apple.security.files.user-selected.read-only` /
  `.read-write` cover the panel route; access past the current launch needs a
  security-scoped bookmark. The measured trap in §5.2 (reading the URL during
  hover can prevent the extension from being issued at drop, with
  `NSPasteboardURLReadingSecurityScopedFileURLsKey` as the reported
  workaround) is the one thing that would bite a naive implementation, and
  kaya's hover-from-types-only rule already avoids it.
- **iOS**: no entitlement for receiving a drop. Cross-app drag is a system
  policy (iPad since iOS 11 in Split View / Slide Over and via the Home bar
  since iPadOS 15; iPhone in-app only through iOS 14, between apps from
  iOS 15). A source can opt out with
  `dragInteraction(_:sessionIsRestrictedToDraggingApplication:) -> true`.
  iOS 16's paste-permission prompt is documented as applying to *programmatic*
  pasteboard reads and not to routes where the user's own gesture is the
  consent (the Paste menu item, ⌘V, `UIPasteControl`); a drop is the same
  shape of explicit gesture. **That last inference is REASONED, NOT MEASURED —
  probe it before it is written down as a fact**, exactly as
  docs/clipboard-plan.md §0d probed the seeded-content prompt and found the
  assumption wrong on every platform it checked.
- **Custom formats across processes**: on mac the id rides the pasteboard as a
  raw type string, which kaya already measured round-tripping byte-identically
  (clipboard-plan §1b). Whether a SwiftUI drag of an undeclared custom UTI
  needs `UTExportedTypeDeclarations` in the Info.plist — and hence whether the
  UNBUNDLED lane guests can carry a `custom` representation across processes
  at all — is the single biggest unknown in this whole area and is the first
  thing a probe should answer.
- **`NSItemProviderRepresentationVisibility`** (`.all` / `.team` /
  `.ownProcess`) is the platform's own scope knob for a representation. kaya
  has no spelling for it; the safe default is `.all`, matching the clipboard,
  and a per-representation visibility is a deliberate cut with an obvious
  trigger (an app that wants an internal format not visible to other apps).

## §9 — The design pass in plain English, and the rulings the maintainer owes

### 9.1 What a drag actually is, on both Apple platforms

A drag is a conversation between two parties held entirely on the MAIN
THREAD, in three acts.

**Act one, the pickup.** The source app is asked, synchronously, "what are you
handing over?" On mac that is `beginDraggingSession(with:event:source:)`,
which the app calls itself from a mouse-drag handler; on iOS it is
`dragInteraction(_:itemsForBeginning:)`, which the system calls and which
returns an array — an empty array means no drag. Either way the app answers a
LIST OF ITEMS, and each item is a bag of representations keyed by type. The
bytes need not be there yet: a representation can be a closure the system
calls later.

**Act two, the hover.** As the finger or cursor moves, the destination is
asked, over and over and synchronously, "would you take this, and as what?"
The answer is one small value: on mac a bitmask (`NSDragOperation`), on iOS a
`UIDropProposal` carrying one of copy / move / forbidden / cancel. The
destination is told which TYPES are on offer and where the pointer is; it is
NOT given the bytes, and on a sandboxed mac asking for the bytes here can
actually break the later drop. Apple's own 2025 API repeats the point in its
documentation: the configuration closure "is called frequently for different
drop locations — avoid expensive calculations."

**Act three, the drop.** The destination is told to take it. On mac that is
`performDragOperation` returning a Bool that means "I have taken
responsibility", after which the app may finish asynchronously; on iOS it is
`performDrop`, which returns nothing at all and is explicitly designed for an
async transfer with a system progress indicator. Then the SOURCE is told what
happened — `draggingSession(_:endedAt:operation:)` or
`dragInteraction(_:session:didEndWith:)` — and that is where a `move` source
deletes its original.

### 9.2 The one sentence that matters for kaya

**The hover verdict cannot be deferred on either Apple platform, at any tier,
and the drop's ACCEPTANCE cannot either — only the drop's COMPLETION can.**
That is the single fact that should drive the ruling, and it means DESIGN.md's
drag paragraph is right in its instinct and slightly off in its placement: the
pre-pushed vocabulary is not a nicety, it is the only implementable design;
and the bounded wait cannot go where "the drop verdict" naively suggests,
because parking `performDrop` parks the main thread inside the platform's own
tracking loop.

### 9.3 The rulings, each stated as a question with a recommendation

1. **Where does the bounded wait live?**
   Recommendation: nowhere on hover (answer from core-side state, zero
   deadline), and on the drop only for the irreversible branch. Concretely:
   `copy` drops accept optimistically and reconcile through the app's own
   later transaction; `move` drops take a bounded main-thread wait with a
   deadline in the low hundreds of milliseconds, expiring to a rejection and
   the platform's own snap-back
   (`NSDraggingSession.animatesToStartingPositionsOnCancelOrFail`, which is on
   by default and needs no kaya drawing). This keeps DESIGN.md:3003's rule —
   a wait may not silently commit an irreversible branch — while not making
   every ordinary copy pay a main-thread park.

2. **What is the operation vocabulary?**
   Recommendation: `copy`, `move`, `link`, `none`, carried as a SET on the
   wire (mac and Windows both have masks; SwiftUI and iOS narrow to one).
   `link` is stated as unrepresentable on iOS and Android and lowers to
   `copy` there — a carve-out stated uniformly, per invariant 1. iOS's
   `forbidden` vs `cancel` distinction is a badge nuance kaya can derive
   (declared-accepting-but-refusing-here = forbidden; not-accepting = cancel).

3. **Do drop and paste share the record?**
   Recommendation: yes, and the ledger already argued it
   (clipboard-plan.md:207). A `dropped` occurrence is a `pasted` occurrence
   plus (a) the destination widget's tag and drop point, (b) the anchor key
   and before/onto bit when the destination is inside a `For`, and (c) the
   operation. Same `Representation` sum, same blob table, same eight-binding
   spelling.

4. **May a drag promise its bytes?**
   Recommendation: `files` only, on the source side, through
   `NSFilePromiseProvider` (mac) and `registerFileRepresentation` (iOS) —
   both asynchronous with completion handlers, both off the main thread. Keep
   `text`/`html`/`image`/`custom` eager, which preserves
   clipboard-plan.md:220's ruling and avoids
   `NSPasteboardItemDataProvider`, the one Apple promise API with no async
   escape.

5. **One item, or many?**
   Recommendation: hold the clipboard's one-item ruling; a multi-file drag is
   one clip whose `files` representation is a list. State the carve-out: iOS's
   `itemsForAddingTo` (a second finger adding items mid-drag) is refused, and
   a drag from another app carrying several heterogeneous items is collapsed
   to the richest single representation kaya understands.

6. **Which mac tier does the backend use?**
   Recommendation: the AppKit floor via `NSViewRepresentable`, NOT SwiftUI's
   `DropDelegate` — because `DropInfo` has no public initializer and
   `DropDelegate` therefore cannot be exercised by an in-process gate, while
   `NSDraggingInfo` is a protocol a test double can conform to. Same trade the
   table tier already made. If the maintainer prefers `DropDelegate` for its
   layout integration, then §7's gate (c) is off the table and the platform
   wiring is proven only by a human dragging.

7. **Is `reorderable` a prop, and what does it emit?**
   Recommendation: a per-`For` prop, and the occurrence is a move REQUEST
   carrying (moved key, anchor key, before/onto) — key-shaped, matching
   `collection_move` exactly, and matching what Apple itself moved to in 2025
   (`DropSession.reorderDestination`). The app confirms with the existing
   `collection_move`; the core reorders; `move_child` runs. No new apply op.
   Refuse `List.onMove`, which is index-shaped.

8. **How is it observed?**
   Recommendation: one harness verb driving kaya's own drag state machine in
   all four backends (the `click` verb's shape), plus a mac-only in-process
   gate that runs the real `NSDraggingDestination` arms against a real
   `NSPasteboard` (the `check-pane-ladder` shape). Assertions are on the
   occurrence, the operation and the model — never on badges, previews or
   animations. And the EXPIRY path must be forcible from the scene, or the
   fail-safe is never watched failing (invariant 3).

9. **Spring loading?** Recommendation: out, with a stated trigger. It is a
   separate opt-in API on each Apple platform (`NSSpringLoadingDestination`,
   `UISpringLoadedInteraction`) and has no uniform analogue on GTK, WinUI or
   Android.

### 9.4 The unknowns that should be PROBED before an arm is written

Following docs/clipboard-plan.md §0d's own discipline ("Measuring the platform
before writing an arm overturned an assumption on EVERY platform during file
dialogs, including one where the wrong arm had already been written"):

1. **Does a `custom` MIME-shaped id survive a DRAG on macOS from an UNBUNDLED
   binary?** The clipboard probe measured the pasteboard round trip; drag adds
   `registerForDraggedTypes` / `hasItemsConforming` and at least one developer
   report claims `UTExportedTypeDeclarations` is required. kaya's lane guests
   have no Info.plist. Probe bundled AND unbundled, exactly as
   tools/mac/clipprobe did.
2. **How long may `performDragOperation` park before the user sees a
   beachball?** Measure it; the deadline in ruling 1 should be a measured
   number, not a guess.
3. **Does an iOS drop from another app trigger iOS 16's paste prompt?**
   Reasoned "no" above; the clipboard milestone's own history says reason it
   and then measure it.
4. **Does the simulator deliver a cross-app drag at all**, or is the iOS lane
   permanently in-app only?
5. **Does a synthetic `NSEvent` mouse-drag through `NSApp.sendEvent` start a
   real `NSDraggingSession`?** If yes, the SOURCE half has an in-process
   observability path too, even though the destination half does not.
