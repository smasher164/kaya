# Range controls: Compose material3, Material Components (Views), React Native libraries

Source read: files downloaded with curl into scratchpad/range/src (gone) and read directly (not summarised by a model).

## 1. Jetpack Compose material3 `RangeSlider`

Source: androidx-main as of 2026-09-24 (commit 32a0e70058),
https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/Slider.kt
(line numbers below are that file's).

- (a) Yes: `RangeSlider(state: RangeSliderState, onValueChange, ...)` with `RangeSliderState(startValue, endValue, steps, trackRange)` (l.621/729/826, class at ~l.3640).
- (b) BUILT AS ONE CONTROL WITH TWO THUMB CHILDREN, not two sliders. `RangeSliderImpl` (l.1400) is one `Layout` with three children tagged `STARTTHUMB`, `ENDTHUMB`, `TRACK`; the thumbs are slot composables (`startThumb`, `endThumb`, `track` lambdas). ONE `pointerInput` (`rangeSliderPressDragModifier`, l.3047) sits on the whole Layout and owns every press; the thumb boxes carry no pointer handling of their own, only semantics, key handling and `focusable`. Closest to "two thumb parts templated inside one control", with the parent owning input.
- (c) Routing, current code (l.3069-3079): on `awaitFirstDown`, `compareOffsets(posX)` compares `|rawOffsetStart - x|` with `|rawOffsetEnd - x|` (l.3196); NEAREST thumb wins. TIE (thumbs at the same spot, equal distance): `draggingStart = state.rawOffsetStart > posX`, i.e. a press to the left of the stacked thumbs takes the START thumb, at or right of them the END thumb. The thumb is chosen at press-down, before any movement. A tap (no drag) moves the chosen thumb to the tap point (l.~3140). A press whose slop is mostly vertical is cancelled so a parent can scroll.
  HISTORY: until 2025-07-24 the tie was broken BY DRAG DIRECTION: `awaitSlop(...)` then, if the press was within slop of BOTH thumbs, `draggingStart = if (isRtl) dir >= 0f else dir < 0f` (drag left takes the start thumb). Removed in commit d6ee1715ed "[Slider] Improve range slider drag logic", b/399393886: https://github.com/androidx/androidx/commit/d6ee1715ed20f18ab7ca173669338174948abfbf . So material3 1.3.x (the version kaya measured) used drag direction; androidx-main uses press position. z-order: the Layout places children in the order start thumb, end thumb, track (placement order is draw order), but since input is owned by the parent, z-order plays no part in hit testing.
- (d) STOP. `RangeSliderState.onDrag` (l.3701) coerces the dragged start offset into `minPx..offsetEnd` and the end into `offsetStart..maxPx`; the `startValue`/`endValue` setters coerce `newVal.coerceIn(trackRange.start, endValue)` and `coerceIn(startValue, trackRange.endInclusive)`. No crossing, no pushing; thumbs may coincide (start == end allowed; no min-separation parameter). The coercion replaced a tolerance after a float-rounding crash: commit 1f4387cd5c "[GH] Coerce slider range when dragging to avoid overlap", https://issuetracker.google.com/issues/324934900 .
- (e) TWO ADJUSTABLE ELEMENTS. Each thumb Box has its own semantics node: `rangeSliderStartThumbSemantics` / `rangeSliderEndThumbSemantics` (l.2891/2945) = `progressSemantics(value, range, steps)` (Android maps it to `AccessibilityNodeInfo.RangeInfo`, i.e. a SeekBar-like node) plus a `setProgress` action and `stateDescription` = the value to 2 decimals, merged with `contentDescription` = `Strings.SliderRangeStart` / `SliderRangeEnd`. The RANGE each node advertises is the other thumb's bound: start node range = `trackRange.start..endValue`, end node = `startValue..trackRange.endInclusive`, and step counts are rescaled (`startSteps`, `endSteps`). `setProgress` returns false if unchanged "to keep it consistent with AbsSeekbar.java". So TalkBack sees two sliders and can adjust each with volume keys/swipe. Default spoken names: "Range start" and "Range end" (compose/ui strings.xml, `range_start`/`range_end`: https://github.com/androidx/androidx/blob/androidx-main/compose/ui/ui/src/androidMain/res/values/strings.xml). The app cannot override those via a parameter; it would have to add its own semantics in the thumb slot (unverified whether a slot's semantics override the merged contentDescription).
- (f) Each thumb is `.focusable(...)` with its own interaction source, so Tab/D-pad focus traversal visits start then end. `rangeSliderOnKeyEvents` (l.1217): Left/Right move by one step (or 1% of range when steps == 0), PageUp/PageDown by `(steps/10).coerceIn(1,10)` steps, Home/End go to the thumb's allowed bounds (start thumb: Home = trackRange.start, End = endValue); RTL reverses; KeyUp fires `onValueChangeFinished`. Up/Down deliberately DO NOT change a horizontal slider so D-pad focus is not trapped (commit d1433cd59f, b/460912699, https://github.com/androidx/androidx/commit/d1433cd59f363a10880f0c6fec33d62b58a78f9d). Keyboard support for RangeSlider was broken until commit 0dd7d89873 (2025-08-27, b/424845268).
- (g) `VerticalSlider(state, onValueChange, ..., topToBottom)` exists for the SINGLE slider (l.448/537; `reverseVerticalDirection`). There is NO vertical RangeSlider: no `RangeSlider` overload takes an orientation, and the range drag is `horizontalDrag` only (l.~3110).
- Stacking: not used. No problems of the stacked kind apply.

## 2. Material Components for Android (Views) `RangeSlider`

Source: master,
https://github.com/material-components/material-components-android/blob/master/lib/java/com/google/android/material/slider/BaseSlider.java
and .../slider/RangeSlider.java (line numbers are BaseSlider.java's unless stated).

- (a) Yes: `com.google.android.material.slider.RangeSlider` (`extends BaseSlider<RangeSlider, ...>`, RangeSlider.java l.58). Not first-party Android framework (the framework has only `SeekBar`); it is Google's Material library.
- (b) ONE CUSTOM-DRAWN VIEW OWNING N THUMBS. `BaseSlider extends View` (l.243) keeps `List<Float> values` (sorted with `Collections.sort`, l.915) and draws every thumb itself. `Slider` and `RangeSlider` are the same class with 1 vs N values; RangeSlider supports more than two thumbs. No child views; no stock SeekBar underneath.
- (c) Routing: `pickActiveThumb()` (l.3497) picks the thumb whose VALUE is nearest the touch value. TIE (thumbs at the same value): if the touch is within `scaledTouchSlop` of the stacked thumbs it returns false ("Two thumbs on the same value and we don't have enough movement to use direction yet", l.3524) and the choice is DEFERRED to ACTION_MOVE, where the later thumb wins if the finger has moved forward (`movingForward`, reversed for RTL and vertical), else the earlier thumb: TIE BROKEN BY DRAG DIRECTION. On ACTION_DOWN inside a scrolling container the pick is also deferred to ACTION_MOVE (l.3360-3368). Tap = down/up within slop picks and snaps (l.3416-3426). ACTION_CANCEL restores the value from touch-down (`snapThumbToPreviousDownTouchEventValue`, l.3438). No z-order question: one View does its own hit testing.
- (d) STOP, with optional MIN SEPARATION. `getClampedValue` (l.3591), commented "Thumbs cannot cross each other, clamp the value to a bound or the value next to it": the bound is the neighbour's value -/+ `minSeparation`. `minSeparation` is settable as a dimension (`setMinSeparation`, px) or a value (`setMinSeparationValue`), validated `>= 0` and a multiple of `stepSize` (l.755-770). No crossing option exists in the file (searched "cross"/"Crossing": only the comment above). Observed but not tested: for RTL or vertical the code negates `minSeparation` before computing the bounds (l.3594), which looks as if it would permit overlap there; unverified. Issues: #2147 "setMinSeparationValue has no effect" https://github.com/material-components/material-components-android/issues/2147 ; drawing bugs when the thumbs overlap, #1394, #1924, #3289 (still open) https://github.com/material-components/material-components-android/issues/3289 .
- (e) TWO (N) VIRTUAL VIEWS via `AccessibilityHelper extends ExploreByTouchHelper` (l.4345). `getVisibleVirtualViews` lists one id per value; `getVirtualViewAt` hit-tests the thumb bounds; each virtual node gets class name `SeekBar`, `RangeInfoCompat(RANGE_TYPE_FLOAT, valueFrom, valueTo, value)` (the FULL range, not bounded by the other thumb, unlike Compose), actions ACTION_SET_PROGRESS and SCROLL_FORWARD/BACKWARD (scroll step = ~1/20th of the range). Content description = `[view's contentDescription,] "Range start, <value>"` / `"Range end, <value>"` (strings `material_slider_range_start`/`_end`, https://github.com/material-components/material-components-android/blob/master/lib/java/com/google/android/material/slider/res/values/strings.xml); middle thumbs of a 3+-thumb slider get an EMPTY type word. If the app sets a stateDescription on the View it is used instead of the value text. So TalkBack can focus and adjust each thumb independently. Keyboard focus on a thumb calls `requestKeyboardFocusForVirtualView`. Past TalkBack issues: #2348 (contentDescription broke reading), #2347 (labelFor did not work).
- (f) One focusable View with a `focusedThumbIdx`. `onKeyDown` (l.4023): TAB moves to the next thumb, Shift+TAB previous (`moveFocus`), returning false at the ends so focus leaves the View; DPAD_LEFT/RIGHT (RTL-swapped) and PLUS/EQUALS/MINUS step the FOCUSED thumb; a long press uses ~1/20th of the range. NO Home/End/PageUp/PageDown and NO DPAD_UP/DOWN handling in `calculateIncrementForKey` (l.4115-4131), including for a vertical slider (unverified whether vertical remaps elsewhere; I found no other key path). On focus gain, `focusThumbOnFocusGained` picks the first thumb for FOCUS_FORWARD/RIGHT, the last for FOCUS_BACKWARD/LEFT.
- (g) Yes: `android:orientation` HORIZONTAL/VERTICAL (`setOrientation`, l.2537), added 2024-11-12 in commit 5bcda8a8d7 "[Slider] Add vertical support" (applies to RangeSlider too, being BaseSlider). Vertical is treated like RTL in the geometry (`isRtl() || isVertical()` throughout).
- Stacking: not used.

## 3. React Native libraries

Sources read from each repo's default branch (HEAD) on 2026-09-29. Issue bodies read with `gh issue view`.

### 3.0 `@react-native-community/slider` (callstack/react-native-slider)
- (a) NO range. Single thumb only, wrapping the platform slider (package/ios/RNCSlider.m, package/android/.../ReactSlider.java; seen in the repo tree, bodies not read). Range requested since 2020 and never built: #172 https://github.com/callstack/react-native-slider/issues/172 (closed; a contributor released the range slider as a separate package, `@sharcoux/slider` 4.0), #269 "Range slider" https://github.com/callstack/react-native-slider/issues/269 (open; maintainer: "quite an implementation to do ... postpone"). The #172 requester said "Currently i have to use 2 separate sliders to get the range" (two sliders side by side, not stacked).
- (b)-(g) n/a.

### 3.1 `@ptomasroos/react-native-multi-slider` (MultiSlider.js)
https://github.com/ptomasroos/react-native-multi-slider/blob/master/MultiSlider.js
- (a) Third-party, `MultiSlider` with `values=[a,b]`.
- (b) ONE JS COMPONENT, TWO THUMB VIEWS, each owning its own gesture. Plain `View`s: track in three segments, then two absolutely positioned 48x48 `markerContainer` views, each with its OWN `PanResponder` (`_panResponderOne`, `_panResponderTwo`); a third `_panResponderBetween` on the middle track segment drags both thumbs together. Not stock sliders.
- (c) Routing by HIT TESTING THE THUMB VIEWS: a touch goes to whichever marker view is on top at that point; there is no nearest-thumb logic and a press on the bare track does nothing (except the middle segment, which moves both). Z-ORDER HACK: marker one gets `zIndex: 1` (`topMarkerContainer`) when `positionOne > sliderLength / 2`, so the LOWER thumb is on top in the right half and the upper thumb in the left half; and marker two is not rendered at all when `positionOne === sliderLength` (l.~620). Documented failure of exactly this: #280 "Markers don't move in one direction when overlapping" (open, 2023): with both thumbs at the same value "on the left side, I'm unable to move the marker down until i move the other marker back up", and the mirror on the right: https://github.com/ptomasroos/react-native-multi-slider/issues/280 . A user patch in that thread makes the covered thumb PUSH the other. PR #236 referenced as a possible fix (not read).
- (d) STOP by default: `moveOne` confines to `positionTwo - (allowOverlap ? 0 : minMarkerOverlapDistance > 0 ? minMarkerOverlapDistance : (minMarkerOverlapStepDistance || 1) * stepLength)` (l.~200), so the default keeps them at least one step apart; `allowOverlap` lets them coincide, never cross. Issues #105 "Overlapping allowed even though allowOverlap is false", #238 "minMarkerOverlapStepDistance doesn't work".
- (e) NONE built in: the file contains no `accessible`/`accessibility*` prop (grep of MultiSlider.js and DefaultMarker.js returned nothing). #218 "Accessibility (TalkBack) support?" (open, 2020): even with `accessible accessibilityRole='adjustable'` on a custom marker, TalkBack could focus it but not adjust it ("Nothing"); a commenter: "Doesn't work on ios as well with voice over". https://github.com/ptomasroos/react-native-multi-slider/issues/218 . #254 web keyboard/screen reader not accessible (open).
- (f) No keyboard handling (none in the source).
- (g) `vertical` prop: the whole container is ROTATED `-90deg` by transform (l.~542), with gesture axes swapped.
- STACKING NATIVE SLIDERS, #76 "Using native sliders to make range slider" (2018): a user stacked two RN `<Slider>` (native UISlider/SeekBar) with `position: 'absolute'` "for native perf and perfect native look"; problems reported: "not being able to slide the one underneath. And preventing overlap is another", and "on press down, it should grab the slider that the press it is closest to ... tried for about a day"; maintainer declined to help, no resolution posted. https://github.com/ptomasroos/react-native-multi-slider/issues/76

### 3.2 `rn-range-slider` (githuboftigran)
https://github.com/githuboftigran/rn-range-slider/blob/master/index.tsx
- (a) Third-party `RangeSlider` (`low`, `high`, `minRange`, `disableRange`).
- (b) ONE COMPONENT, ONE TOUCH OWNER: two `Animated.View` thumbs are drawn, then a transparent `touchableArea` View is laid OVER everything with the single `PanResponder` (index.tsx l.~317). Thumbs are render-props (`renderThumb('low'|'high')`).
- (c) NEAREST thumb at grant: `isLowCloser(downX, lowPosition, highPosition)`; TIE when both thumbs are at the same position: `downX < lowPosition` picks low, else high (helpers.ts l.6-7) = BY PRESS SIDE, same rule as Compose main. Starts only if `|dx| > 2|dy|`.
- (d) STOP with `minRange`: low limited to `high - minRange`, high to `low + minRange` (l.233-234).
- (e) NONE: no accessibility props in index.tsx or hooks.tsx (grep returned nothing). Thumbs sit under the touch overlay, so even an app-labelled thumb would not receive the gesture (inference, not tested).
- (f) None. (g) No vertical prop found.

### 3.3 `@miblanchard/react-native-slider`
https://github.com/miblanchard/react-native-slider/blob/master/src/index.tsx
- (a) Third-party `Slider` taking `value` as a number or an ARRAY (any number of thumbs; values clamped and sorted, l.82-91).
- (b) ONE COMPONENT, ONE `PanResponder` on the container; thumbs drawn as `Animated.View`s. Not stock sliders.
- (c) `_thumbHitTest` (l.540): walks thumbs IN INDEX ORDER and takes the FIRST whose touch rect contains the point, so with overlapping thumbs thumb 0 always wins; if none is hit and `trackClickable` (default true), the thumb with the smallest track distance wins (`indexOfLowest`).
- (d) STOP with a built-in gap, 2-thumb case only: while dragging thumb 1 its minimum is `values[0] + buffer`, thumb 0's maximum `values[1] - buffer`, where `buffer = step || 0.1` (l.420-428). So two thumbs can never coincide exactly, which also avoids the stacked-tie case. With 3+ values no neighbour constraint exists in `_getValue` (read; behaviour then relies on the re-sort, unverified).
- (e) NONE in the source (grep for "accessib" returned nothing). No accessibility issues found by search (search returned no issues; absence of complaints, not evidence of support).
- (f) None. (g) `vertical` prop: container rotated `-90deg` (l.~803).

### 3.4 `react-native-awesome-slider` (alantoa)
- (a) NO range: single `progress` shared value (src/slider.tsx). #9 "Implement range" owner: "Sorry, currently not supported", recommends miblanchard https://github.com/alantoa/react-native-awesome-slider/issues/9 ; #50 same question, user went to rn-range-slider. No accessibility code found (grep "accessib" in slider.tsx returned nothing).

### 3.5 `@sharcoux/slider` (Sharcoux/slider) — the one RN library found WITH accessibility
https://github.com/Sharcoux/slider/tree/master/src (the package callstack's #172/#269 point to)
- (a) Third-party `RangeSlider` (`range=[min,max]`, `minimumRange`, `crossingAllowed`).
- (b) ONE COMPONENT: one `ResponderView` owns all touches; two `Thumb` views (components/Thumb.tsx) drawn inside; not stock sliders.
- (c) `useRange.updateClosestValue` (hooks/useRange.ts l.71): on press, NEAREST value; tie (`minValue === maxValue`) broken by press side, `value < minValue` takes min. During a drag the held thumb stays held.
- (d) STOP by default (`minimumRange` bounds each thumb by the other). With `crossingAllowed`, the thumbs SWAP: when the dragged value passes the other, the held thumb identity flips and the other thumb is set to the crossing point ("When the 2 thumbs cross, we set the other thumb to the max possible value"); `onValueChange` always reports the sorted pair.
- (e) TWO ADJUSTABLE ELEMENTS: each Thumb view is `accessible`, `accessibilityRole='adjustable'`, `accessibilityActions` increment/decrement (step, or a tenth of the range), `accessibilityValue {min,max,now}` (rescaled to 0-100 when any number is fractional, since "Accessibility values cannot be decimal"), `accessibilityLabel={thumb}` where `thumb` is the literal `'min'` or `'max'` (RangeSlider.tsx l.136-138): the spoken names are "min" and "max", untranslated. The per-thumb accessibilityValue advertises the WHOLE track range, not the bound set by the other thumb. Not tested with a screen reader by me.
- (f) Web only: `onKeyDown` on each focusable thumb, ArrowUp/Right increment, ArrowDown/Left decrement; no Home/End/PageUp.
- (g) `vertical` prop, laid out as a column (flexDirection), not a rotation.

## Summary for kaya's question
- No toolkit or library assigned here builds its range control by STACKING TWO STOCK SLIDERS. Compose and the Views RangeSlider are each one control that owns every press and exposes two per-thumb accessibility nodes (Compose: two real semantics nodes; Views: two ExploreByTouchHelper virtual views), both named "Range start"/"Range end".
- The one recorded attempt to stack two native sliders (RN multi-slider #76, 2018) hit exactly the problems kaya must plan for: the lower slider cannot be grabbed, press-to-nearest routing is not available from stacked native views, and non-overlap has to be enforced from outside. multi-slider's own per-thumb views show the same z-order problem at a coincident value (#280, open).
- Tie-break at a coincident value: Views RangeSlider and Compose ≤1.3 by DRAG DIRECTION (defer until slop); Compose androidx-main (since 2025-07), rn-range-slider and @sharcoux/slider by PRESS SIDE; miblanchard avoids the tie with an enforced gap; multi-slider by z-order.
- All of them STOP; only @sharcoux/slider offers optional crossing (swap); only a user patch to multi-slider PUSHES.
- Per-thumb accessibility range: Compose advertises the bound set by the other thumb; Views and @sharcoux advertise the whole track.
