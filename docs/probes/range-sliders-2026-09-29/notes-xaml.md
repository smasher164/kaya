# Two-thumb range controls in the XAML/.NET family (research notes, 2026-09-29)

Source read directly (gh api / raw.githubusercontent) unless marked otherwise.

## Windows Community Toolkit RangeSelector (WinUI 3 / UWP / Uno)

Source: https://github.com/CommunityToolkit/Windows/tree/main/components/RangeSelector/src
(RangeSelector.cs, .Input.Pointer.cs, .Input.Drag.cs, .Input.Key.cs, .Properties.cs, RangeSelector.xaml)

- (a) Not first-party WinUI; community toolkit control `CommunityToolkit.WinUI.Controls.RangeSelector` (ported from the old WindowsCommunityToolkit in PR #44, 2023-05-08: https://github.com/CommunityToolkit/Windows/pull/44).
- (b) TWO THUMB PARTS TEMPLATED INSIDE ONE CONTROL. `RangeSelector : Control` with template parts `MinThumb`, `MaxThumb` (both `Thumb`, styled with WinUI's own `SliderThumbStyle`), `ActiveRectangle`, all children of one `Canvas x:Name="ContainerCanvas"` (RangeSelector.xaml lines ~306-336). Not stock Sliders: the control positions the thumbs itself with Canvas.SetLeft/SetTop in `SyncThumbs`/`DragThumb`. The track is drawn by the template.
- (c) Routing: `ContainerCanvas_PointerPressed` computes the value under the pointer, compares `|RangeEnd - v|` with `|RangeStart - v|`; if the upper is STRICTLY nearer it takes Max, else Min — so a TIE (thumbs at the same value) always goes to the MIN thumb, no drag-direction tie-break. The pressed thumb jumps to the pointer immediately (RangeEnd/RangeStart = v) and then tracks PointerMoved. Grabbing a thumb itself uses the Thumb's own DragStarted/DragDelta. Z-order: `Thumb_DragStarted` sets ZIndex 10 on the thumb being dragged and 0 on the other, so the LAST-DRAGGED thumb is on top (and gets hit first when stacked). Consequence (my reading, not an observed bug report): both thumbs at Minimum, a press to their right is a tie → Min thumb, which is clamped at Max's position, so it cannot move right; the user must grab the Max thumb directly (which is on top only if it was the last dragged).
- (d) STOP. `DragThumb(thumb, min, max, pos)` clamps between 0 and the other thumb's canvas position (Input.Drag.cs, Input.Pointer.cs). Pushing was requested and not implemented: https://github.com/CommunityToolkit/WindowsCommunityToolkit/issues/4029 ("[Feature] RangeSelector: Moving past second handle", closed without implementation as far as the thread shows).
  Keyboard path: `MinThumb_KeyDown` does `RangeStart += change` then `SyncThumbs(fromMinKeyDown:true)`, which calls DragThumb to clamp the THUMB'S POSITION but discards DragThumb's returned value; the RangeMin callback only clamps to Minimum/Maximum. So from reading, the VALUE could pass the other thumb by keyboard while the thumb is drawn stopped. Unverified at runtime.
- (e) Accessibility: TWO FOCUSABLE ELEMENTS, BUT NEITHER IS ADJUSTABLE. There is no RangeSelectorAutomationPeer (no `OnCreateAutomationPeer`, no "Peer" in any src file; grep of the whole component dir). Each thumb is a stock `Thumb` whose peer is ThumbAutomationPeer (ControlType Thumb, no RangeValue pattern), named via `AutomationProperties.Name="Min thumb"` / `"Max thumb"` (hard-coded English in the xaml). Narrator reads only "Min thumb, thumb"/"Max thumb, thumb" and announces NO value and no change: https://github.com/CommunityToolkit/WindowsCommunityToolkit/issues/3538 (open since 2020-10-21; maintainer marcelwgn: no UIA pattern fits a two-value control, "the closest would be RangeValue", and a custom peer needs subclassing Thumb; Arlodotexe 2021-12-29 proposes "a RangeBaseAutomationPeer on each individual thumb and treat them as separate sliders"). Not ported/fixed in the new repo (no a11y issue there; search https://github.com/CommunityToolkit/Windows/issues?q=RangeSelector).
- (f) Keyboard: both thumbs `IsTabStop=True`, TabIndex 0 and 1 → Tab moves between thumbs. Only arrows: Left/Right when horizontal (flipped under RTL, fix for #819 https://github.com/CommunityToolkit/Windows/issues/819), Up/Down when vertical, by StepFrequency. NO Home/End/PageUp/PageDown (Input.Key.cs `GetKeyboardChange` handles only the four arrows).
- (g) Vertical: yes, `Orientation` property, added 2026-02-10 by PR #756 (https://github.com/CommunityToolkit/Windows/pull/756, issue #755). Vertical puts min at the bottom (UVCoord helper, SyncThumbs "vertical is inverted").
- Other bugs: touch dragging of thumbs broken (https://github.com/CommunityToolkit/Windows/issues/486 open; #520 closed); Minimum==Maximum crashes (#366, #867, old #4110); tooltip clipped (#480); on Uno/WASM the thumbs drew square borders (#386, fixed PR #400).

### Xceed Extended WPF Toolkit RangeSlider — THE STACKED-STOCK-SLIDERS DESIGN

Source: https://github.com/xceedsoftware/wpftoolkit/blob/master/ExtendedWPFToolkitSolution/Src/Xceed.Wpf.Toolkit/RangeSlider/Implementation/RangeSlider.cs and .../RangeSlider/Themes/Generic.xaml (last touched in the v4.7.0 release, 2025-03-10).

- (a) Third-party `Xceed.Wpf.Toolkit.RangeSlider : Control` (LowerValue / HigherValue).
- (b) TWO STOCK WPF `Slider`s OVERLAID. Template parts `PART_LowerSlider` and `PART_HigherSlider` are `typeof(Slider)`, both in the same Grid cell (`Grid.ColumnSpan="5" Grid.Row="1"`), declared after the track. Each is re-templated with `SliderTemplate` = a bare `Track x:Name="PART_Track"` holding only a `Thumb` — NO DecreaseRepeatButton/IncreaseRepeatButton — so each slider's own track has nothing hit-testable but its thumb (Generic.xaml lines ~205-222). The visible track is drawn by the RangeSlider itself: three `RepeatButton`s (`PART_LowerRange`, an unnamed middle one, `PART_HigherRange`) whose widths are computed in code (`AdjustView`: LowerRangeWidth/RangeWidth/HigherRangeWidth), plus a Border. TICKS: a THIRD, hidden-thumb `Slider x:Name="TickSlider"` (Focusable=False, `HorizontalTickSliderTemplate`) exists only to draw the tick bar ("Create a Hidden Slider to only display its Ticks", Generic.xaml ~537) — the tick-drawing problem solved by borrowing a stock slider's TickBar.
  THE OVERLAP TRICK: `SetSlidersMargins()` gives the higher slider a LEFT margin of the lower thumb's width and the lower slider a RIGHT margin of the higher thumb's width (vertical: bottom/top). So the two sliders' travel ranges are offset by one thumb width and the thumbs can never be drawn on top of each other — at equal values they sit side by side, and `AdjustView` subtracts both thumb widths from the track length. This sidesteps the z-order/tie problem entirely at the cost of a track that is two thumbs shorter than the control and values that are not at the same pixel for both thumbs.
- (c) Routing: no nearest-thumb logic. A press on a thumb goes to that slider's Thumb (the only hit-testable part of each Slider). A press on the track falls through to the RepeatButtons underneath: `LowerRange_Click` steps LowerValue DOWN by `Step`, `HigherRange_Click` steps HigherValue UP by `Step`; the middle (selected-range) RepeatButton has no handler, so pressing inside the range does nothing. There is no move-to-point. Overlap/tie: cannot occur (margins above). PART_HigherSlider is declared later so it is above in z-order, irrelevant given the offset.
- (d) STOP. `LowerSlider_ValueChanged` → `UpdateLowerValue` clamps with `Math.Min(newValue, cv.HigherValue)` and writes it back into the Slider (`SetLowerSliderValues`), so a dragged thumb is snapped back at the other value; symmetrical for Higher. A DP-level LowerValue > HigherValue is not coerced on set (open issue https://github.com/xceedsoftware/wpftoolkit/issues/992 "Set LowerValue greater than HigherValue"; `GetCoercedValues` only fixes the view).
- (e) Accessibility: no automation code in RangeSlider.cs (no OnCreateAutomationPeer; grep). Therefore the UIA tree is whatever the two stock Sliders give: each `Slider` creates WPF's own `SliderAutomationPeer` (Slider.cs `OnCreateAutomationPeer`, https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Controls/Slider.cs line ~1269), i.e. TWO Slider elements with the RangeValue pattern, plus the hidden TickSlider (a THIRD Slider peer — accessibility duplication, my inference from the template; not verified with Inspect). Neither PART slider has an AutomationProperties.Name in Generic.xaml, so both are unnamed ("slider"). Both PART sliders are `Focusable="False"` while their inner Thumb is `Focusable="True"`. Runtime Narrator behaviour: UNVERIFIED.
- (f) Keyboard: WPF's Slider registers class command gestures (Slider.cs lines 136-154): Up/Right and Down/Left for small change, PageUp/PageDown for large, Home/End for min/max. Those fire for a key event routed up from the focused inner Thumb, so each thumb should get arrows/Page/Home/End and Tab should walk the two thumbs; the RangeSlider itself is `IsTabStop=False`. Inferred from source, not run.
- (g) Vertical: yes, `Orientation` DP and a separate `VerticalRangeSlider` ControlTemplate (Generic.xaml ~363) with vertical margins in SetSlidersMargins.
- Issues: https://github.com/xceedsoftware/wpftoolkit/issues/999 "RangeSlider : Add Ticks" (open 2017), #1349 deferred-update background (open). No accessibility issue found in the tracker search ("RangeSlider", 7 hits).

### MahApps.Metro RangeSlider

Source: https://github.com/MahApps/MahApps.Metro/blob/develop/src/MahApps.Metro/Controls/RangeSlider.cs, .../Themes/RangeSlider.xaml, .../Automation/Peers/RangeSliderAutomationPeer.cs, tests .../Mahapps.Metro.Tests/Tests/RangeSliderAutomationTests.cs

- (a) Third-party `MahApps.Metro.Controls.RangeSlider : RangeBase` (LowerValue / UpperValue, MinRange, MoveWholeRange, ExtendedMode).
- (b) FIVE TEMPLATE PARTS LAID OUT IN A ROW, ONE CONTROL: a `StackPanel PART_RangeSliderContainer` holding `RepeatButton PART_LeftEdge`, `Thumb PART_LeftThumb`, `Thumb PART_MiddleThumb` (the selected range itself, draggable), `Thumb PART_RightThumb`, `RepeatButton PART_RightEdge` (RangeSlider.xaml ~72-100). The control computes each part's width. No stock Slider; a hidden `TickBar` for ticks.
- (c) Routing by region, not nearest: `VisualElementsContainerPreviewMouseDown` — a press on either thumb is left alone (the thumb takes it); left of the left thumb → lower value (jumps to point if IsMoveToPointEnabled, else repeat-steps on a timer); right of the right thumb → upper value; between the thumbs → the middle thumb (moves the whole range). Middle-button toggles MoveWholeRange. Since the thumbs are consecutive StackPanel children they never overlap in layout, so no tie-break is needed; both thumbs carry `Panel.ZIndex="1"`.
- (d) STOP (with MinRange gap): coercion `CoerceLowerValue`/`CoerceUpperValue` keeps them MinRange apart; commit 20aa8b3d "fix(RangeSlider): stop a dragged thumb at the other value" (2026-09-14). `MoveWholeRange` / middle-thumb drag moves both together (an explicit "push both" mode, not pushing by collision).
- (e) Accessibility: NEW as of 2026-09-15 (commit 7045cc5c "feat(RangeSlider): hand over the two values it holds"). `RangeSliderAutomationPeer`: the control is ControlType **Slider** with ClassName "RangeSlider", NO RangeValue pattern on itself, and ItemStatus "lower - upper" (e.g. "20 - 80"). In `GetChildrenCore` it replaces the peers of PART_LeftThumb/PART_RightThumb with `RangeSliderThumbAutomationPeer : ThumbAutomationPeer, IRangeValueProvider` — ControlType **Thumb** that implements **RangeValue** (Value/Min/Max/SmallChange/LargeChange, SetValue through the DP so coercion still stops it). The middle thumb gets no value. So: ONE Slider element with two adjustable children. The peer's own doc comment states the rationale: "A range slider holds two values, and no automation pattern holds two." Thumb names: no AutomationProperties.Name on the thumbs in RangeSlider.xaml, so no default spoken name beyond the control type (unverified with Narrator). Before 2026-09-15 there was no peer at all.
- (f) Keyboard: `OnKeyDown` acts on whichever of the two thumbs `IsFocused`; Left/Right (horizontal) or Down/Up (vertical) by SmallChange, PageDown/PageUp by LargeChange, Home → Minimum, End → Maximum. Both value thumbs are forced `Focusable=true, IsTabStop=true` in OnApplyTemplate, the control itself `IsTabStop=false` → Tab walks the two thumbs. Also Ctrl/Alt+F/B RoutedCommands for moving the range (RangeSlider.cs lines 47-65).
- (g) Vertical: yes, `Orientation` DP and vertical templates (RangeSlider.xaml ~203 lists Right/Middle/Left thumbs in reverse for vertical).

### Ursa.Avalonia RangeSlider (irihitech; theme in Ursa.Themes.Semi)

Source: https://github.com/irihitech/Ursa.Avalonia/blob/main/src/Ursa/Controls/RangeSlider/RangeSlider.cs, RangeTrack.cs, https://github.com/irihitech/Ursa.Avalonia/blob/main/src/Ursa.Themes.Semi/Controls/RangeSlider.axaml

- (b) ONE CONTROL, TWO THUMB PARTS: `RangeSlider : TemplatedControl` with one template part `PART_Track` of a custom `RangeTrack : Control` (a two-thumb analogue of Avalonia's Track) whose `LowerThumb` / `UpperThumb` properties hold two plain `Thumb`s using the stock `SliderThumbTheme` (axaml ~69-87), plus Lower/Inner/Upper section controls. The slider does its own pointer handling (tunnel handlers on the whole control).
- (c) Routing: `GetThumbByPoint` picks the thumb whose CENTRE is nearer the pointer; on an exact TIE (thumbs overlapped) it breaks by WHICH HALF OF THE TRACK the press is in: pointer right of the track's midpoint → LOWER thumb, left → UPPER (inverted when IsDirectionReversed). Rationale in commit 258a8f0b (2024-04-02) "make an assumption that user want to drag to opposite direction when two thumbs overlap" (https://github.com/irihitech/Ursa.Avalonia/commit/258a8f0b): two thumbs stacked near the max are most likely to be pulled apart leftwards, so the lower one is chosen. Press = move-to-point then drag; the chosen thumb is locked for the gesture (`_currentThumb`).
- (d) PUSH. `MoveToPoint`: dragging the lower thumb past the upper sets UpperValue to the same value first ("if (UpperValue < value) SetCurrentValue(UpperValueProperty, …)"), and vice versa — the dragged thumb pushes the other along. (RangeTrack's coerce also keeps lower ≤ upper.)
- (e) Accessibility: none. No AutomationPeer, no OnCreateAutomationPeer, no AutomationProperties in RangeSlider.cs, RangeTrack.cs or the axaml (grep). Avalonia's default peer for a TemplatedControl would expose it as a generic element; unverified what a screen reader says.
- (f) Keyboard: none. The RangeSlider is `Focusable=true` (one focus stop) but has no key handler (grep "Key" finds nothing). No Tab between thumbs.
- (g) Vertical: yes, `Orientation` (shared with RangeTrack), vertical template section in the axaml (~112-179).
- Tracker: only feature requests (#35, #87), no bugs filed about a11y.

### Avalonia.RangeSlider (DmitryNizhebovsky)

Source: https://github.com/DmitryNizhebovsky/Avalonia.RangeSlider/blob/HEAD/RangeSlider.Avalonia/Controls/RangeSlider.cs, .../Primitives/RangeBase.cs, .../Primitives/RangeTrack.cs

- (b) Same shape as Ursa: one control, custom RangeTrack with two Thumb parts. `IsThumbOverlap` property chooses whether thumbs may draw over each other or sit side by side (template setting scales the reserved thumb space 1x or 2x, `UpdateTemplateSettings`).
- (c) Routing: `GetNearestTrackThumb` — a press inside a thumb's own extent takes that thumb; otherwise nearest thumb edge, classified Inner/Outer. When IsThumbOverlap and the thumbs are at the same position it returns `TrackThumb.Overlapped`, does NOT move on press, and on the first PointerMoved `SelectThumbBasedOnPointerDirection` picks LOWER if the pointer moved toward smaller values and UPPER if toward larger — a true drag-direction tie-break. `MoveWholeRange` option: press between thumbs drags both.
- (d) STOP: RangeBase `ValidateLowerValue` clamps to [Minimum, UpperSelectedValue], `ValidateUpperValue` to [LowerSelectedValue, Maximum].
- (e) Accessibility: none found (grep "automation" in RangeSlider.cs/RangeBase.cs: 0).
- (f) Keyboard: ONE focus stop (`Focusable=true` on the control). `OnKeyDown`: arrows and PageUp/PageDown call `MoveToNextTick`, which moves ONLY `LowerSelectedValue`; Home sets lower to Minimum, End sets UPPER to Maximum. So the upper value is reachable by keyboard only via End. (Read from source; not run.)
- (g) Vertical: yes (`Orientation`).

### RangeSlider.MAUI / PanRangeSlider (AndreiMisiukevich — author of the Xamarin Community Toolkit RangeSlider)
Source: https://github.com/AndreiMisiukevich/RangeSlider.MAUI/blob/HEAD/PanRangeSlider/Common/RangeSlider.cs
- (b) Cross-platform VIEWS, not native sliders: `RangeSlider : TemplatedView` over an AbsoluteLayout with children Track, TrackHighlight, LowerThumb, UpperThumb (each a `Border` subclass `ThumbBorder`), two value Labels (lines ~394-399). ### Xamarin.RangeSlider (halkar, 89 stars, last push 2020-09-07) — native custom-drawn control per platform
Source: https://github.com/halkar/xamarin-range-slider (Forms renderers for Droid/iOS/UWP wrapping a per-platform control)
- (b) iOS: `RangeSliderControl : UIControl` drawing its own handles (NMRangeSlider-style), not two UISliders (Xamarin.RangeSlider.iOS/RangeSliderControl.cs line 13). Android: `RangeSliderControl : ImageView` custom-drawn (RangeSeekBar-style), not two SeekBars (Xamarin.RangeSlider.Droid/RangeSliderControl.cs line 18). UWP: a UserControl with two `Thumb`s on a Canvas (RangeSliderControl.xaml line 50-51) — the Toolkit RangeSelector shape.
- (c) Overlap tie-break, two different rules in one library:
  - Android `EvalPressedThumb`: if the touch hits both thumbs, "choose the one with more room to drag. this avoids 'stalling' the thumbs in a corner" → `touchX / Width > 0.5 ? Lower : Upper` (track-half rule, same as Ursa).
  - iOS `BeginTracking` highlights BOTH handles when both contain the touch; `ContinueTracking` keeps the lower one if the first movement goes lower, the upper if higher, and `BringSubviewToFront` the winner (drag-direction rule, same as DmitryNizhebovsky Avalonia).
- (d) Android: min clamped ≤ max ("0 <= value <= normalized max value <= 1"); iOS: stop (Set*Value clamp) — iOS read only around tracking, clamp inferred from comments.
- (e) No accessibility code in any of the three controls (grep accessib/automation: 0) — a custom UIControl/ImageView with no accessibilityElements or ExploreByTouchHelper is invisible to VoiceOver/TalkBack as two values (inferred; not tested).
- (g) Horizontal only (x-only geometry in tracking code).

## Microsoft guidance and UIA

- WinUI has no two-thumb control. WinUI Gallery request https://github.com/microsoft/microsoft-ui-xaml/issues/9919 ("Range selector C++ WinUI", 2024-08-16, labels "feature proposal", "area-Slider"); karkarl (MS) 2024-08-22: "This is a feature request and not a sample update request. Current slider cannot cover this scenario." Open. No RangeSelector in microsoft/WinUI-Gallery (code search empty).
- Fluent/Windows slider guidance https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/slider says nothing about range selection or two thumbs. Relevant to a trim bar: "If the control is used to seek within media, like in a video app, use a horizontal orientation"; "For vertical slider, put the largest value at the top"; media seek bars always have the lower value on the left even in RTL.
- UIA RangeValue pattern is SINGLE-VALUED: IRangeValueProvider = IsReadOnly, Value, LargeChange, SmallChange, Maximum, Minimum, SetValue(one double); "used to support controls that can be set to a value within a range"; nothing about a start/end pair (https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-implementingrangevalue). No other UIA pattern holds two numbers (confirmed by the maintainers of both toolkits: WCT #3538 marcelwgn "There doesn't seem to be a pattern that does exactly what this control does"; MahApps peer comment "no automation pattern holds two").
- UIA Slider control type (https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportslidercontroltype): typical control view is Slider → Button (2 or 4), **Thumb (1)**, List Item (0+); and "The children (buttons and thumb) of a slider control should never take the focus. The focus should always remain on the slider control itself." Implication for a two-value control: the UIA-conformant shape is TWO Slider elements, each with its own RangeValue and focus — which is exactly what stacking two WinUI `Slider`s produces for free (each gets WinUI's SliderAutomationPeer), and what the Xceed WPF control gets implicitly. MahApps' shape (one Slider with two focusable Thumb children carrying RangeValue) violates the "children never take focus" and "Thumb (1)" conventions, though it works with clients that read child patterns. WCT RangeSelector's shape (two focusable Thumbs with no pattern) is the failing case: Narrator hears "Min thumb, thumb" and no value.

## Summary for kaya

1. Every XAML-family two-thumb control read is ONE control; only Xceed WPF (and nothing in MAUI/Avalonia/WinUI) is built from TWO STOCK Sliders overlaid. Xceed's lessons: re-template each stock slider down to a bare Track+Thumb so only the thumb hit-tests; draw the track (and handle track clicks) in the parent; borrow a THIRD hidden stock slider just to draw ticks; offset the two sliders' travel by one thumb width (margins) so thumbs never overlap — trading exact alignment for no tie-break problem. PanRangeSlider (MAUI) uses the same one-thumb-width offset.
2. Overlap tie-break rules seen: (i) always Min (WCT RangeSelector — can strand both thumbs at Minimum); (ii) which half of the track the press is in: right half → lower thumb, left half → upper (Ursa commit 258a8f0b, halkar Android "choose the one with more room to drag"); (iii) drag direction on first move (DmitryNizhebovsky Avalonia `SelectThumbBasedOnPointerDirection`, halkar iOS ContinueTracking); (iv) never overlap (Xceed, PanRangeSlider, MahApps StackPanel layout). Z-order: last-dragged on top (WCT ZIndex 10/0, halkar iOS BringSubviewToFront).
3. Stop vs push: stop is the norm (WCT, Xceed, MahApps, DmitryNizhebovsky, PanRangeSlider, halkar); Ursa PUSHES; WCT users asked for push (#4029) and it was not done; whole-range move is a separate mode (MahApps middle thumb / MoveWholeRange, DmitryNizhebovsky MoveWholeRange, Syncfusion DragBehavior.Both).
4. Accessibility is the weak point everywhere: WCT no values (open since 2020), Ursa/DmitryNizhebovsky/PanRangeSlider/halkar none, Syncfusion "no support" for screen reader and keyboard; only MahApps (since 2026-09-15) exposes two RangeValue thumbs, and Xceed gets two RangeValue Sliders only as a side effect of stacking stock sliders.
5. Keyboard: Tab between two thumbs (WCT, MahApps, Xceed-by-inference); single focus stop moving only one value (DmitryNizhebovsky: arrows move lower only; End moves upper) or nothing (Ursa). Home/End/PageUp/PageDown: MahApps yes, Xceed yes via stock Slider, WCT no.
6. Vertical: WCT (since PR #756, 2026-02-10), MahApps, Xceed, Ursa, DmitryNizhebovsky, Syncfusion yes; PanRangeSlider, halkar no.
