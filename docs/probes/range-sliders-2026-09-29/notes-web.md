# The web platform: two-thumb range controls

Source files downloaded for reading live in `scratchpad/range/web/`.

## 1. WAI-ARIA APG, Multi-Thumb Slider pattern

Source: https://www.w3.org/WAI/ARIA/apg/patterns/slider-multithumb/

- (a) This is a pattern, not a control.
- (e) There is one `role=slider` per thumb, so the pattern has two adjustable elements. Quote: "Each element serving as a focusable slider thumb has role slider." Each thumb's range depends on the other thumb: "When the range of another slider is dependent on the current value of a slider, the values of aria-valuemin or aria-valuemax of the dependent sliders are updated when the value changes." So the lower thumb's aria-valuemax equals the upper thumb's value, and the upper thumb's aria-valuemin equals the lower thumb's value. `aria-valuetext` carries a value that reads better as words (for example a price or a day). The name comes from `aria-labelledby` pointing at a visible label, or from `aria-label` when there is none.
- (e) The page names an AT limit: "Some users of touch-based assistive technologies may experience difficulty utilizing widgets that implement this slider pattern because the gestures their assistive technology provides for operating sliders may not yet generate the necessary output." In plain terms, on iOS VoiceOver and Android TalkBack a `div role=slider` announces itself as adjustable, but the swipe-up/down or volume-key gesture sends no key event the page can hear. The thumb therefore cannot be adjusted. Evidence: material-web issue #1285 (https://github.com/material-components/material-web/issues/1285), which points at the long-open APG issue w3c/aria-practices#8. Patrick Lauke recommends "a proper `<input type="range">` which is either heavily styled, or which is being 'piggy-backed'". The maintainers closed #1285 by recommending the M3 slider "since it uses native sliders under the hood".
- (f) "Each thumb is in the page tab sequence." The tab order stays fixed whatever the thumb positions are. Each thumb takes the single-slider keys (https://www.w3.org/WAI/ARIA/apg/patterns/slider/): Right/Up increase by one step, Left/Down decrease, Home and End go to min and max, PageUp/PageDown are an optional larger step.
- (d) The pattern implies that the thumbs stop at each other: each thumb's valuemin/valuemax is the other thumb's value, so it cannot cross.
- (g) The pattern supports vertical sliders: `aria-orientation=vertical`.
- (c) The pattern says nothing about pointer routing.

## 2. HTML: is there a native multi-thumb input?

- (a) **No. There is no native two-thumb input today.** HTML once specified `<input type=range multiple value="a,b">`. It was removed in 2016 for lack of implementers: whatwg/html#1520 (https://github.com/whatwg/html/issues/1520), opened 2016-07-07 and closed 2016-07-18. Chromium (tkent): "I don't think it will be used widely, and I guess the implementation cost is high." Gecko (smaug): "certainly not trivial to implement". WebKit (cdumez): "not aware of any plans". Domenic: "lacking any implementer commitment, we should probably remove it".
- whatwg/html#10806 "[Input] Dual Range slider and strict markers" (open, 2024-11-29; https://github.com/whatwg/html/issues/10806). It asks for `type=dualrange` whose "handles cannot cross over each other", and describes the status quo as "lots of libraries layer 2 sliders on top of each other with lots of css hacks". keithamus, 2025-06-11: "this is being incubated in Open UI".
- **The Open UI "Enhanced Range Input" explainer** (https://open-ui.org/components/enhanced-range-input.explainer/; created 2025-03-10, updated 2026-09-08, author utilitybend). It proposes `<rangegroup>` wrapping one real `<input type=range>` per handle: "presents child ranges as handles on a common track, while maintaining the individual inputs for form submission and JavaScript interaction". In other words, **the standards track proposes one native range input per thumb, drawn on one shared track.** That is structurally what kaya is considering.
  - (c) "When a user clicks or taps anywhere on the slider's track, the component identifies the thumb closest to the click location and moves it to that position." Ties are **open**: "The UX of selecting overlapping thumbs (e.g., disambiguating via drag direction) remains an area for further work."
  - (d) Overlap is **allowed** in v1: "Current consensus leans toward allowing overlap for the initial version". `stepbetween` is a minimum gap between adjacent handles, and "Authors can prevent overlap using `stepbetween` or per-thumb `min`/`max` constraints." v1 has no push.
  - (e) Each handle keeps "their native accessibility features"; the group is labelled by `<legend>`, and entering the group should announce its overall min, max and stepbetween.
  - (f) Each thumb is a tab stop with the native range keys.
  - (g) Vertical is an **open question**: "Browsers also disagree today on whether arrow keys and Home/End invert on a vertical slider."
  - Ticks: `list` on `<rangegroup>` points at one shared `<datalist>`.

## 3. Material Web `md-slider` with `range`: two stacked native `<input type=range>`

Sources: the file https://github.com/material-components/material-web/blob/main/slider/internal/slider.ts and its stylesheet https://github.com/material-components/material-web/blob/main/slider/internal/_slider.scss. Read in full (main branch, fetched 2026-09-29).

- (a) Material Web ships a first-party control: `<md-slider range>`, with `value-start`/`value-end`, `aria-label-start`/`-end` and `aria-valuetext-start`/`-end` attributes.
- (b) **Two native `<input type=range>` elements, stacked.** This is the stacked-native design itself. render() emits `renderInput(inputStartProps)` (range mode only) and then `renderInput(inputEndProps)`. Both inputs cover the full width (`position:absolute; width:100%; height:100%`) at `opacity:0`, with `pointer-events:auto`. Their native thumbs are also `opacity:0`. The visible track, tick marks and handles are separate divs that sit under a container with `pointer-events:none` (comment: "note, only the native inputs are interactive"). Both native inputs keep min and max at the whole slider's bounds, so a native value can pass the other thumb; JavaScript then clamps it (see (d)). The tick marks are drawn by the component's own CSS (a `.tickmarks` div driven by `--_tick-count`), not by `<datalist>`.
- (c) **Routing is geometric: each input is clipped at the midpoint between the two values.** It does not use pointer-events on the thumb pseudo-element. From the scss: "Clip the inputs to the space left/right of the center point between the values so the right input gets pointer events." `.ranged input.start { clip-path: inset(0 $_clip-to-end 0 0) }` and `.ranged input.end { clip-path: inset(0 0 0 $_clip-to-start) }`, where the clip point is `start_fraction + (end_fraction - start_fraction)/2`, and the rule is mirrored for `:dir(rtl)`. The effect is that a press on the track goes to the NEAREST thumb, and the native input moves its own thumb to the press point, so clicking the track works. Because each input's clip ends at the midpoint, the two hit areas never overlap, so z-order does not decide routing. z-order (`.onTop {z-index:1}`) only decides which drawn handle paints on top: `updateOnTop()` sets `startOnTop` from the last input to take focus, pointerdown or input. When the handles touch, `isOverlapping()` (a bounding-rect test) adds an outline to the handle on top (`.onTop.isOverlapping .handleNub {border: ...}`).
  - **The tie at coincident values is broken by drag direction.** When both values are equal the clip midpoint sits on the thumb, so the press lands on whichever input owns that side. `isActionFlipped()` then applies. Its comment: "if start/end start coincident and the first drag input would e.g. move start > end, avoid clamping and 'flip' to use the other input as the action target." In code: `canFlip` is true only for `pointerdown`, not for keyboard. If `values.get(target) === values.get(fixed)` and `needsClamping()`, it swaps `action.target` and `action.fixed`. `flipAction()` writes the dragged value into the other input and resets the pressed one. The component also redispatches the `input` event from the flipped target and fires `change` by hand on pointerup ("When action is flipped, change must be fired manually since the real event target did not change"), then calls `target.focus()` on the flipped input ("Ensure any flipped input is focused so the tab order is right").
- (d) **The thumbs stop at each other.** `clampAction()`: "clamp such that start does not move beyond end and visa versa", implemented as `target.valueAsNumber = fixed.valueAsNumber`. There is no push and no swap; the flip above only picks which thumb moves when the two are equal. There is no minimum gap. For keyboard changes clamped at the other thumb, `handleChange` suppresses the `change` event.
- (e) **Two adjustable elements, both native.** Each `<input type=range>` is a real range input, so the platform AT maps it natively (see section 6). Per-input `aria-valuemin`/`aria-valuemax` follow the APG rule: `inputStartProps.ariaMax = this.valueEnd ?? this.max`, `inputEndProps.ariaMin = this.valueStart ?? this.min`, while the native `.min`/`.max` stay at the whole bounds. Code comment: "Slider requires min/max set to the overall min/max for both inputs. This is reported to screen readers, which is why we need aria-valuemin and aria-valuemax." Default names: `aria-label-start`; otherwise `"${ariaLabel} start"`; otherwise value-label-start; otherwise the value as a string. The end thumb is the same with " end". `aria-valuetext` comes from aria-valuetext-start or value-label-start, otherwise the number. The visible value-label bubble is `aria-hidden="true"`.
- (f) The inputs are native, so the keys are native: arrows, Home/End and PageUp/PageDown, whatever the browser gives `<input type=range>`. keydown/keyup only open and close an "action" so that clamping applies. Tab order comes from `.tabIndex=${start ? 1 : 0}`. The start input gets **tabindex=1**, a positive tabindex. Across the whole document that puts it before every tabindex=0 element. Inside the shadow root it only means "start first", because shadow roots scope tab order. That is my reading of HTML's focus-navigation scope rules, not something I tested.
- (g) No vertical support: no orientation property, and the scss has no vertical rule.
- Problems hit (issue tracker, `gh search`):
  - #5016 "[slider] iOS: cannot drag handle to change value" (https://github.com/material-components/material-web/issues/5016). The cause was `transform: scaleX(0)` on the hidden `::-webkit-slider-thumb`, which was done to enlarge the tappable area near the handle. Hiding and resizing the native thumb broke the touch drag on iOS Safari. **This is a hit-target problem specific to hidden native thumbs.**
  - #5108 "Slider sometimes glitches and cannot be dragged" (open; Chrome/Edge on Windows 11, not Firefox) (https://github.com/material-components/material-web/issues/5108): a nearby text selection or `labeled` bubble leaves the slider undraggable.
  - #3326 "mwc-slider-range unable to set valueStart greater than the previous valueEnd" (old mwc range; programmatic writes clamped against the stale other value).
  - #1285 (above): the older mwc-slider, an MDC div with ARIA, did not work with touch AT. The maintainers' answer was the native-input M3 slider. **This is the reason for native inputs under the hood.**

## 4. React Aria and React Spectrum: a drawn thumb div with one visually hidden native `<input type=range>` per thumb

Sources, all read in full on main, 2026-09-29:
- the useSlider hook: https://github.com/adobe/react-spectrum/blob/main/packages/react-aria/src/slider/useSlider.ts
- the useSliderThumb hook: https://github.com/adobe/react-spectrum/blob/main/packages/react-aria/src/slider/useSliderThumb.ts
- the useSliderState hook: https://github.com/adobe/react-spectrum/blob/main/packages/react-stately/src/slider/useSliderState.ts
- React Spectrum v3's RangeSlider: https://github.com/adobe/react-spectrum/blob/main/packages/@adobe/react-spectrum/src/slider/RangeSlider.tsx
- React Spectrum v3's SliderThumb: https://github.com/adobe/react-spectrum/blob/main/packages/@adobe/react-spectrum/src/slider/SliderThumb.tsx
- the S2 RangeSlider: https://github.com/adobe/react-spectrum/blob/main/packages/@react-spectrum/s2/src/RangeSlider.tsx
- react-aria-components' Slider: https://github.com/adobe/react-spectrum/blob/main/packages/react-aria-components/src/Slider.tsx

- (a) React Spectrum ships `RangeSlider` (v3 and S2). React Aria's hooks and components let one `Slider` hold any number of `SliderThumb` children.
- (b) **It is drawn, with a native input hidden inside each thumb.** The drawn thumb is a `div` with `role="presentation"` that carries the pointer handlers (`useMove`). Inside it sits `<VisuallyHidden><input {...inputProps}/></VisuallyHidden>`, in both React Spectrum's SliderThumb.tsx and react-aria-components' Slider.tsx. `inputProps` gives `type:'range'`, `tabIndex:0`, `min: state.getThumbMinValue(index)`, `max: state.getThumbMaxValue(index)`, `step`, `value`, `aria-orientation`, `aria-valuetext`, and `onChange` feeding `state.setThumbValue`. The hook's own comment: "We install mouse handlers for the drag motion on the thumb div, but not the key handler for moving the thumb with the slider. Instead, we focus the range input, and let the browser handle the keyboard interactions; we then listen to input's onChange to update state." The root has `role:'group'`, and the slider's label names the group. The native inputs are therefore **never hit-tested**: pointer input goes to the drawn thumb divs and the track, while keyboard and AT go to the native inputs.
- (c) **Track press: the nearest thumb, ties to the END thumb.** `onDownTrack` in useSlider.ts, whose comment reads "When the user clicks or drags the track, we want the motion to set and drag the closest thumb". The code finds `split = values.findIndex(v => value - v < 0)`. If split is 0 it picks the first thumb; if split is -1 it picks the last; otherwise it compares distances with a strict `<`, and the comment says "Pick the last left/start thumb, unless they are stacked on top of each other, then pick the right/end one". When the thumbs are equal, a press on the start side of the stack picks the start thumb, and a press exactly at or beyond the stack picks the end thumb. The press sets that thumb's value to the press point and goes on to drag it.
  - **A press on the thumb itself is decided by DOM z-order**, and the later thumb paints on top. Two open bugs cover this. #3387 (https://github.com/adobe/react-spectrum/issues/3387): "The rightmost thumb is always on top, so when the thumbs are both set to the same value, it's only possible to drag a thumb to the right", and at [100,100] the thumbs are "no longer draggable". #6408 (https://github.com/adobe/react-spectrum/issues/6408), "When multiple slider thumbs are visually collapsed, the thumb with the highest index captures all pointer interaction". The fix discussed there is a z-index hack; S2's RangeSlider ships it as `zIndex: state.getThumbPercent(0) === 1 ? 1 : undefined` on the lower thumb. Spectrum v3 instead adds an `is-tophandle` class to the focused thumb, following the audit #1231 (https://github.com/adobe/react-spectrum/issues/1231), item 5: "Focused slider thumb should always be on top in the z-index order". **There is no drag-direction tie-break.** In #6408 the maintainers weighed allowing thumbs to cross and sorting the values; they note that Spectrum Web Components defaults to allowing a swap.
- (d) **The thumbs stop at each other.** `getThumbMinValue(i) = i===0 ? minValue : values[i-1]` and `getThumbMaxValue(i) = i===last ? maxValue : values[i+1]`. `updateValue` snaps and clamps into [thisMin, thisMax] (useSliderState.ts). There is no push and no swap.
- (e) **Two adjustable elements.** Each thumb is a native range input whose native `min`/`max` are the neighbouring thumbs' values, so the APG's dynamic valuemin/valuemax comes from the native attributes rather than from aria-*. Each input's `aria-labelledby` is the group label's id followed by the thumb's own label. Default thumb names in React Spectrum's RangeSlider, en-US: **"Minimum"** and **"Maximum"** (the `minimum`/`maximum` keys in https://github.com/adobe/react-spectrum/blob/main/packages/@adobe/react-spectrum/intl/slider/en-US.json; S2 uses `slider.minimum`/`slider.maximum`). A VoiceOver-iOS workaround in useSlider.ts: the label's `htmlFor` is deleted because "VoiceOver on iOS causes this to override the `aria-labelledby` on the thumb", citing WebKit bug 172464. The reason given for the hidden native input (from #1285 in section 3, and the react-aria design) is that touch AT's swipe-to-adjust reaches only a real `<input type=range>`. Open issue #4101 (https://github.com/adobe/react-spectrum/issues/4101): VoiceOver on iOS changes the value by only one step per swipe, and a tap-and-hold drag is not announced. A maintainer: "The behavior can be reproduced using any `input[type="range"]`". #1400: TalkBack does not announce the output text.
- (f) Each hidden input has `tabIndex:0`, so there are two tab stops in DOM order. Arrows come from the native input. PageUp/PageDown step by `pageSize` (default (max-min)/10). Home and End go to **the thumb's own min/max, meaning the neighbour's value** (`state.getThumbMinValue(index)` in useSliderThumb.ts). Shift+arrow gives a page step through `useMove`'s keyboard path.
- (g) Vertical is supported (`orientation` flips the axis in both hooks, and `aria-orientation` goes on the input).

## 5. Radix UI Slider: a drawn `span role=slider` per thumb, with no native input for AT

Source: https://github.com/radix-ui/primitives/blob/main/packages/react/slider/src/slider.tsx (read in full, main, 2026-09-29).

- (a) Radix has one `Slider.Root` that takes `value: number[]`, and two `Slider.Thumb` children make a range.
- (b) **One drawn control with templated thumb parts.** Each thumb is `<Primitive.span role="slider" tabIndex=0 aria-valuemin aria-valuenow aria-valuemax aria-orientation>`. The `SliderBubbleInput` per thumb is `style={{display:'none'}}` and exists only for form submission: "We purposefully do not use `type="hidden"` here otherwise forms that wrap it will not be able to access its value via the FormData API". AT never sees it. The root takes pointer capture itself (`target.setPointerCapture`).
- (c) Pointerdown on a thumb only focuses it; the thumb's onFocus sets `valueIndexToChangeRef = index`, and later moves drag that index. Pointerdown on the track calls `handleSlideStart`, which picks `getClosestValueIndex`, using `distances.indexOf(closestDistance)`. **A tie goes to the LOWEST index.** A press on a stack of thumbs hits the later DOM thumb (paint order), but with the default crossing behaviour the direction does not matter.
- (d) **By default the thumbs cross and the values are re-sorted**: `getNextSortedValues` sorts, and `valueIndexToChangeRef` follows the moved value via `nextValues.indexOf(constrainedValue)`, so focus moves to the other thumb element. `preserveThumbOrder` (new; the doc comment is "thumbs keep their relative order and won't cross over one another while dragging") makes each thumb stop at its neighbours. `minStepsBetweenThumbs` gives a minimum gap: a move that breaks it is refused, and the value does not change.
- (e) There are two adjustable elements, but they are ARIA only, a `span role=slider`. Both carry **static `aria-valuemin`/`aria-valuemax` = the whole min/max**, not the APG's dynamic values. Default names from `getLabel()`: "Minimum" and "Maximum" when there are two thumbs, "Value N of M" for more than two, none for one. Because they are not native inputs, the touch-AT problem described in section 1 applies: a VoiceOver-iOS swipe or TalkBack volume key cannot adjust them. I did not test this on a device; it follows from the APG caveat and from MUI #23506 and material-web #1285.
- (f) Two tab stops. Arrows step, and Shift+arrow or PageUp/PageDown step by 10×step. **Home always moves thumb 0 to min, and End always moves the LAST thumb to max, whichever thumb has focus** (`updateValues(min, 0, …)` and `updateValues(max, values.length - 1, …)` in the root's onHomeKeyDown and onEndKeyDown).
- (g) Vertical is supported (`SliderVertical`, `orientation`), and so is `inverted`.

## 6. MUI Slider (range mode): a drawn thumb span with one visually hidden native `<input type=range>` per thumb

Sources, both read in full on master, 2026-09-29: the hook https://github.com/mui/material-ui/blob/master/packages/mui-material/src/Slider/useSlider.ts and the component https://github.com/mui/material-ui/blob/master/packages/mui-material/src/Slider/Slider.js

- (a) MUI has `<Slider value={[a,b]}>`; range mode is on whenever `value` is an array.
- (b) **Drawn thumbs, each with a visually hidden native range input.** `getHiddenInputProps` returns `type:'range'`, `min`/`max` = the whole bounds, `aria-valuemin/max` = the whole bounds scaled, `aria-orientation`, and `style: {...visuallyHidden, width:'100%', height:'100%', writingMode}`, with the comment "So that VoiceOver's focus indicator matches the thumb's dimensions". The input sits inside the thumb span. Pointer input goes to the root (`getFingerNewValue`); keyboard and AT go to the inputs. MUI adopted this after #23506, "[slider] Component doesn't work on touch+AT devices" (https://github.com/mui/material-ui/issues/23506). There a maintainer suggested "Use the native slider, but 'hidden'", and a contributor asked "could you use multiple hidden `<input type="range">`, one for each Thumb?", which is what shipped.
- (c) **Nearest thumb, and a tie goes to the LAST thumb used, else to the higher index.** `findClosest(values, newValue, lastUsedThumbIndexRef.current)` keeps the later index on equal distance (`distance <= acc.distance`), then `if (preferredIndex >= 0 && values[preferredIndex] === values[closestIndex]) return preferredIndex`. So when the thumbs are stacked, the thumb used last wins. z-order: `getThumbStyle` gives zIndex 2 to the active thumb and 1 to the last-used one, and sets `pointerEvents:'none'` on the non-active thumb during a drag.
- (d) **Swap by default**, and `disableSwap` makes the thumbs stop. Without disableSwap, `activeIndex = newValue.indexOf(previousValue)` after a sort, and `focusThumb` moves DOM focus to the other input. With it, the value is clamped to its neighbours (`clamp(newValue, values[i-1], values[i+1])`). There is no push. Tab order stays fixed: #20494 (https://github.com/mui/material-ui/issues/20494) found tabbing after a swap left the slider, and a maintainer answered "This is expected, the focus is kept on the active thumb."
- (e) **Two native inputs, so two adjustable elements.** Their aria-valuemin/max are the WHOLE bounds, not the neighbour. There is **no default per-thumb name**: both thumbs get the same `aria-label` unless the app supplies `getAriaLabel(index)` and `getAriaValueText(value, index)` (Slider.js).
- (f) Two tab stops. Arrows step and Shift+arrow uses `shiftStep` (default 10); PageUp/PageDown use shiftStep; Home and End go to the whole min and max. With disableSwap the result is then clamped to the neighbour; without it, the thumbs swap (createHandleHiddenInputKeyDown and changeValue).
- (g) Vertical is supported: the `orientation` prop, and the hidden input gets `writing-mode: vertical-lr` or `vertical-rl`.
- Open issue **#45577 "Expose `getThumbIndex` prop"** (https://github.com/mui/material-ui/issues/45577) is a **video-trim use case**: "the left/right thumbs are 'trim' controls for video playback, while the middle thumb handles scrubbing", and nearest-thumb routing gets it wrong. The maintainers were willing to add the prop.

## 7. noUiSlider: drawn `div role=slider` handles

Source: https://github.com/leongersen/noUiSlider/blob/master/src/nouislider.ts (read the relevant functions, master, 2026-09-29).

- (a) noUiSlider takes any number of handles (`start: [a, b]`).
- (b) **Drawn.** `addOrigin()` creates an origin div per handle, with a handle div inside it carrying `role="slider"`, `tabindex=0` (when `keyboardSupport` is on) and `aria-orientation`. It has no native input.
- (c) A tap on the track uses `getClosestHandle()`. `isCloser` is a strict `<`, and `isCloserAfter` is `<=` combined with "the click lies past this handle". **On a tie, the later handle wins if the click is after it; otherwise the earlier one keeps the tap.** Stacking is handled by `setZindex()`, whose comment reads "Handles before the slider middle are stacked later = higher, Handles after the middle later is lower". So when both handles sit at the maximum, the LOWER handle is on top and can be dragged back down. **This avoids the stuck-at-the-edge bug that React Aria still has open (#3387, #6408), using a static rule rather than drag direction.**
- (d) **The handles stop by default.** `checkHandlePosition`: "For sliders with multiple handles, limit movement to the other handle. Apply the margin option by adding it to the handle positions." `margin` is a minimum gap and `limit` is a maximum gap. The `unconstrained` behaviour lets the handles cross, and it cannot be combined with margin or limit. The `drag` behaviour drags the connect bar, moving both handles together, and `fixed` keeps the width locked. No push.
- (e) Two ARIA sliders. **Dynamic aria-valuemin/valuemax per the APG**: the `aria()` handler, with the comment "Update Aria Values for all handles, as a change in one changes min and max values for the next", computes min and max through `checkHandlePosition(..., 0|100, true, true, true)`, so they are the neighbour's value plus or minus the margin. `aria-valuetext` comes from `ariaFormat`. There is no default name; the app sets one through the `handleAttributes` option. The touch-AT limitation in section 1 applies (unverified on a device).
- (f) Two tab stops. Arrows, and PageUp/PageDown (×`keyboardPageMultiplier`, default 5). Home and End jump to the whole min and max and are then clamped by `setHandle`/`checkHandlePosition`, so each thumb stops at its neighbour. Vertical sliders reverse the Up/Down keys so they follow the visual direction.
- (g) Vertical is supported (`orientation: 'vertical'`).

## 8. Shoelace 2 `sl-range` and Web Awesome 3 `wa-slider range`

Sources:
- Shoelace's range component: https://github.com/shoelace-style/shoelace/blob/next/src/components/range/range.component.ts (grepped)
- Web Awesome's slider: https://github.com/shoelace-style/webawesome/blob/next/packages/webawesome/src/components/slider/slider.ts (relevant parts read, 2026-09-29)

- Shoelace 2's `sl-range` is **single-thumb**, one native `<input type="range">` "under the hood" (its own comment). It has no range mode. Its authors note that with a native input "we don't have access to the thumb's true coordinates", so the tooltip position is "guessed". That is a cost of the native-input approach.
- (a) Web Awesome 3 has a first-party range: `<wa-slider range min-value max-value>`.
- (b) **Drawn, and it dropped the native input.** The two thumbs are `<span role="slider" tabindex=0>` inside one component (`thumb-min` and `thumb-max` parts). There is no hidden native input.
- (c) A thumb press drags that thumb. A track press ("Enable track dragging for finding the closest thumb") picks the nearest thumb with `minDistance <= maxDistance ? 'min' : 'max'`, so **a tie goes to min**, with extra rules when the distances are exactly equal: past the max picks max, below the min picks min, and between the thumbs **the direction of pointer movement decides** ("prioritize the thumb that's in the direction of movement", `movingForward ? 'max' : 'min'`). If a thumb is already active from focus, that thumb is kept: "If the thumbs are in nearly the same position, we prioritize the one that's already active or the one that received focus most recently".
- (d) **The thumbs PUSH.** In `setThumbValueFromCoordinates`: "If min thumb is being dragged and would exceed max thumb — Move both thumbs, keeping their distance at 0", which sets `maxValue = minValue = value`. The keyboard path does the same ("If min thumb exceeds max thumb, move both"). This is the only web library I read that pushes.
- (e) Two ARIA sliders with **static** aria-valuemin/max (the whole bounds). Default names are hard-coded English, not run through `localize`: `"Minimum value"` / `"Maximum value"`, or `"${label} (minimum value)"` / `"(maximum value)"`. `aria-valuetext` comes from `valueFormatter` or `localize.number`. Touch AT: the same caveat as section 1 (unverified).
- (f) Two tab stops. Arrows, and PageUp/PageDown. Home on the min thumb goes to the whole min; Home on the max thumb goes to `minValue`, which collapses the range onto the min thumb. End mirrors this.
- (g) Vertical is supported (`orientation`).

## 9. Spectrum Web Components `sp-slider` with several `sp-slider-handle`s: a native input inside each drawn handle

Source: https://github.com/adobe/spectrum-web-components/blob/main/1st-gen/packages/slider/src/HandleController.ts (relevant parts read, 2026-09-29).

- (a) `<sp-slider>` takes any number of `<sp-slider-handle>` children.
- (b) Each handle renders as `<div class="handle" role="presentation"><input type="range" class="input" min=clamp.min max=clamp.max step .../></div>`, so a native range input sits in each drawn handle. That is the React Aria shape. I did not read the CSS that hides the input, so how it is hidden is unverified. Pointer events are captured on the track (`this.host.track.setPointerCapture`), and the value comes from `calculateHandlePosition`.
- (c) **A track press moves the ACTIVE handle, meaning the one used last, not the nearest.** `extractDataFromEvent`: when the target is not a handle, `model = this.model.find(item => item.name === this.activeHandle)`. z-order: `zIndex = handleOrder.indexOf(name) + 2`, so the handle activated last paints on top. (That `activateHandle` reorders handleOrder is my inference from the name; I did not read its body, so it is unverified.)
- (d) **Handles CROSS by default.** They are independent unless a handle declares `min="previous"` / `max="next"`, in which case `clamp.min = Math.max(previous.value, range.min)` and similarly for max, so the handle stops. The native input's min/max are that clamp. React Aria #6408 cites this default ("defaults to allowing swapping while allowing customization to prevent it").
- (e) There are two native inputs. `aria-labelledby="label input-N"`, an optional `aria-label` per handle, `aria-valuetext` from the number format. Every input's `aria-describedby` points at the fixed English string "Press escape or double click to reset the slider to its default value."
- (g) `calculateHandlePosition` reads only `clientX` and `rect.width`, so there is no vertical support in the handle controller.

## 10. The "two stacked `<input type=range>` with CSS" tutorial technique, and its documented problems

Sources:
- CSS-Tricks, Ana Tudor, "Multi-Thumb Sliders: Particular Two-Thumb Case": https://css-tricks.com/multi-thumb-sliders-particular-two-thumb-case/
- the same author's general case: https://css-tricks.com/multi-thumb-sliders-general-case/
- Mike Jolley, 2019: https://mikejolley.com/2019/08/02/building-a-cross-browser-compatible-multi-handle-range-slider/
- Sandra Lewis, DEV: https://dev.to/sandra_lewis/building-a-multi-range-slider-in-react-from-scratch-4dl1
- Paul J. Adam's demo: https://pauljadam.com/demos/multithumb-slider.html

- (b) Two full-width native inputs are placed in the same grid cell. Their tracks are made transparent, and one shared track is drawn on the wrapper. The key CSS is "`pointer-events: none` on the actual `<input>` elements and then revert to `auto` on their thumbs" (CSS-Tricks). The wrapper is `role=group` with `aria-labelledby`, and each input has a screen-reader-only label.
- Problems documented:
  1. **The track cannot be clicked.** With `pointer-events:none` on both inputs, only the thumbs take presses, so tapping the track moves nothing. Material Web avoids this by clipping at the midpoint instead (section 3). React Aria and MUI avoid it by routing presses in code.
  2. **The thumbs stick when they meet at an edge.** The later input's thumb is always on top, so at [max,max] only the upper thumb can be grabbed, and it cannot move right. The tutorial fix is a JS z-index swap: `thumb--zindex-5` on the left thumb when `minVal > max - 100` (Lewis). Jolley needed the z-index swap anyway, for all input, on IE/Edge: "if you disable pointer-events on the range slider, it is impossible to re-enable them for the slider handle", so they computed "which is closest to the mouse and move it 'up'".
  3. **Crossing.** The inputs are independent, so the CSS-Tricks version lets the thumbs pass each other ("--a > --b" and "--b > --a" fill cases). Stopping needs JS: `Math.min(+value, maxVal - 1)` (Lewis, with a hard-coded minimum gap of 1). The native `min`/`max` attributes are usually left at the whole bounds, so AT hears the whole range rather than the APG's dynamic one, unless aria-valuemin/max is overridden as Material Web does.
  4. **Engine differences in thumb geometry.** "In Chrome, the thumb's `border-box` moves within the limits of the track's `content-box`, while in Firefox, it moves within the limits of the slider's `content-box`" (CSS-Tricks). Jolley: "Firefox worked with translate, whereas Chrome supported negative margins." There are separate pseudo-elements: `::-webkit-slider-thumb`, `::-moz-range-thumb`, and the old `::-ms-*`. Because the native thumb's real coordinates cannot be read, a drawn thumb or tooltip has to be placed by guessing (Shoelace's comment in section 8). Material Web resizing the hidden native thumb broke iOS dragging (#5016, section 3).
  5. **Screen readers hear two unrelated sliders** unless the group is labelled and each input gets its own name ("minimum"/"maximum"). None of the tutorials fix the valuemin/valuemax each thumb reports.
  6. **Ticks.** `<datalist>` ticks are per-input and render differently or not at all across engines. Stacked implementations draw their own ticks: Material Web's `.tickmarks`, and Open UI proposes one `list` on the group. (Per-engine datalist rendering is from my knowledge, not re-read for this report, so it is unverified.)
- Paul J. Adam (an accessibility specialist) argues for the native inputs, on the grounds that "a native HTML input type=range slider can be adjusted correctly with mobile screen readers", "screen reader user can use their Volume Up/Down keys to adjust the values of native sliders but not with custom sliders", and they give "free support for Home/End, and Page Up/Page Down keys".

## 11. How an engine exposes a native range input to each desktop and mobile AT, and what an AT "increment" does

- HTML-AAM, `input type=range`: role `slider`, and every platform column says "Use WAI-ARIA mapping" (https://w3c.github.io/html-aam/, entry `el-input-range`). Core-AAM's slider row (https://w3c.github.io/core-aam/) gives:
  - MSAA/IA2: `ROLE_SYSTEM_SLIDER` with the `IAccessibleValue` interface.
  - UIA: control type **Slider** with the **RangeValue** pattern. aria-valuemin, valuemax and valuenow map to `RangeValue.Minimum`, `Maximum` and `Value`.
  - ATK/AT-SPI: `ROLE_SLIDER` with the **Value** interface.
  - AX API: `AXSlider`, with `AXMinValue`, `AXMaxValue` and `AXValue`; aria-valuetext maps to `AXValueDescription`.
  So **one native (or hidden native) input per thumb maps each thumb to exactly one platform slider on every desktop API**: UIA RangeValue, AT-SPI Value and NSAccessibility AXSlider. It is the same shape as kaya's proposal of two stock platform sliders, which Narrator, Orca and VoiceOver already know how to adjust.
- **Android (Chromium):** `WebContentsAccessibilityAndroid::AdjustSlider` (https://github.com/chromium/chromium/blob/main/content/browser/accessibility/web_contents_accessibility_android.cc) calls `manager()->Increment/Decrement` for any node where `IsSlider()`. The TalkBack volume-key and scroll-action path feeds a `RangeInfo` node (the Java side is WebContentsAccessibilityImpl).
- **What Blink does with that increment** (https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/accessibility/ax_node_object.cc, `AlterSliderOrSpinButtonValue`, read on main):
  - For a **native** range input it sets the value directly by the step. The `SynthesizedKeyboardEventsForAccessibilityActions` flag, when enabled, sends a synthetic arrow keydown instead. That flag is `status: "experimental"` in runtime_enabled_features.json5, so it is off in stable.
  - For an **ARIA** `role=slider`, `StepValueForRange` returns a step of 0 with `true`, and the code falls through to **synthesizing ArrowUp/ArrowRight keydown and keyup** on the element: "For an ARIA slider, the corresponding keydown/up JS events will be fired. It is expected that the handlers for those events manage the update of the slider value."
  - `StepValueForRange` for native inputs does not expose the step when there are 40 or more stops, "so that Talkback will move by 5% increments".
- **WebKit** (https://github.com/WebKit/WebKit/blob/main/Source/WebCore/accessibility/AccessibilityNodeObject.cpp, `alterRangeValue` and `postKeyboardKeysForValueChange`, read on main): it moves by `step` if a step attribute exists, otherwise by 5%. `setNodeValue` tries `setValue`, which succeeds on a native input, and otherwise **posts synthetic arrow keydown/keyup** ("Fire a keyboard event if we were not able to set this value natively"). It sends ArrowUp/Down for vertical sliders and flips left/right for RTL.
- **Consequence.** In current engine source, a VoiceOver-iOS swipe or TalkBack volume key on an ARIA `role=slider` reaches the page as a synthetic arrow key. So the old "div sliders cannot be adjusted by touch AT" complaint (material-web #1285 and MUI #23506, both from 2020) is at least partly addressed in the engines. I did not check which release shipped the fallback, or test on a device; both are unverified. The native-input approach needs no fallback, and on WebKit it also gets the 5% default step.
- Known native-input AT limits that remain: React Spectrum #4101 (https://github.com/adobe/react-spectrum/issues/4101) reports that VoiceOver on iOS moves a native range input by only one step per swipe, and that a tap-and-hold drag is not announced. The iOS VoiceOver `label[for]` bug is WebKit bug 172464 (section 4).

## Synthesis for kaya's choice (stack two platform sliders over a kaya-drawn track)

| Library | How it is built | Track-press routing | Tie at equal values | Stop, cross or push | AT elements | Default thumb names |
|---|---|---|---|---|---|---|
| Material Web md-slider | **Two stacked native inputs** | Nearest, by clip-path at the midpoint | Drag direction (flip) | Stop | 2 native; aria-valuemin/max = neighbour | "{label} start" / "{label} end", else the value |
| React Aria / Spectrum | Drawn thumb + hidden native input each | Nearest (code) | End thumb; a press on the thumb itself: DOM-last on top (bug #3387/#6408) | Stop | 2 native; min/max = neighbour | "Minimum" / "Maximum" |
| MUI | Drawn thumb + hidden native input each | Nearest (code) | Last-used thumb, else higher index | Swap (disableSwap → stop) | 2 native; whole bounds | none (app's getAriaLabel) |
| Radix | Drawn span role=slider | Nearest | Lower index | Cross, values re-sorted (preserveThumbOrder → stop) | 2 ARIA; whole bounds | "Minimum" / "Maximum" |
| noUiSlider | Drawn div role=slider | Nearest | The later one if the press is past it | Stop (+margin/limit; unconstrained → cross) | 2 ARIA; dynamic per APG | none |
| Web Awesome | Drawn span role=slider | Nearest; active thumb kept | Min, or movement direction when between | **Push** | 2 ARIA; whole bounds | "Minimum value" / "Maximum value" |
| Spectrum WC | Drawn handle + native input each | Last-active handle | n/a | Cross (min=previous → stop) | 2 native | app |
| Open UI `<rangegroup>` (proposal) | One native input per thumb on a shared track | Nearest | **Open** ("disambiguating via drag direction") | Overlap allowed; `stepbetween` | 2 native | via `<label>` |

- Every web implementation exposes **two adjustable elements**, never one element with two values. That matches kaya's plan, and the APG and the Open UI proposal both require it.
- **Stacking literal native sliders is done in production by Material Web.** What made it work: (1) full-width inputs **clipped at the midpoint between the thumbs**, so hit-testing is decided by geometry, not z-order, and a track press reaches the nearer thumb; (2) a separate drawn track, handles and ticks, with the native parts invisible; (3) JS clamping, because the native min/max stay at the whole bounds, with aria-valuemin/max overridden to the neighbour; (4) a **drag-direction flip** when the thumbs are equal at pointerdown, with focus moved to the flipped input; (5) an outline on the handle on top when the handles overlap. The problems it hit were the hidden native thumb's size and transform breaking iOS touch drag (#5016), and an intermittent undraggable state on Chromium/Windows (#5108, open).
- The **z-order tie trap** (the thumbs stuck at [max,max] because the later thumb is on top and cannot move further) appears in React Aria (#3387 and #6408, both open) and in the stacked-input tutorials. Fixes in the wild: a clip at the midpoint plus a direction flip (Material Web); a static rule where handles past the middle stack lower-index-on-top (noUiSlider `setZindex`); a z-index bump for the lower thumb when the upper is at max (React Spectrum S2); last-used on top (MUI and Spectrum WC); focused on top (React Spectrum v3).
- For a trim control, the **nearest-thumb rule can be wrong**. MUI #45577 asks for a `getThumbIndex` hook for exactly the video-trim-plus-playhead case.
