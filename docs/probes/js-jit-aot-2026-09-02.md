# "No interpreted JS" on the phones — what that can actually mean in 2026

Research report, written 2026-09-02. RESEARCH ONLY — no repo edits.
Every claim carries a URL; every status claim carries the date it was read.
Companion to `js-mobile-research.md` (same directory), whose engine survey,
N-API surface and threading findings this report assumes rather than repeats.

**The ruling being interpreted:** *"no interpreted JS — a normalization step
(babel/esbuild) or bundling a runtime is fine, but no interpretation."*

## §0 The measurements, first — because they decide the reading

Everything below was run on **2026-09-02**, host **Apple M5 Pro / macOS
26.6.2**, by a probe that transliterates `bindings/js/kaya/wire.ts`'s real
encoder: per-scalar `Uint8Array` + `DataView`, `cat()` concatenation,
`pad()` to 8, `record()` framing, a pure-JS UTF-8 encoder so every engine
runs byte-identical work. Probe kept at
`jit-probes/wirebench.js` and `jit-probes/wirebench2.js` beside this report.

**The prior report could not measure this** (§1.8: "setting `JSC_useJIT=false`
was accepted … but changed a 50M-iteration loop only from 349 ms to 373 ms …
I could not tell those two causes apart"). The cause was the *route*: the
environment variable did not take. The **command-line flag does**, and
`--dumpOptions=1` prints `useJIT=false (default: true)` to prove it. The
canary confirms it independently: pure integer arithmetic goes **34 ms →
428 ms, 12.6×**, which no memory-bound loop would do.

### Throughput, synthetic (best of N)

| engine / mode | pack 100k records | canary 50M int ops | 20M DataView writes |
|---|---|---|---|
| **JSC, full JIT** (LLInt+baseline+DFG+FTL) | **47 ms** | 34 ms | 5 ms |
| JSC, FTL off (baseline+DFG) | 51 ms | 54 ms | 12 ms |
| JSC, **baseline JIT only** (DFG+FTL off) | 86 ms | 278 ms | 112 ms |
| **JSC, `--useJIT=false` — LLInt only, the iOS shape** | **251 ms** | **428 ms** | 295 ms |
| node 24.19.0 (V8, full JIT) | 73 ms | 35 ms | 9 ms |
| **QuickJS-ng 0.13.0** (interpreter, nixpkgs build) | **390 ms** | 894 ms | 327 ms |

### Throughput, at kaya's real batch sizes

`portfolio15003` is the portfolio refresh — **15,003 inserts**, the largest
batch kaya ships (commit 2f36c09). `handler20` is an ordinary click handler
emitting 20 records. Tiers warmed first, as a real app warms them.

| engine / mode | 15,003-record batch | µs/record | 20-record handler |
|---|---|---|---|
| **JSC, full JIT** | **8.57 ms** | 0.572 | **9.70 µs** |
| node 24.19.0 | 11.45 ms | 0.763 | 14.10 µs |
| **JSC, JIT-less (iOS)** | **39.63 ms** | 2.641 | **52.90 µs** |
| **QuickJS-ng 0.13.0** | **58.80 ms** | 3.919 | **78.75 µs** |

**The three numbers that decide this report:**

1. **JIT-less JSC costs 4.6× a JIT'd JSC on kaya's heaviest real batch**
   (39.6 ms vs 8.57 ms) — a real, visible regression on the one batch that
   is already known to be the slow path.
2. **An ordinary handler costs 53 µs interpreted** — **0.3 % of a 60 Hz
   frame**, and 43 µs more than the JIT'd figure. Below every threshold
   kaya has.
3. **QuickJS-ng is only 1.48× slower than JIT-less JSC** on the same batch
   (58.8 ms vs 39.6 ms), not the order of magnitude the folk ranking
   assumes. The gap between *any interpreter* and *any JIT* is far larger
   than the gap between two interpreters.

### The baseline kaya already ships: its own Python binding, on an interpreter

The same 15,003 records were packed by a faithful transliteration of
`bindings/python/kaya/wire.py` (`jit-probes/wirebench.py`), on the dev shell's
**CPython 3.14.7** — a bytecode interpreter with no JIT, which kaya has already
ratified shipping in both mobile bundles (`docs/python-mobile-plan.md`,
2026-08-28):

| binding / engine | 15,003 records | µs/record | 20-record handler |
|---|---|---|---|
| **kaya's Python binding, CPython 3.14.7** | **6.03 ms** | **0.402** | **8.11 µs** |
| kaya's JS binding shape, node 24 (JIT) | 11.30 ms | 0.753 | 13.80 µs |
| kaya's JS binding shape, JSC JIT-less | 39.63 ms | 2.641 | 52.90 µs |
| JS cursor encoder, JSC JIT-less | 13.88 ms | 0.925 | 17.40 µs |

**kaya's JavaScript binding is 1.9× slower than its Python binding on a JIT'd
engine.** Not because JavaScript is slower than Python — because `wire.py`
pushes each scalar through one `struct.pack` C call while `wire.ts` builds a
`Uint8Array` and a `DataView` per scalar in JS. Checked for fairness: swapping
the probe's pure-JS UTF-8 encoder for node's native `TextEncoder` changes
nothing (11.30 ms either way), so string encoding is not the difference; the
allocation shape is. (Neither the `jsc` CLI nor `qjs` exposes `TextEncoder` at
all — a bare engine would get it as a native call anyway, which is what the
prior report's D6 already recommends.)

**So the interpreter question has an existing answer in this tree.** A
JIT-less JavaScriptCore with a cursor encoder (13.88 ms) is **2.3× the Python
binding kaya already ships on both phones**, and **1.23× kaya's own JS binding
on the desktop today**.

### Warm-up and start-up, measured — so reading (iii) can be dismissed with a number

`jit-probes/coldbench.js` times the **first** 15,003-record batch in a fresh
process and then the next twelve:

| engine / mode | first batch | batches 2–13 (ms) |
|---|---|---|
| JSC, full JIT | **10 ms** | 10 9 8 9 10 10 9 8 9 9 25 6 |
| JSC, JIT-less | 38 ms | 39 35 38 37 38 38 39 38 39 57 37 36 |
| QuickJS-ng | 59 ms | 58 57 58 57 57 58 57 58 57 57 58 57 |

**The JIT reaches steady state inside the first batch.** There is no warm-up
curve to trade against: the JIT'd engine's *cold* number (10 ms) already beats
the interpreter's *warm* number (37 ms) by 3.7×. Process start-up for an empty
script, best of seven: `jsc` **4.9 ms**, `jsc --useJIT=false` **4.4 ms**,
`qjs` **2.4 ms** — all noise beside a launch.

### The measurement that reframes the question: the encoder, not the engine

kaya's `wire.ts` allocates **two objects per scalar** — a `Uint8Array` and a
`DataView` — then concatenates the pieces (`cat()`). That is the shape the
table above measures. A second probe (`jit-probes/cursorbench.js`) encodes the
byte-identical output (600,128 bytes, checked) into **one growable buffer at a
cursor**, with one `DataView` for the process:

| engine / mode | 15,003 records, current shape | 15,003 records, cursor shape | gain |
|---|---|---|---|
| JSC, full JIT | 8.57 ms | **0.55 ms** | **15.6×** |
| node 24.19.0 | 11.45 ms | **0.72 ms** | **15.9×** |
| **JSC, JIT-less (iOS)** | 39.63 ms | **13.88 ms** | **2.9×** |
| QuickJS-ng 0.13.0 | 58.80 ms | **18.40 ms** | **3.2×** |

And the 20-record handler: JIT-less JSC **52.9 µs → 17.4 µs**; QuickJS-ng
78.8 µs → 23.8 µs; JSC with JIT 9.7 µs → 0.6 µs.

**Read the two columns against each other.** Holding the encoder fixed, the
JIT is worth **4.6×**. Holding the engine fixed, the encoder is worth
**15.6×**. On kaya's own workload **the allocation shape costs more than the
JIT does** — and the allocation shape is entirely inside kaya's control, while
the JIT is Apple's to grant.

The number that follows from that: **JIT-less JavaScriptCore with a cursor
encoder runs kaya's heaviest batch in 13.88 ms against the 11.45 ms that node
manages on the desktop today** — 1.21×, on the platform with no JIT at all.
The probe is conservative: it allocates a closure per record for readability,
which a real encoder would not.

Caveat stated plainly: an M5 Pro is not a phone. Phone-class cores run this
work roughly 2–3× slower, so read the interpreted 15k batch as **~80–120 ms
on device** and the interpreted handler as **~110–160 µs**. Both scale
linearly; neither was measured on a device here.

## §1 iOS — can a third-party app execute JIT-compiled JavaScript at all?

**Short answer: no, and the code that says no is readable.** There is exactly
one gate, it is an entitlement check inside JavaScriptCore itself, and no
non-browser app can pass it.

### 1.1 The gate, quoted from WebKit's own source

`Source/JavaScriptCore/jit/ExecutableAllocator.cpp`
(<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/jit/ExecutableAllocator.cpp>,
read 2026-09-02):

```cpp
static bool NODELETE isJITEnabled()
{
    bool jitEnabled = !g_jscConfig.jitDisabled;
#if HAVE(IOS_JIT_RESTRICTIONS)
    jitEnabled = jitEnabled && (processHasEntitlement("dynamic-codesigning"_s) ||
                                processHasEntitlement("com.apple.developer.cs.allow-jit"_s));
#elif HAVE(MAC_JIT_RESTRICTIONS) && USE(APPLE_INTERNAL_SDK)
    jitEnabled = jitEnabled && processHasEntitlement("com.apple.security.cs.allow-jit"_s);
#endif
    return jitEnabled;
}
```

and when that returns false:

```cpp
void ExecutableAllocator::disableJIT()
{
    ...
    g_jscConfig.jitDisabled = true;
    Options::useJIT() = false;
```

So the fallback is not a special mode — it is **`Options::useJIT() = false`,
the same switch this report measured on the command line in §0.** That is why
the §0 JIT-less column is a faithful model of the device and not an analogy.

**`dynamic-codesigning`** is the private entitlement Apple grants only to
system processes; Saagar Jha's writeup is the standard reference: "True
just-in-time compilers require the ability to generate executable pages with
an invalid code signature, a practice that is usually prohibited on iOS for
third-party apps because it sidesteps code validation guarantees that Apple
would like to enforce", granted to "system processes that require the
high-performance tiers of JavaScriptCore"
(<https://saagarjha.com/blog/2020/02/23/jailed-just-in-time-compilation-on-ios/>,
2020-02-23; still the live mechanism per the source above, read 2026-09-02).

**`com.apple.developer.cs.allow-jit`** is the other accepted key. It has **no
public Apple documentation page** — `developer.apple.com`'s documentation JSON
for it returns 404 (checked 2026-09-02), while sibling entitlements resolve
fine. It is the browser-engine key; §1.3 covers who can hold it.

### 1.2 What "JIT-less JavaScriptCore" actually is

JSC has four tiers, named in WebKit's own architecture post
(<https://webkit.org/blog/10308/speculation-in-javascriptcore/>, Filip Pizlo):
**LLInt** ("an interpreter that obeys JIT compiler ABI"), **Baseline JIT**
(a method JIT), **DFG** and **FTL**. WebKit's published figures on JetStream 2:
Baseline is "more than 2×" LLInt, DFG a similar step over Baseline, FTL 1.1×
over DFG.

`disableJIT()` turns off **all three JIT tiers at once**. There is no
"baseline only" configuration available to an app, because the gate is
executable memory, not a policy dial — and every JIT tier needs the same
pages. §0 measured what that costs and what the unavailable middle would have
been worth: baseline-only would have run kaya's packing loop in **86 ms**
against LLInt's **251 ms**. That 165 ms is not on the table.

On ARM64 the LLInt is the offline-assembler-generated **assembly** interpreter,
not the C++ CLoop fallback, which is why JIT-less JSC is merely ~5× slower on
this workload rather than ~50×.

### 1.3 The EU/Japan browser-engine entitlements — and why kaya cannot hold one

Apple's **Web Browser Engine Entitlement**
(`com.apple.developer.web-browser-engine.host`) is documented at
<https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.developer.web-browser-engine.host>
(availability read 2026-09-02: **iOS 17.4+, iPadOS 17.4+**; abstract: "An
entitlement that enables your browser app to implement an alternative browser
engine"). Related keys listed on the same page:
`com.apple.developer.embedded-web-browser-engine`,
`…​.engine-association`, `…​web-browser-engine.networking`,
`…​.webcontent`, `…​.rendering`, `…​.restrict.notifyd`,
`com.apple.developer.memory.transfer_send` / `_accept`.

**Eligibility, from Apple's own program pages (read 2026-09-02):**

*EU* — <https://developer.apple.com/support/alternative-browser-engines/>.
The app must "Be distributed solely on iOS and/or iPadOS in the European
Union" and "Have the default web browser entitlement". The *Embedded* variant
instead requires the app to provide in-app browsing whose UI must "Take over
the majority of the display", "Provide a button or link to the default browser
of the system" and "Display the domain or URL whose content is being
rendered". Both require passing **90% of Web Platform Tests and 80% of
Test262**, a published vulnerability-disclosure policy, 30-day exploit
mitigation, memory-safe languages for web-content code, PAC adoption, and
process separation.

*Japan* — <https://developer.apple.com/support/alternative-browser-engines-jp/>,
read 2026-09-02: "In iOS **26.2** and later, browser engines other than WebKit
can be used in two types of apps for users in Japan: Dedicated browser apps …
and apps from browser engine stewards that provide in-app browsing
experiences". Same test-suite and security bars, distribution "solely in Japan
on iOS". This page is the one that names the payoff explicitly — authorized
developers get "just-in-time compilation, multiprocess support, and more".

**No non-browser app qualifies, in either region.** The entitlement is gated on
being a default-browser-capable browser or on shipping a majority-of-screen
in-app browser, on region-exclusive distribution, and on a web-engine
conformance bar. kaya is a GUI toolkit; none of the three is reachable, and
none is reachable by pretending.

One more clause worth keeping: **even a browser-engine holder must work
JIT-less.** Both program pages require the app to "Meet the above test suite
requirement if Just in Time (JIT) compilation is unavailable (e.g., if
Lockdown Mode is enabled by the user)". Apple treats JIT-less as a
first-class configuration on iOS even for the apps it privileges.

### 1.4 iPadOS, visionOS, tvOS, watchOS, macCatalyst

The restriction macro is defined in
<https://github.com/WebKit/WebKit/blob/main/Source/WTF/wtf/PlatformHave.h>
(read 2026-09-02):

```c
#if PLATFORM(IOS_FAMILY) && !PLATFORM(IOS_FAMILY_SIMULATOR) && !PLATFORM(MACCATALYST)
#define HAVE_IOS_JIT_RESTRICTIONS 1
#endif
```

and WebKit's `IOS_FAMILY` is defined as "iOS family, including iOS, iPadOS,
macCatalyst, tvOS, watchOS, and visionOS"
(<https://github.com/WebKit/WebKit/blob/main/Source/WTF/wtf/PlatformOS.h>,
read 2026-09-02). So:

- **iPadOS** — restricted, same as iOS. Browser-engine entitlements available
  there too (iPadOS 17.4+), same eligibility.
- **visionOS, tvOS, watchOS** — restricted, and with **no** browser-engine
  entitlement of any kind (the entitlement's availability names iOS and
  iPadOS only). Strictly worse than iOS.
- **macCatalyst** — explicitly excluded from the restriction; a Catalyst build
  gets the JIT. Not a phone, so not a route.

### 1.5 THE TRAP: the iOS Simulator is exempt, so kaya's iOS lane cannot see this

Read that macro again: **`!PLATFORM(IOS_FAMILY_SIMULATOR)`**. The simulator is
a macOS process and is **not** subject to the iOS JIT restriction, so
JavaScriptCore in a simulator app runs with **all four tiers**.

kaya's iOS lane is `tools/ios/run-sim.py` — a simulator pool. **Every JS
performance number that lane would ever print is the JIT'd number**, roughly
**4.6× better than the device** on kaya's own heaviest batch (§0). A lane that
green-lights JS on iOS from simulator timings is measuring a configuration no
user has. This is the same class as the size-class trap already written down
in CLAUDE.md ("what no gate holds is whether a PHYSICAL device reports the size
class the simulator did") and belongs in `docs/traps.md` **whether or not any
of this is built**, because it costs a session to rediscover and nothing to
write down.

### 1.6 Is Apple's in-app JavaScriptCore throughput documented anywhere?

**No.** Apple publishes no throughput figure for `JSContext` in a third-party
app, and no comparison against Safari. Apple's JavaScriptCore documentation
(<https://developer.apple.com/documentation/javascriptcore>) is an API
reference with no performance section, and no WWDC session states the
JIT-less penalty. The only quantitative statements available are WebKit's own
tier ratios (§1.2) and measurements like §0's.

That absence is itself a finding: **nobody is going to hand you this number;
you measure it or you guess it.** §0 measured it.

### 1.7 The routes people bring up, and why none of them is one

- **Attach a debugger.** A process with `get-task-allow` under a debugger gets
  `CS_DEBUGGED` and can map executable pages; this is how UTM SE, AltStore's
  "enable JIT" and JitStreamer work. It does **not** turn JSC's JIT on —
  `isJITEnabled()` above tests entitlements, not debug state — and it is a
  development/sideload mechanism, not an App Store distribution.
- **`JSC_useJIT` / `Options`.** Options can only turn the JIT *off*. The
  entitlement check runs first and is not an option.
- **`WKWebView`.** Gets the JIT, because its JavaScript runs out-of-process in
  a WebKit content process that holds the entitlement — which is exactly why
  an in-process `JSContext` does not. A WKWebView cannot call `libkaya`, runs
  on the main thread's web view, and communicates by string messages. Not a
  route for a binding.
- **Ship your own JIT engine (V8, SpiderMonkey).** The engine would hit the
  same wall: iOS refuses executable pages to the process. V8 has a `jitless`
  mode precisely for this, which makes it an interpreter — i.e. the thing the
  ruling forbids, at 20 MiB.

### 1.8 MEASURED: a plain macOS app that embeds JavaScriptCore is ALREADY JIT-less — and that hands kaya a free, faithful iOS harness

This resolves the prior report's one unresolved measurement and is, on its own,
the most useful operational finding here.

The prior report compiled `jsc-probes/jitbench.c` — the public JavaScriptCore
C API, three loops — and reported that `JSC_useJIT=false` "changed a 50M-iteration
arithmetic loop only from 349 ms to 373 ms", concluding it "could not tell those
two causes apart". **That probe was recompiled and re-run on 2026-09-02, against
the `jsc` CLI running the identical loops:**

| | arith 50M | typed-array 20M | strings 200k |
|---|---|---|---|
| `jsc` CLI, JIT | **15 ms** | **20 ms** | 5 ms |
| `jsc` CLI, `--useJIT=false` | 363 ms | 330 ms | 7 ms |
| **`clang`-built C probe embedding JavaScriptCore.framework, default** | **353 ms** | **332 ms** | 15 ms |
| same probe with `JSC_useJIT=false` | 370 ms | 334 ms | 14 ms |

The embedding probe's *default* numbers **are** the CLI's JIT-less numbers.
The environment variable did nothing because **there was no JIT to turn off.**

**The cause, isolated:** the same binary was re-signed with one entitlement —

```xml
<key>com.apple.security.cs.allow-jit</key><true/>
```

`codesign -s - --entitlements jit.ent -f jitbench` — and re-run unchanged:

    JIT=default  arith=24ms  typedarray=10ms  strings=4ms

**353 ms → 24 ms, 14.7×, from a signature.** On Apple Silicon the kernel
refuses `MAP_JIT` pages to a process without that entitlement, so JSC's
allocator comes up empty and `Options::useJIT()` goes false — the same end
state as §1.1's iOS path, reached by a different gate. For completeness,
Apple's own `jsc` CLI carries `com.apple.security.cs.allow-jit`,
`com.apple.security.cs.jit-write-allowlist`, `com.apple.security.cs.single-jit`,
`com.apple.private.verified-jit` and `com.apple.developer.hardened-process`
(`codesign -d --entitlements -`, read 2026-09-02).

**The asymmetry that matters:** on **macOS**, `com.apple.security.cs.allow-jit`
is a plain entitlement any developer adds to their own app. On **iOS**, the key
JSC accepts is `com.apple.developer.cs.allow-jit`, which is not self-grantable
and is issued only under the browser-engine programs of §1.3.

**Two consequences for kaya, both actionable today:**

1. **The iOS JS configuration is measurable on the Mac, in-process, with the
   real framework and no device.** Link JavaScriptCore, do not sign with
   `allow-jit`, and you are running exactly what an iPhone runs. Sign the same
   binary and you get the JIT'd column. One probe, two columns, a real
   comparison on every run — the shape kaya already uses for its watched
   negatives.
2. **A JSC-based kaya lane on macOS will silently pick one of those two worlds
   depending on how it is signed, and nothing will say which.** That is a
   false-green generator of exactly the kind invariant 4 exists for: a mac lane
   signed with `allow-jit` measures a configuration iOS does not have, and one
   signed without it measures a configuration macOS users do not have. Whichever
   way it is decided, the decision has to be *stated at the signing site and
   asserted at runtime* — `JSGlobalContextRef` gives no "is the JIT on" query,
   so the honest assertion is a timing canary, not a flag read.

### What this means for kaya

**"No interpreted JS on iOS" is not achievable by any JIT route.** Not by
entitlement (no non-browser app qualifies, in either region that has the
program), not by configuration (the switch only goes the other way), not by
engine choice (every engine hits the same OS wall), and not by trick (the
debugger route is not distributable and does not affect JSC anyway).

The only remaining reading of the ruling that iOS can satisfy is **ahead-of-time
compilation to native code, linked into the app at build time** — §2.

And whichever way the ruling lands, one thing is worth writing down today:
**the iOS simulator lane measures the JIT'd engine.** Any JS-on-iOS decision
taken from simulator numbers is taken from the wrong column.

## §2 Ahead-of-time compilation of JS/TS to native code

The only reading of the ruling iOS can satisfy. This section is what actually
exists, dated.

### 2.1 Static Hermes / `shermes` — the one serious contender, and it moved

The prior report (2026-09-02, earlier the same day) said Static Hermes was "12
commits old, on the `static_h` dev branch, never shipped in a release". **Two
of those three are now wrong, and the correction cuts both ways.**

**What changed (all read 2026-09-02 via the GitHub API):**

- **`static_h` is the repository's DEFAULT branch.** `GET /repos/facebook/hermes`
  returns `"default_branch": "static_h"`. Its last commit is dated
  **2026-09-02** (same day); `main`'s is **2026-08-13**. It is not a side
  branch — it is Hermes.
  (<https://github.com/facebook/hermes>)
- **It ships in React Native, as the default engine, on both phones.**
  "React Native 0.84 — **Hermes V1 by Default**", 2026-02-11
  (<https://reactnative.dev/blog/2026/02/11/react-native-0.84>): "Hermes V1
  represents the next evolution of the Hermes engine, with significant
  improvements to both the compiler and VM". It was an experimental opt-in in
  0.82 (2025-10-08). Current React Native is **v0.87.1, 2026-08-26**.
- **The engine's own feature set is far past the prior report's "ES6".**
  `doc/Features.md` on `static_h`
  (<https://github.com/facebook/hermes/blob/static_h/doc/Features.md>, read
  2026-09-02) lists `async`/`await`, generators, tagged template literals,
  classes with private fields, `Proxy`, `Reflect`, TypedArrays, optional
  chaining, BigInt, `Promise.withResolvers`. The June 2026 stable-release
  note (`doc/blog/2026-06-05-new-hermes-stable-release.md`) adds iterator
  helpers, `FinalizationRegistry`, `TextDecoder` in the engine, and a
  `--transform-ts` flag that strips TypeScript types "similar to Node.js's
  `--strip-types` — no separate Babel pass required".
  **kaya's four ruled sugar shapes — the implicit transaction (microtasks),
  promise dialogs, the row-handle `Proxy`, and the `kaya.fmt` tagged template
  — are all in that list.** That is a material change from the prior report's
  read.
- **Hermes now has a JIT**, and it is off by default. `CMakeLists.txt` on
  `static_h`: `set(HERMESVM_ALLOW_JIT 0 CACHE STRING "JIT mode: 0 (off), 1
  (auto) or 2 (force on)")`
  (<https://github.com/facebook/hermes/blob/static_h/CMakeLists.txt>, read
  2026-09-02). `doc/blog/2025-11-02-hermes-compilation-runtime-modes.md`
  enumerates the whole matrix: "AOT compilation of typed or untyped JS to
  bytecode / AOT compilation of typed or untyped JS to native code" plus
  runtime modes "Native execution / Bytecode interpreter / Lazy compilation /
  Baseline JIT".

**What did NOT change — and this is the part that decides it:**

- **`shermes` does not ship in React Native.** MEASURED: the npm package
  `hermes-compiler@250829098.0.17` (published **2026-08-21**), which is "the
  hermes compiler CLI used during the React Native build process", was
  downloaded and its contents listed. It contains **`hermesc` only** — a
  `linux64-bin`, an `osx-bin` and a `win64-bin` — and **no `shermes`**. The
  shipped `hermesc --help` output ends its "Choose output" list at
  `-emit-binary` (bytecode). There is no `-emit-c`, no object file, no native
  target. It *does* carry `-parse-ts` and `-typed`, so the Static Hermes typed
  front end is in the shipping compiler; only the native back end is absent.
  React Native's own Hermes page still describes the pipeline as bytecode:
  "you are using the highly optimised pre-compiled bytecode … Confirm that you
  are using the `.hbc` file" (<https://reactnative.dev/docs/hermes>, read
  2026-09-02). Neither the 0.84 nor the 0.87 release post mentions Static
  Hermes, native compilation or a JIT.
- **The typed language is still declared unstable.**
  `doc/TypedLanguage.md` opens: "The typed language implementation is **in
  progress and considered unstable**. … The Flow type syntax is supported (use
  `-typed`). The TypeScript type syntax is **partially supported** (use
  `-parse-ts` to convert TS to Flow before compilation)."
  (<https://github.com/facebook/hermes/blob/static_h/doc/TypedLanguage.md>,
  read 2026-09-02.) Its object types are **exact and order-sensitive**
  ("Properties must be in the same order as the type requires"), its arrays
  are a nominal generic incompatible with untyped JS arrays, and its classes
  are nominally typed. That is not TypeScript; it is a Flow-shaped language
  that TypeScript syntax is partly parsed into.
- **The Node-API implementation has not moved since July.**
  `API/napi/` on `static_h` has **12 commits, oldest 2026-05-12, newest
  2026-07-16** (GitHub API, read 2026-09-02) — the same 12 the prior report
  counted. What the prior report could not see is how much is in them: the
  `README.md` describes an implementation "built directly on Hermes VM
  internals (not JSI), covering all non-experimental APIs through
  NAPI_VERSION 10", across 22 source files including
  `hermes_napi_typedarray.cpp`, `hermes_napi_dataview.cpp`,
  `hermes_napi_tsfn.cpp` (thread-safe functions) and `hermes_napi_promise.cpp`
  — and a test story: "31 GTest files", "~65 test files vendored from the
  Node.js source tree. **33 pass, 31 skipped** … **Zero failures**".
  (<https://github.com/facebook/hermes/blob/static_h/API/napi/README.md>.)
  Stated limitations: external strings always copy, `napi_adjust_external_memory`
  does not influence GC, weak-reference teardown ordering asserts in debug
  builds. **It is not in any release and not in React Native.**

**How AOT-compiled Hermes would call `libkaya` — and this part is genuinely
good.** Static Hermes has a first-class C FFI. hermes/tools/ffigen/ffi_helpers.js
(<https://github.com/facebook/hermes/blob/static_h/tools/ffigen/ffi_helpers.js>,
read 2026-09-02) is written in it:

```js
const _malloc = $SHBuiltin.extern_c({include: "stdlib.h"},
    function malloc(size: c_size_t): c_ptr { throw 0; });
```

`c_ptr` is a **native type in the typed language** (`doc/TypedLanguage.md`
lists it under "Native Types"), hermes/tools/ffigen/ffigen.py generates these
declarations from C headers, and the call compiles to a direct C call — no
N-API, no JSI, no marshalling layer. For a binding whose whole job is
`kaya_submit(ptr, len)` that is the cleanest interop story of any option in
this report. It is also the part that is least exercised outside Meta.

**What `shermes` actually emits.** hermes/tools/shermes/shermes.cpp's output levels
are `C`, `Asm`, `Obj`, `SharedObj`, `Executable`, `Run` — it lowers JS to C,
then invokes a C compiler, whose path comes from `SHERMES_CC` / the `CC`
environment variable, with `SHERMES_CC_SYSCFLAGS` and `SHERMES_CC_SYSLDFLAGS`
for system flags (hermes/tools/shermes/CMakeLists.txt). So **cross-compiling to
`arm64-apple-ios` or `aarch64-linux-android` is mechanically reachable** —
point `CC` at `xcrun -sdk iphoneos clang` or the NDK's clang and supply a
Hermes VM built for that target. `doc/CrossCompilation.md` documents
cross-building **the engine** for Android with the NDK toolchain file; it
documents **no shermes cross-compilation pipeline for either phone**. Nobody
has published one.

**And the honest asterisk on "no interpreter in the bundle":** shermes output
**links the Hermes VM**, and even the `--lean` variant only swaps in
`hermesHBCBackendLean` — a reduced bytecode *compiler*, not the removal of the
bytecode *interpreter* (`lib/CMakeLists.txt`, read 2026-09-02). AOT-compiled
functions run as native code; the runtime beside them is still a JavaScript
VM with an interpreter loop in it. If the ruling means "no interpreter ships
in the app", Static Hermes does not literally deliver that either, unless the
linker can be shown to have dropped the loop.

Two build options on `static_h` are worth naming because they show how far the
native path is actually built out inside Meta
(<https://github.com/facebook/hermes/blob/static_h/CMakeLists.txt>, read
2026-09-02):

```cmake
set(HERMESVM_INTERNAL_JAVASCRIPT_NATIVE OFF CACHE BOOL
  "Use natively compiled InternalJavaScript. Set OFF to use bytecode version")
set(HERMES_BUILD_LEAN_LIBHERMES OFF CACHE BOOL "Exclude the Hermes compiler from libhermes.")
```

The first exists because Hermes's own internal JavaScript — which includes the
`Promise` implementation, "an internally bundled **polyfill compiled to
bytecode** rather than … a native intrinsic" (`doc/Features.md`, Known
Deviations) — can be AOT-compiled to native. **By default it is not.** So on a
stock Hermes, kaya's implicit-transaction commit, which rides
`Promise.resolve().then`, executes interpreted bytecode even in a
natively-compiled app. The deviations listed for that polyfill are
`Symbol.species` dispatch and an extra microtask hop **on `Promise`
subclasses**; kaya subclasses nothing, so its ruled semantics are unaffected.

One more constraint Hermes shares with JavaScriptCore, from the same file:
"**ES Modules (`import`/`export`): Hermes does not currently provide a runtime
module loader** … the React Native ecosystem relies heavily on bundlers (like
Metro)". So the esbuild step the prior report's D5 recommends is required by
this route too — it is not an extra cost of choosing Hermes.

**MEASURED, 2026-09-02 — what Hermes V1 actually costs to ship.** The Maven
artifacts for `260318099.0.1` (latest published, `lastUpdated 20260821`) were
downloaded and their binaries measured, then deleted:

| artifact | file | size |
|---|---|---|
| `com.facebook.hermes:hermes-ios:260318099.0.1` (release) | `hermesvm.xcframework/ios-arm64/hermesvm.framework/hermesvm` | 6,321,384 B as shipped; **2,986,156 B (2.85 MiB) after `strip -x`** |
| `com.facebook.hermes:hermes-android:260318099.0.1` (release AAR, 85,031,145 B) | `jni/arm64-v8a/libhermesvm.so` (already stripped, NDK r27b) | **2,688,760 B (2.56 MiB)** |

So Hermes V1 is roughly **2.6–2.9 MiB per ABI** — up from the ~2.04 MiB the
prior report measured for the older Hermes, and against **0 bytes** for
JavaScriptCore on iOS and ~762 KiB for QuickJS-ng on Android.

**And the shipped iOS framework contains the JIT it can never use.** `strings`
over that binary returns `Xjit`, `Xjit-memory-limit`, `Xjit-crash-on-error`,
`"JIT mode (default off)"`, `"JIT is disabled"`, `"JIT is on"`. So Meta builds
Hermes V1 with `HERMESVM_ALLOW_JIT` on, the runtime default is **off**, and on
iOS it could not be turned on in a third-party app anyway (§1). The same
binary's bundled `hermesc` (also in the iOS artifact) again offers no output
beyond `-emit-binary`.

### 2.2 Porffor — the only other live JS→native compiler, and its one stub is kaya's design

Full notes with every URL are in `jit-aot-survey.md` beside this report; the
decision-relevant facts, all read **2026-09-02**:

- Porffor is genuinely AOT. Its README: "Porffor is a 100% AOT compiled JS
  engine/runtime. **There is nothing interpreted or compiled just-in-time.**
  Porffor compiles JS to C (with an IR inbetween)."
  (<https://github.com/CanadaHonk/porffor>)
- It reached **alpha three weeks ago**: `alpha-1` 2026-08-12 through `alpha-4`
  2026-08-29 (GitHub releases API). One author. 5,104 stars.
- **It no longer emits WebAssembly at all** — `main`'s targets are `c` and
  `native`; the pipeline is IR → C → your `cc`.
- Its C ABI story is first class and would suit kaya:
  `Porffor.dlopen(lib, {fn: {parameters: ["pointer","buffer","i32"], result: "i32"}})`.
- **Conformance: 67.45 % of test262**, and that figure is the one Porffor
  publishes — `https://cdn.porffor.dev/test262/history.json`, whose most recent
  data point is dated **2026-03-06**, six months stale despite four alpha
  releases since. 8,049 of the failures are *runtime* errors: the program
  compiles and then dies. A mature engine scores 95–99 %.
- Its own docs: "Porffor is pre-alpha. **Treat compatibility as something to
  verify, not something to assume.**" (<https://porffor.dev/docs/>)
- **iOS is untested.** "The result targets the OS and CPU architecture of the
  build machine." The `porf c` → clang-for-iOS route is plausible and
  undemonstrated.

**And the disqualifier, which is specific to kaya:** Porffor's `Proxy` is a
**stub that returns the target unchanged and never fires a trap** — filed under
Porffor's own documentation heading "Silent gaps". kaya's row handle *is* a
Proxy, and its ruled contract (docs/js-plan.md §4 ruling 3) is that a
misspelled field on assignment is **refused by name with the record's fields in
the sentence**. Under Porffor that contract inverts into a silent wrong write,
and **no gate can observe it** — the wire bytes are simply different. Invariant
3's whole shape is "failures become guards"; this is a failure with no
observable, which is the one kind kaya has no answer for. Any Porffor plan
begins with "replace the row-handle design", which is a binding redesign, not a
port.

### 2.3 The WebAssembly detour — the hard half is JS→Wasm, not Wasm→iOS

Worth stating because it is the route people reach for, and the difficulty is
the opposite way round from the intuition.

**Wasm→iOS is solved.** `wasm2c` (WABT 1.0.41, 2026-05-07) and `w2c2` compile a
`.wasm` to portable C that *your* clang compiles at build time and links into
the signed binary — no executable pages mapped at runtime, nothing to
interpret, and imports become ordinary C symbols the linker resolves, so
calling `libkaya` is direct. w2c2 reports **~7 % slower than native** on
Coremark 1.0 and "passes 99.9 % of the WebAssembly core semantics test suite".
This is legal, mature AOT on iOS.

**JS→Wasm does not exist.** AssemblyScript (0.28.20, 2026-07-22) compiles a
*subset* of TypeScript with its own type system, not JavaScript. Porffor
dropped its Wasm backend. There is no compiler to feed the wasm2c pipeline.

**And every in-process Wasm *runtime* on iOS is an interpreter or is blocked.**
JavaScriptCore's own Wasm falls back to IPInt when `Options::useJIT()` is false.
wasm3 is an interpreter by design and says why: "on some platforms (i.e. iOS…)
you can't generate executable code pages in runtime". WAMR's `wamrc` AOT is
ruled out by its own maintainer — "iOS doesn't support mmap for allocating
executable memory… probably not able to support AoT on iOS" (issue #242, still
restated in #4166 in 2025), and XIP does not help because it addresses
read-only *code*, not non-executable *data*. Wasmtime's `.cwasm` needs
executable pages; its **Pulley** backend, which a maintainer named as the iOS
answer ("execution with Pulley doesn't generate or jump to any native code",
2026-01-07), **is an interpreter**. Wasmer **deleted `create-exe`**, its
static-link AOT path, on **2026-08-27**.

### 2.4 The things that look like AOT and are not

Each of these compiles ahead of time and then **interprets**: QuickJS `qjsc`
(emits C containing bytecode plus the interpreter), Moddable XS `xsc` ("XS
binary files containing symbols and byte codes"), Hermes `hermesc` (HBC — what
React Native actually ships), JerryScript snapshots. GraalVM `native-image`
with GraalJS AOT-compiles *the engine*, and without a JIT the guest JS runs in
Truffle's "fallback runtime… interpreter-only mode" — and Native Image is
"available for Linux, macOS, and Windows", with iOS only via Gluon Substrate
and no one having done it with GraalJS. `bun build --compile` and
`deno compile` bundle your code **with a copy of a JIT'd runtime**, and neither
targets iOS or Android at all. NectarJS is dead (last commit 2022-12-30). ts2c
is a toy ("~70 % of ES3… all numbers are `int16_t`"). Prepack is archived.

**One direction-of-travel observation, because it is evidence about the bet:**
in the last six months the ecosystem moved *toward* interpreters for
JIT-forbidden platforms, not away — Wasmtime shipped Pulley, Deno added a
QuickJS engine option, wasm3 tagged its first release since 2021, and Wasmer
removed its static-link AOT path. The single countercurrent is Porffor's alpha.

### What this means for kaya

**There are exactly two live routes to AOT-compiled JavaScript on a phone, and
neither is buildable today.**

*Static Hermes* is the serious one, and it is much further along than the prior
report knew: its branch is Hermes's default, its engine ships as React Native's
default on both phones, its feature set now covers every shape kaya's JS sugar
was ruled on, and `$SHBuiltin.extern_c` is the best `libkaya` interop in this
report. But **`shermes` itself ships in nothing** — measured, from the actual
npm package the React Native build uses — its typed language is documented as
unstable and its TypeScript support as partial, no one has published a
cross-compilation pipeline to either phone, and the runtime it links still
contains a bytecode interpreter that by default executes `Promise`.

*Porffor* is three weeks into alpha, publishes a six-month-old 67 % conformance
figure, has never targeted iOS, and stubs the exact language feature kaya's row
handle is built on — silently.

So the honest statement is: **"no interpreted JS on the phones" is, in
September 2026, a research project, not a configuration.** It could become
true — the most likely path is Static Hermes shipping `shermes` in a React
Native release with an iOS/Android pipeline, which is a thing to watch rather
than a thing to plan against. If the ruling is held strictly today, the
achievable outcome is not "AOT JavaScript on the phones"; it is **no JavaScript
on the phones**.

## §3 Android — where the ruling IS satisfiable, and cheaper than expected

Android permits a JIT in an ordinary app process, so on this phone "not
interpreted" is a purchasable property. Full notes with every URL are in
`jit-android.md` beside this report; the decision-relevant facts, all read
**2026-09-02**.

### 3.1 The correction that matters: the 21.97 MiB V8 was the JIT-LESS one

The prior report measured V8 on Android at **21.97 MiB** and used it to
disqualify V8 on size. That artifact is `v8-android`'s
`arm64-v8a/libv8android.so` = **23,040,248 B**, and it is built **jitless**:
the publisher's CI matrix sets `NO_JIT = !contains(variant,'jit')` →
`v8_enable_lite_mode=true`, and V8's own `BUILD.gn` has
`v8_jitless = v8_enable_lite_mode`. Confirmed on the binaries themselves —
`liftoff` symbol count 0 vs 8, `WebAssembly` 9 vs 88 between the two variants.

**Both JIT-capable prebuilts are smaller than the jitless one that was
measured:**

| artifact (read 2026-09-02) | arm64-v8a `.so` | stored in APK | JIT | last publish |
|---|---|---|---|---|
| `v8-android` (the previously measured one) | 23,040,248 B = **21.97 MiB** | — | **none — `v8_jitless`** | — |
| `v8-android-jit-nointl` 11.1000.4 | **14.79 MiB** | 5.20 MiB | full V8 JIT | V8 11.10, **2023-08-20**; repo untouched ~2 yr |
| **`jsc-android` 2026004.0.1** (no Intl) | **9.70 MiB** (10,173,344 B) | **3.39 MiB** | **baseline JIT on** | Maven Central, **2024-11-29** |
| `jsc-android-intl` 2026004.0.1 | 19.17 MiB | 6.74 MiB | same | same |
| Hermes V1 `260318099.0.1` | **2.56 MiB** (measured, §2) | — | JIT compiled in, **default off** | 2026-08-21 |
| QuickJS-ng (prior report, built with this repo's NDK) | 762 KiB | 379 kB | none | ~monthly |

### 3.2 jsc-android's JIT is ON — and it is exactly the tier §0 measured

From `scripts/compile/jsc.sh`
(<https://github.com/react-native-community/jsc-android-buildscripts/blob/main/scripts/compile/jsc.sh>,
read 2026-09-02):

```sh
if [[ "$ARCH_NAME" = "i686" ]]; then
    JSC_FEATURE_FLAGS=" -DENABLE_JIT=OFF -DENABLE_C_LOOP=ON "
else
    JSC_FEATURE_FLAGS=" -DENABLE_JIT=ON  -DENABLE_C_LOOP=OFF "
fi
... build-webkit --jsc-only --jit --no-webassembly ... -DENABLE_DFG_JIT=OFF -DENABLE_FTL_JIT=OFF
```

So on arm64-v8a, armeabi-v7a and x86_64 the JIT is on and the C-loop is off;
only 32-bit x86 is interpreted. **But the optimizing tiers are off** — no DFG,
no FTL. That is "LLInt plus baseline JIT", which is **precisely the
configuration §0 measured** on the Mac by turning DFG and FTL off:
**86 ms** on the 100k-record pack, against 47 ms with all four tiers and
251 ms with none. So a jsc-android Android leg would land roughly **2.9×
better than an interpreter and 1.8× worse than a full-tier engine** on kaya's
own workload — a number this report can quote rather than guess, because the
tier is named in the build script and measured in §0.

Its embedding surface is also right: the AAR ships a **prefab** module
(`api 24, ndk 27, stl c++_shared`) with `JavaScriptCore/JSTypedArray.h`, and
the arm64 binary exports `JSObjectMakeTypedArrayWithBytesNoCopy`,
`JSObjectMakeArrayBufferWithBytesNoCopy`, `JSObjectGetTypedArrayBytesPtr` and
`JSObjectGetArrayBufferBytesPtr` — kaya's exact zero-copy wire surface — plus
`JSObjectMakeFunctionWithCallback`, in a plain C API with no JNI in the path.
Distribution note: the **npm** `jsc-android` is stale (`250231.0.0`,
2023-02-05); the live coordinate is Maven Central
`io.github.react-native-community:jsc-android:2026004.0.1`, `lastUpdated`
2024-11-29, which is what `@react-native-community/javascriptcore` depends on.

### 3.3 Hermes on Android is an interpreter as shipped

Hermes's tree does contain an arm64 asmjit JIT (§2), but `CMakeLists.txt`
defaults `HERMESVM_ALLOW_JIT 0` and React Native's Android Gradle build passes
no override, so **the Hermes that ships in every React Native app on Android is
a pure bytecode interpreter**. `shermes` can emit a `.so`, and no React Native
Android pipeline uses it.

### 3.4 The two that are disqualified on mechanism

**A headless WebView** is pinned to the Looper of the thread that created it —
in practice the UI thread, which is the one thread kaya's app thread is defined
not to be — and `addJavascriptInterface` carries no `ArrayBuffer`.

**`androidx.javascriptengine`** is real and current now — **1.1.0, stable since
2026-05-06**, backed by the WebView's V8 **with the JIT on**. It is still
unusable here, for a reason no version will fix: **the JS runs in a different,
isolated OS process and can never call `libkaya`.** The only channels are
Binder-mediated — script text or an fd in, `provideNamedData` bytes in (one-shot,
unique id per array, not a call/response channel), a `String` result out, and
since 1.1.0 a `MessagePort` carrying `Message.TYPE_ARRAY_BUFFER` as `byte[]`.
Even that is at minimum one copy into the parcel and one out, because the two
sides do not share an address space. The limits: return size defaults to
`DEFAULT_MAX_EVALUATION_RETURN_SIZE_BYTES = 20971520` (20 MiB), and absent the
newer feature flag everything rides Android's shared **1 MB** Binder
transaction buffer
(<https://developer.android.com/reference/android/os/TransactionTooLargeException>).
kaya's `kaya_submit(ptr, len)` — a function call today — would become a
cross-process round trip per batch. The library is built for "evaluate an
untrusted snippet and get an answer", which is not this.

### 3.5 The Rust-native options, corrected

**`rusty_v8` has no Android prebuilt.** Android assets were dropped at
**v0.102.0 (2024-08-05)** and the current **152.2.0 (2026-08-20)** has none, so
choosing it means owning a V8 source build per ABI.

**`servo/mozjs` does publish one, today.** Prebuilt
`libmozjs-aarch64-linux-android.tar.gz`, **16.2 MiB, SpiderMonkey 153,
2026-08-29**, whose `libjs_static.a` carries 20 `Unified_cpp_js_src_jit*.o`
members — the JIT is in. It hands a Rust core the JSAPI directly. It is the
freshest JIT-capable Android artifact in the survey, and the least travelled
path for an embedder of kaya's shape.

### What this means for kaya

**On Android the ruling is affordable, and the cheapest way to satisfy it is
also the smallest artifact: `jsc-android` at 9.70 MiB arm64 (3.39 MiB in the
APK), with its baseline JIT on and kaya's exact zero-copy typed-array surface
exported.** It is 2.3× smaller than the cheapest JIT'd V8 and 43 % of the
jitless V8 the prior report priced. Its weaknesses are real and should be said
out loud: it is a community build of a 2019-era WebKit branch, last published
2024-11-29, with no DFG or FTL.

It also produces the tidiest possible answer to "one JS implementation":
**JavaScriptCore on both phones** — free on iOS, 9.70 MiB on Android — which is
the same engine, the same C API, the same zero-copy primitives, and one bridge
instead of two. The prior report rejected that on size while comparing against
a 762 KiB interpreter; against the *JIT-capable* alternatives (14.79 MiB V8,
16.2 MiB SpiderMonkey) it is the cheap option, not the expensive one.

And the asymmetry the ruling cannot remove: **on Android kaya can buy a JIT for
9.70 MiB; on iOS it cannot buy one at any price.**

## §4 What the ruling can mean — three readings, tested against the numbers

"No interpreted JS … a normalization step (babel/esbuild) or bundling a
runtime is fine, but no interpretation." Three things that sentence can be
protecting. Each is stated, then tested.

### Reading (i) — PERFORMANCE: "an interpreter is too slow for handlers that pack wire records"

**Tested in §0, and it does not hold at kaya's sizes.**

An ordinary handler emitting 20 records costs **52.9 µs** on JIT-less
JavaScriptCore and **78.8 µs** on QuickJS-ng, against 9.7 µs with the JIT. At
60 Hz a frame is 16,667 µs, so the worst of those is **0.47 % of a frame** —
and this is the encoder kaya has today, not a tuned one. Nothing in kaya's
handler path is at risk from interpretation.

The one place it is visible is the batch that is already kaya's slow path: the
portfolio's **15,003 inserts** cost 8.57 ms JIT'd and **39.63 ms** JIT-less
(4.6×), call it 80–120 ms on phone-class silicon. That is user-perceptible.
It is also the batch that commit `2f36c09` already split away from the push
precisely because it was too slow — so the remedy for it exists and is not
"get a JIT".

**And there is a baseline in this tree that settles it.** kaya's own **Python**
binding packs the same 15,003 records in **6.03 ms** on CPython 3.14.7 — a
bytecode interpreter with no JIT, already ratified for both mobile bundles.
kaya's **JavaScript** binding packs them in **11.30 ms on node with a full
JIT**. The JS tier is already 1.9× slower than the Python tier *with* a JIT,
and the reason is not the engine: `wire.py` calls `struct.pack` once per
scalar, `wire.ts` allocates a `Uint8Array` and a `DataView` per scalar. If
interpretation were the thing that makes a binding too slow to pack wire
records, the Python binding would be the one in trouble, and it is the fastest
one measured.

**And the encoder dominates the engine.** §0's second table: at a fixed
encoder the JIT is worth 4.6×; at a fixed engine, replacing kaya's
two-allocations-per-scalar `wire.ts` with a single-cursor encoder is worth
**15.6×**. JIT-less JSC with a cursor encoder runs the 15,003-record batch in
**13.88 ms**, against the **11.45 ms** node manages on the desktop *today*.
If the ruling is about speed, **the cheapest and largest win available is a
`wire.ts` rewrite that helps all nine bindings' JS tier on all five
platforms — and it is worth more than any engine decision in this report.**

### Reading (ii) — PRINCIPLE: "a kaya app is a compiled program and must not ship a script interpreter"

**Coherent, and it costs the phones — but kaya has already ruled the other way
once, on the same two platforms.**

`docs/python-mobile-plan.md`, ratified by the maintainer **2026-08-28**:
"packaging's important half is Python on mobile — **CPython and the binding
embedded in the iOS and Android app bundles**". Its own §D5 puts that at
"**~20 MB on iOS (framework + stdlib + extension frameworks), ~26 MB on
Android carrying both ABIs**". CPython is a bytecode interpreter. kaya's
answer to "may a kaya app ship a script interpreter on a phone?" is on the
record, and it is yes, at 20–26 MB.

Against that, JavaScriptCore on iOS costs **0 bytes** (system framework) and
QuickJS-ng on Android costs **762 KiB** — 1/34th of the Python bundle already
accepted. A principle that admits 26 MB of CPython and refuses 762 KiB of
QuickJS is not a principle about interpreters; it is a preference about
JavaScript, which is a legitimate thing to hold but should be said in those
words.

If the principle is meant strictly, it has exactly one implementation —
Static Hermes AOT on both phones (§2) — and §2 shows what that costs today:
a compiler that ships in no release, a typed language its own documentation
calls unstable, a TypeScript front end its own documentation calls partial, no
published cross-compilation pipeline for either phone, and a runtime that
still links a JavaScript VM with a bytecode interpreter in it (and executes
`Promise` as interpreted bytecode unless a non-default build flag is set). The
strict reading is not satisfiable by Static Hermes today either — only more
nearly satisfied.

### Reading (iii) — START-UP: "an interpreter starts fast, a JIT warms slowly"

**Tested in §0, and it is simply not a factor.** JSC with the JIT reaches
steady state *within the first 15,003-record batch*: 10 ms cold, 8–10 ms
thereafter — its cold number already beats the interpreter's warm number by
3.7×. Process start-up on an empty script is 4.9 ms (`jsc`), 4.4 ms
(`jsc --useJIT=false`), 2.4 ms (`qjs`). There is no warm-up trade to make.

### What this means for kaya

Of the three readings, **only (ii) survives contact with the measurements** —
and (ii) is a values position, not an engineering one, which is why it is the
maintainer's to hold and not this report's to argue with. What the report can
do is price it: reading (ii), taken strictly, is the only one that forbids
JavaScriptCore on iOS, and the only thing it can be traded for is a Meta
research compiler that has not shipped.

Reading (i) has a better answer than any engine: **fix `wire.ts`**. That is a
15.6× win, it is kaya's own code, it needs no ruling, it helps the three
desktop lanes that ship today, and it makes the interpreted phone case land
within 21 % of what the desktop does now.

## Decisions

The three options as posed, priced with the measurements above. All figures are
the 15,003-record portfolio batch on an M5 Pro unless stated; a phone is
2–3× slower and scales linearly.

### Option A — JavaScriptCore JIT-less on iOS, a JIT'd engine on Android

*Interpreted on iOS because Apple says so; native code on Android.*

Two shapes, and §3 changed which one is cheaper:

- **A1 — JSC on iOS + QuickJS-ng on Android.** The prior report's
  recommendation. 0 bytes on iOS, 762 KiB on Android. **But QuickJS-ng is an
  interpreter**, so this option is interpreted on *both* phones and satisfies
  the ruling nowhere. Measured cost: 39.63 ms on iOS, **58.80 ms** on Android —
  the slowest row in this report.
- **A2 — JavaScriptCore on both phones.** 0 bytes on iOS; **9.70 MiB arm64
  (3.39 MiB in the APK)** on Android from
  `io.github.react-native-community:jsc-android:2026004.0.1`, with the baseline
  JIT **on**, `JSObjectMakeTypedArrayWithBytesNoCopy` exported, and one C API
  and one bridge for both phones instead of two. Measured cost: **39.63 ms on
  iOS, ~2.9× better than that on Android** (the baseline-JIT tier §0 measured
  at 86 ms against LLInt's 251 ms on the 100k pack).

A2 is strictly better than A1 on every axis the ruling cares about, and the
only axis it loses is 9 MiB against a project that has already accepted 26 MB
of CPython on the same platform.

**What A gives up:** iOS runs interpreted. That is not a choice inside this
option; §1 establishes it is not a choice inside *any* option.

### Option B — AOT everywhere via Static Hermes

*No interpreter anywhere, if it works.* **What works today, exactly:**

- The engine ships and is good: `static_h` is Hermes's default branch, Hermes
  V1 is React Native's default on both phones since **RN 0.84, 2026-02-11**,
  and its feature list now covers `async`/`await`, `Proxy`, tagged templates
  and TypedArrays — every shape kaya's four JS sugar rulings depend on.
- `$SHBuiltin.extern_c` is the best `libkaya` interop in this report: `c_ptr`
  is a native type in the language and the call compiles to a direct C call.
- **`shermes` ships in nothing.** MEASURED: `hermes-compiler@250829098.0.17`
  (2026-08-21), the package the React Native build actually uses, contains
  `hermesc` and no `shermes`; its `hermesc`'s output options end at
  `-emit-binary`. Same for the `hermes-ios` artifact's bundled `hermesc`.
- The typed language is documented as "**in progress and considered
  unstable**"; TypeScript is "**partially supported**" and is converted to Flow
  first; object types are exact and **order-sensitive**; arrays are a nominal
  generic incompatible with untyped JS arrays.
- No published cross-compilation pipeline for either phone. Mechanically
  reachable (`SHERMES_CC` + `SHERMES_CC_SYSCFLAGS`), demonstrated by nobody.
- Node-API on Hermes: 12 commits, **untouched since 2026-07-16**, not in any
  release — though far more substantial than a commit count suggests (22
  source files, 31 unit-test files, 33 of ~65 vendored node tests passing,
  zero failures).
- **It does not literally deliver "no interpreter in the bundle" either**: the
  output links a JS VM, and `Promise` — which kaya's implicit transaction rides
  — is a bytecode-compiled polyfill unless `HERMESVM_INTERNAL_JAVASCRIPT_NATIVE`
  is turned on, which it is not by default.

The only other AOT candidate, **Porffor**, is three weeks into alpha, publishes
a **six-month-stale 67.45 %** test262 figure, has never targeted iOS, and its
`Proxy` is a **stub that silently returns the target and never fires a trap** —
which is kaya's row handle, whose entire contract is refusing a misspelled
field by name. That failure has no observable, so no gate can catch it.

**Option B is not buildable in September 2026.** Held strictly today it does
not produce AOT JavaScript on the phones; it produces **no JavaScript on the
phones**.

### Option C — accept interpretation on the phones as Apple's constraint, pick the smallest engine

*The prior report's shape, honestly labelled.* On iOS this is forced. On
Android it is a choice, and the smallest engine is QuickJS-ng at 762 KiB —
which measures **58.80 ms**, the slowest option here, to save 9 MiB against
A2's JIT'd JavaScriptCore.

---

### Recommendation

**Take A2, and spend the freed effort on `wire.ts`.**

1. **iOS runs JavaScriptCore, interpreted, and this is stated as Apple's
   constraint rather than kaya's preference.** §1 closes every alternative:
   the entitlement is `com.apple.developer.cs.allow-jit` or
   `dynamic-codesigning`, WebKit's own source is the gate, the browser-engine
   programs (EU, and Japan from iOS 26.2) require being a default-browser-capable
   browser or a majority-of-screen in-app browser, distributed region-exclusively,
   passing 90 % WPT and 80 % test262. kaya is none of those. There is no version
   of this that ends differently.
2. **Android runs JavaScriptCore too, with its baseline JIT on**, at 9.70 MiB
   arm64 / 3.39 MiB in the APK — cheaper than every other JIT'd option
   (V8 14.79 MiB, SpiderMonkey 16.2 MiB) and the *only* choice that gives both
   phones one engine, one C API, one bridge, and one set of zero-copy
   primitives. The ruling is honoured on the platform where it can be.
3. **The performance concern is answered by kaya's own code, not by an
   engine.** Measured: at a fixed encoder the JIT buys **4.6×**; at a fixed
   engine, replacing `wire.ts`'s two-allocations-per-scalar shape with a single
   growable cursor buffer buys **15.6×**. kaya's Python binding — a bytecode
   interpreter — packs the same batch in **6.03 ms** while its JavaScript
   binding takes **11.30 ms on node with a full JIT**. A JIT-less
   JavaScriptCore with a fixed encoder lands at **13.88 ms**, within **1.23×**
   of what kaya's JS binding does on the desktop today. **This is the highest-
   value item in the report and it needs no ruling**: it helps the three
   desktop lanes that ship now, it helps every engine equally, and it is
   entirely inside the tree.
4. **Watch Static Hermes; do not plan against it.** The thing to watch for is
   a single event: `shermes` appearing in a `hermes-compiler` release with a
   documented iOS/Android pipeline. That is checkable in one command
   (`npm pack hermes-compiler && tar tzf`), which makes it a cheap standing
   check rather than a judgement call.

### Two things to write down whatever is decided

Both are `docs/traps.md` material today, independent of every ruling above,
because each costs a session to rediscover and nothing to record:

1. **The iOS Simulator is exempt from the iOS JIT restriction.**
   `HAVE_IOS_JIT_RESTRICTIONS` is `PLATFORM(IOS_FAMILY) &&
   !PLATFORM(IOS_FAMILY_SIMULATOR) && !PLATFORM(MACCATALYST)`. kaya's iOS lane
   is a simulator pool, so every JS number that lane could ever print is the
   JIT'd one — **4.6× better than the device** on kaya's heaviest batch. A
   JS-on-iOS decision taken from simulator timings is taken from the wrong
   column.
2. **A macOS process that embeds JavaScriptCore is JIT-less unless it is signed
   with `com.apple.security.cs.allow-jit`** — measured at **353 ms → 24 ms**,
   14.7×, from the signature alone on one unchanged binary. This is why the
   prior report's `JSC_useJIT=false` probe showed no difference: there was no
   JIT to turn off. It is also a gift: it means the iOS JavaScript
   configuration is measurable on the Mac, in-process, against the real
   framework, with no device — and that any mac lane embedding JSC silently
   picks one of two worlds depending on how it was signed, with nothing to say
   which, since `JSGlobalContextRef` exposes no "is the JIT on" query. The
   honest assertion is a timing canary, not a flag read.
