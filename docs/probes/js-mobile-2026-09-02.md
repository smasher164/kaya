# The JS binding on mobile — research report

Written 2026-09-02 for the ruling "the JS binding must run on EVERY
platform including mobile, and on iOS under JavaScriptCore". RESEARCH
ONLY: nothing in the repo was changed. Every claim carries its source.

---

## The eight things that decide this

Every one was measured on this machine or read out of a primary source;
the section is named beside each.

1. **Apple does not require JavaScriptCore.** MEASURED: the strings
   "JavaScriptCore" and "WebKit" appear **zero times** in the current
   Apple Developer Program License Agreement, and its interpreted-code
   clause governs *downloaded* code only. Guideline 2.5.2 names no
   engine. kaya already ships CPython in its own iOS bundle. JSC on iOS
   is a good choice, not a rule. (§2.0)
2. **JSC drops its API lock around native callbacks.** MEASURED, and it
   breaks the ruled semantics if ignored: a pump thread ran a handler
   *inside* another handler's continuation — `app:enter | pump:handler |
   app:leave`. So the iOS bridge must have **no pump thread**; the app
   thread runs the occurrence loop itself. That is a simplification, and
   it is mandatory. (§1.5)
3. **The implicit transaction survives on JSC, exactly.** MEASURED:
   three pumped occurrences produced `h0,commit0,h1,commit1,h2,commit2`
   — one continuation, one atomic batch, with no scheduler of kaya's own.
   This was the biggest risk to the ruling and it is clear. (§1.6)
4. **ES modules are unreachable on iOS.** MEASURED: `JSScript.h` is
   absent from the shipped SDK, `evaluateJSScript:` is SPI, `import`
   statements are a SyntaxError and `import()` rejects. One classic
   script per guest, so a bundler is forced on iOS regardless of
   TypeScript. (§1.4)
5. **The typed-array `byteOffset` trap.** MEASURED: N-API adjusts the
   data pointer by `byte_offset`; JSC's `JSObjectGetTypedArrayBytesPtr`
   does **not**. A faithful port of `node.rs` compiles, runs, and submits
   the wrong bytes for every `subarray` — and `wire.ts` uses `subarray`.
   This belongs in docs/traps.md whether or not the port is built. (§1.2)
6. **The binding is already 95% engine-neutral.** `wire.ts` and
   `index.ts` (4,724 of 4,992 lines) import nothing from node; the node
   dependence is one 268-line file and one 618-line Rust file, and the
   engine contract is already a written TypeScript type — `Floor`, 17
   methods. 38 of 42 guests import only `kaya-gui`. (§0, §3.1)
7. **Android ships no embeddable system JS engine, so it costs bytes.**
   QuickJS-ng, **built for arm64 with this repo's own NDK**, is **762 KiB
   stripped / 379 kB in-APK** — 2.7× smaller than Hermes, 13× smaller
   than a two-year-stale jsc-android. kaya already accepts ~26 MB of
   CPython on that platform; this is 1/34th of it. (§2.1)
8. **esbuild, verified present.** MEASURED at kaya's own pinned nixpkgs
   rev (`391b592e`): `esbuild` is **0.27.2** there. All 42 guests bundle
   to **1.8 MB total, 52 kB each, in 0.13 s**. (§4.2)

**The one recommendation to act on first**, if only one is taken: build
the iOS bridge as a **single-threaded occurrence loop on the app thread,
with no pump thread**, and put a guard on it. Finding 2 is measured, it
is the opposite of what porting `node.rs` faithfully would produce, and
getting it wrong corrupts transactions silently rather than loudly.

## §0 What the binding actually depends on today (read from the tree)

This is the baseline the rest of the report is measured against. Read
from `docs/js-plan.md`, `bindings/js/kaya/{index,runtime,wire}.ts`,
`crates/kaya/src/node.rs`, `bindings/js/{tsconfig,package}.json` and
`guests/js/*.ts`.

| `bindings/js/kaya/index.ts` (the sugar) | 3,412 | **No node import.** Uses `Proxy`, `Promise`, `queueMicrotask`, `setImmediate`, `TextEncoder` |

Twenty-four functions, and only three of them (the threadsafe-function

it is small enough that a second implementation on another engine is a
day's work per engine, not a subsystem.

### Non-ECMA-262 globals the neutral layers assume

These are **not** in the ECMAScript standard and are **not** in a bare
`JSGlobalContextCreate` or a bare QuickJS runtime. They come from node
or from a browser, and each one is a thing the mobile bootstrap must
provide:

- `TextEncoder` / `TextDecoder` — WHATWG Encoding, not ECMA-262
  (<https://encoding.spec.whatwg.org/#api>). Used in `wire.ts:274-275`
  and `index.ts:1502`. `TextDecoder("utf-8", {fatal: true})` — the
  fatal flag matters, it is how a malformed string is refused.
- `queueMicrotask` — WHATWG HTML, not ECMA-262
  (<https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#microtask-queuing>).
  `index.ts:133` — **this is the implicit-transaction mechanism**
  (docs/js-plan.md §4 ruling 1). It can be written as
  `Promise.resolve().then(fn)`, which IS ECMA-262, so this one is a
  three-line shim rather than a hole.
- `setImmediate` — **node-only**, not standardised anywhere; the
  WHATWG rejected it
  (<https://developer.mozilla.org/en-US/docs/Web/API/Window/setImmediate>).
  `index.ts:3250` — the idle drain of `app.post`ed work. On another
  engine this needs the host loop to call back, which is exactly the
  occurrence-loop question (§3).
- `Promise`, `Proxy`, `DataView`, `BigInt`, `Atomics`, `SharedArrayBuffer`
  are all ECMA-262 and present in every engine considered here, with
  the SAB caveat noted per engine in §2.

### The guests

42 guests under `guests/js/`. Of these, **four** touch node:
`clipboard.ts`, `filedialog.ts`, `save.ts` import `node:fs`, `node:os`,
`node:path` (they write scratch files into `tmpdir()`), and `stall.ts`
uses `Atomics.wait` on a `SharedArrayBuffer` as its blocking sleep
("JS has no sleep" — the comment in the file). The other 38 import only
`kaya-gui`. That ratio is the single most encouraging number in this
report: **90% of the guests are already engine-neutral source.**

### The type-stripping premise

`guests/js/*.ts` are TypeScript run **directly** by node 24; the
tsconfig sets `erasableSyntaxOnly` so every source stays inside what
node's stripper can erase, and there is no build step and no artifact
to go stale (docs/js-plan.md §1). `package.json` sets
`"exports": {".": "./kaya/index.ts"}` — the package's entry point is a
`.ts` FILE. Neither JavaScriptCore nor QuickJS nor Hermes strips
TypeScript, so this premise is the thing §4 has to replace.

## §1 JavaScriptCore on iOS

Sources are cited inline. **Where a claim is marked MEASURED it was run on
this machine** against the shipped `JavaScriptCore.framework` (macOS 26.5
SDK, Xcode 26.6.0). The eight probe sources are kept beside this report in
`jsc-probes/` so any claim can be re-run: `cc -o p p.c -framework
JavaScriptCore && ./p`. Nothing here is inferred from documentation alone
where it could be run instead.

### 1.1 What is actually public

`JavaScriptCore.framework` is a public framework on iOS since iOS 7
(`JSContext` is `NS_CLASS_AVAILABLE(10_9, 7_0)` in
<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSContext.h>).
Two APIs ship in it:

- **The Objective-C API** — `JSContext`, `JSValue`, `JSVirtualMachine`,
  `JSManagedValue`, `JSExport`. Usable from Swift directly.
- **The C API** — `JSGlobalContextRef`, `JSValueRef`, `JSObjectRef`,
  `JSStringRef`, and the typed-array header `JSTypedArray.h`.

**MEASURED — the exact public header set in the shipped iOS 26.5 SDK**
(`.../Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS26.5.sdk/System/Library/Frameworks/JavaScriptCore.framework/Headers/`):

    JSBase.h  JSContext.h  JSContextRef.h  JSExport.h  JSManagedValue.h
    JSObjectRef.h  JSStringRef.h  JSStringRefCF.h  JSTypedArray.h
    JSValue.h  JSValueRef.h  JSVirtualMachine.h  JavaScript.h
    JavaScriptCore.h  WebKitAvailability.h

`JSTypedArray.h` **is** public on iOS. `JSScript.h` **is not** — see 1.4.

### 1.2 What a native "addon" looks like on JSC vs N-API

The mapping is close to one-for-one, and every N-API call kaya uses has a
JSC counterpart. All JSC signatures below are quoted from the WebKit
headers (<https://github.com/WebKit/WebKit/tree/main/Source/JavaScriptCore/API>).

| kaya's N-API call | JSC C API equivalent | Availability |
|---|---|---|
| `napi_create_function` | `JSObjectMakeFunctionWithCallback(ctx, name, cb)` | since iOS 7 |
| `napi_set_named_property` | `JSObjectSetProperty(ctx, obj, JSStringRef, val, attrs, exc)` | since iOS 7 |
| `napi_get_cb_info` | the callback's own `(ctx, function, thisObject, argc, argv[], exception)` parameters | since iOS 7 |
| `napi_throw_error` | write a `JSValueRef` through the callback's `exception` out-parameter | since iOS 7 |
| `napi_get_value_double` | `JSValueToNumber` | since iOS 7 |
| `napi_get_value_string_utf8` | `JSValueToStringCopy` + `JSStringGetUTF8CString` | since iOS 7 |
| `napi_get_typedarray_info` | `JSObjectGetTypedArrayBytesPtr` + `…ByteLength` + **`…ByteOffset`** | `JSC_API_AVAILABLE(macos(10.12), ios(10.0))` |
| `napi_create_arraybuffer` / `napi_create_typedarray` | `JSObjectMakeTypedArray(ctx, kJSTypedArrayTypeUint8Array, len, exc)` then memcpy into `JSObjectGetTypedArrayBytesPtr` | ios(10.0) |
| (no N-API equivalent used) | `JSObjectMakeTypedArrayWithBytesNoCopy(ctx, type, bytes, len, deallocator, ctx, exc)` — a **zero-copy** Uint8Array over native memory | ios(10.0) |
| `napi_create_object` | `JSObjectMake(ctx, NULL, NULL)` | since iOS 7 |
| `napi_get_null` / `undefined` / `boolean` | `JSValueMakeNull` / `MakeUndefined` / `MakeBoolean` | since iOS 7 |
| `napi_call_function` | `JSObjectCallAsFunction(ctx, fn, thisObj, argc, argv, exc)` | since iOS 7 |
| `napi_get_and_clear_last_exception` | the `exception` out-parameter every call already takes | since iOS 7 |
| `napi_coerce_to_string` | `JSValueToStringCopy` | since iOS 7 |
| `napi_create_bigint_uint64` | `JSBigIntCreateWithUInt64(ctx, u64, exc)` — **`API_AVAILABLE(macos(15.0), ios(18.0))`** | **ios(18.0)** |
| `napi_create_threadsafe_function` trio | **no equivalent, and none needed** — see 1.5 | — |

Two entries in that table are the whole story of the port.

**(a) The BigInt deployment floor.** `wire.ts` reads the spec hash as a
`bigint` (`SPEC_HASH = 0x2d485dd5237b14c3n`, and `runtime.ts` compares
`lib.specHash() !== wire.SPEC_HASH`). **MEASURED against the shipped iOS
26.5 SDK:** the C API *does* have BigInt —
`JSBigIntCreateWithUInt64`, `JSBigIntCreateWithInt64`,
`JSBigIntCreateWithDouble`, `JSValueIsBigInt` and `kJSTypeBigInt` are all
declared in `JSValueRef.h` — but every one of them carries
`API_AVAILABLE(macos(15.0), ios(18.0))`. So it is not a hole, it is a
**deployment-target floor**: using it sets kaya's iOS minimum at 18.0.
The fix is trivial and costs nothing: hand the hash across as two
`number` halves, or as a hex string, and compare that, which keeps the
floor wherever the rest of the port puts it. It is worth naming because
it is the one N-API call whose JSC counterpart is not available at
iOS 10.

**(b) THE TYPED-ARRAY OFFSET TRAP — MEASURED, and it silently corrupts
data.** N-API's `napi_get_typedarray_info` returns a `data` pointer that
is *already adjusted*: the node docs say "data: The data buffer
underlying the `TypedArray` adjusted by the `byte_offset` value so that
it points to the first element in the `TypedArray`"
(<https://nodejs.org/api/n-api.html#napi_get_typedarray_info>).
**JSC's `JSObjectGetTypedArrayBytesPtr` does not adjust.** Measured:

    a = new Uint8Array([0,1,2,3,4,5]); s = a.subarray(2,5)   // s is 2,3,4
    JSObjectGetTypedArrayBytesPtr(s) -> reads 0,1,2
    JSObjectGetTypedArrayByteLength(s) -> 3     (the VIEW's length)
    JSObjectGetTypedArrayByteOffset(s) -> 2     (must be added by hand)

The header's own wording is the hint — "a pointer to the raw data buffer
that serves as object's **backing store**"
(<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSTypedArray.h>).
A port of `node.rs` that transliterates `napi_get_typedarray_info` into
`bytesPtr + byteLength` **compiles, runs, and submits the wrong bytes**
for every `subarray`. `wire.ts` uses `subarray` and constructs views with
`byteOffset` (`new DataView(buf.buffer, buf.byteOffset, buf.byteLength)`
appears four times in `wire.ts`), so this would fire. It is exactly the
`check-file-modes` shape: a number that means one thing on one side and
another on the other, with no compiler between them.

The same header warns: "The pointer returned by this function is
temporary and is not guaranteed to remain valid across JavaScriptCore API
calls." So the bytes must be copied out before any other JSC call —
which is what `node.rs` already does (§2 of docs/js-plan.md: "Bytes cross
as `Uint8Array` copies both ways").

**JSExport** (<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSExport.h>)
lets an ObjC/Swift *class* be exposed wholesale to JS through a protocol.
It is the wrong tool here: it marshals ObjC types, has no typed-array
support (see 1.3), and kaya's floor is 18 free functions. The C API is
the right layer, and it is also the layer `node.rs` is already written
against, so the Rust code shape carries over.

### 1.3 The Objective-C API cannot carry bytes

**MEASURED** by grepping the shipped `JSValue.h` (824 lines, 18
`JSC_API_AVAILABLE` macros): there is **no** typed-array method on
`JSValue` — no `typedArrayBytes`, no `valueWithNewTypedArray…`, nothing
matching `Typed`, `Buffer` or `Uint8`. Typed arrays exist only in the C
API's `JSTypedArray.h`.

That settles a design question before it is asked: a Swift-only bridge
built on `JSContext`/`JSValue` cannot move a `Uint8Array` in or out. The
bridge must drop to the C API, via `JSValue.jsValueRef` and
`JSContext.jsGlobalContextRef` (declared as
`@property (readonly) JSValueRef JSValueRef` in `JSValue.h` and
`@property (readonly) JSGlobalContextRef JSGlobalContextRef` in
`JSContext.h`). Since kaya's addon is already Rust talking to a C ABI,
the clean shape is: **a `jsc.rs` beside crates/kaya/src/node.rs, written
against the same C API, with no Swift in the path at all.**

### 1.4 Module loading — ES modules are unreachable

**MEASURED:** `JSScript.h`, which declares `kJSScriptTypeModule`
(`JSC_CLASS_AVAILABLE(macos(10.15), ios(13.0))`,
<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSScript.h>),
**is not in the shipped SDK's `JavaScriptCore.framework/Headers/`** and
is **not** `#include`d by the umbrella header `JavaScriptCore.h`
(<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JavaScriptCore.h>,
which includes only `JavaScript.h`, `JSStringRefCF.h`, `JSContext.h`,
`JSValue.h`, `JSManagedValue.h`, `JSVirtualMachine.h`, `JSExport.h`).

And the methods that would *run* a module script live in
**`JSContextPrivate.h`** — SPI, not API:
`- (JSValue *)evaluateJSScript:(JSScript *)script`,
`@property id <JSModuleLoaderDelegate> moduleLoaderDelegate`, and
`- (JSValue *)dependencyIdentifiersForModuleJSScript:` are all declared
there
(<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSContextPrivate.h>).
`JSContext.h` mentions `JSScript` only in a forward `@class` declaration.

**MEASURED confirmation, both directions:**

- `import * as x from "y";` inside `JSEvaluateScript` → **`SyntaxError`**
  (a classic script, by definition).
- `import('./x.js')` **parses and returns a Promise**, which then
  **rejects**: `Referrering script's url is not valid:` — the module
  loader has no host hooks wired up, so dynamic import is inert.

So the only supported way to run code is
`JSEvaluateScript` / `-[JSContext evaluateScript:]`, one classic script
at a time
(<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSBase.h>).
Multi-file JS on iOS therefore means one of:

1. **Concatenate at build time into one classic script** (esbuild
   `--bundle --format=iife`). This is what React Native does — Metro
   produces one bundle and JSC evaluates it.
2. **Evaluate each file separately and wire them by hand** — define a
   tiny `require` in JS over a native "read this file" function, with
   each module's source evaluated inside a function wrapper. This is a
   ~40-line CommonJS loader and is what most JSC embedders did before
   bundlers.
3. Ship an engine that *does* have a module loader (QuickJS's
   `JS_SetModuleLoaderFunc`) — but that is not JSC, and the ruling names
   JSC.

Given kaya has exactly two neutral files (`wire.ts`, `index.ts`) plus one
guest, option 1 costs one esbuild invocation per guest and option 2 costs
one small file. Both are cheap; option 1 is cheaper to *verify*.

### 1.5 Threading — the part that changes the architecture

The class comment on `JSVirtualMachine` is the whole documented rule:
"An instance of JSVirtualMachine represents a single JavaScript 'object
space' or set of execution resources. **Thread safety is supported by
locking the virtual machine, with concurrent JavaScript execution
supported by allocating separate instances of JSVirtualMachine.**"
(<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSVirtualMachine.h>)

That sentence is usually read as "JSC is thread-confined like CoreData"
— the Cash App engineering blog reaches exactly that conclusion and
advises "confine JSC objects to a specific thread"
(<https://code.cash.app/a-multithreading-saga-part-2>, Nick Entin,
2020-07-14). **That reading is wrong, and it matters, so it was
measured.**

**MEASURED — three findings:**

1. **A JSContext created on one thread is usable from another.** A
   context was created on the main thread, then driven entirely from a
   background `pthread` (natives installed, scripts evaluated, typed
   arrays passed) while the main thread slept; then from a *second*
   background thread; then from the main thread again. Every step
   succeeded and state written on one thread was read on the next. There
   is no thread confinement.

2. **JS execution is serialised by the VM's lock.** Four threads each
   running the same 60M-iteration loop in **one** JSContext: 1 thread
   299 ms, 4 threads 1171 ms — a ratio of **3.92**. They take turns.
   (Repeated: 298 ms / 1175 ms, ratio 3.94.) So no JS data races.

3. **THE LOCK IS DROPPED AROUND A NATIVE CALLBACK.** Four threads each
   calling a native function that `usleep`s 20 ms: 1 thread 22 ms,
   4 threads **29 ms**, ratio **1.29** — not 4×. While one thread blocks
   inside a native function, other threads enter JS.

Finding 3 is the one that changes kaya's design, because it breaks the
premise the JS binding's ruled semantics rest on. docs/js-plan.md §4
ruling 1 says "**The app thread is one thread**, so a mutation with no
transaction open opens one, and a microtask commits it when the current
continuation runs out: ONE CONTINUATION IS ONE ATOMIC BATCH." Node
guarantees that structurally — a worker has one JS thread and a native
call blocks it entirely. **JSC does not.**

**MEASURED, the hazard reproduced directly:** an "app thread" ran
`order.push('app:enter'); blocking(); order.push('app:leave')` where
`blocking()` is a native function that sleeps 120 ms — kaya's
`PickedFile.read()` shape. A "pump thread" called a JS handler 30 ms in.
The result:

    order => app:enter | pump:handler | app:leave

A handler ran **inside** another handler's continuation. On node that
cannot happen. On JSC it happens by default, and it would interleave two
implicit transactions, mis-own a row handle (docs/js-plan.md §4 ruling 3:
"the owner is the innermost For open at the handler's registration"), and
corrupt `_drainPosted`.

**The remedy is a simplification, not a workaround.** The node pump
exists only because node's event loop owns the worker's JS thread, so
kaya cannot block there. On JSC, **kaya owns the thread outright** — the
guest is not inside anyone's event loop. So the app thread runs the
occurrence loop itself:

    for (;;) { let rec = kaya_next_occurrence(); if (rec.is_null()) break;
               JSObjectCallAsFunction(ctx, handler, ...); }

One thread, one entry point, no threadsafe function, no condvar, and the
stall watchdog stays honest for the same reason it does on node — a
wedged handler never returns, so the next occurrence is never claimed.
The three `napi_*_threadsafe_function` calls have no JSC counterpart and
**need none**.

### 1.6 Microtasks — the implicit transaction survives, exactly

This was the highest-risk question, since the whole implicit-transaction
ruling is a microtask. WebKit bug 146828, "Integrate automatic microtask
draining into JSC framework and re-enable Promise", landed 2015-07-17 in
r186966: microtasks are drained "when the apilock depth becomes 0", i.e.
on the way out of a C/ObjC API call
(<https://bugs.webkit.org/show_bug.cgi?id=146828>).

**MEASURED — it behaves exactly as kaya needs.** Driving three
occurrences from a native thread into a handler that pushes a marker and
queues a microtask:

    handler = (u8) => { order.push('h'+u8[0]);
                        Promise.resolve().then(() => order.push('commit'+u8[0])); }

    order => h0,commit0,h1,commit1,h2,commit2

**Each occurrence's microtask ran before the next occurrence was
delivered.** That is "one continuation is one atomic batch" preserved
byte for byte, with no scheduler of kaya's own. `await` also resumes
across the boundary: `(async()=>{log.push('a'); await null;
log.push('b')})()` left `log` as `a` inside the call and `a,b` by the
next one.

### 1.7 What is MISSING from a bare JSContext — MEASURED

Every one of these evaluated to `undefined` in a fresh
`JSGlobalContextCreate(NULL)`:

| Global | Present? | Used by kaya | Cost to fix |
|---|---|---|---|

| `TextDecoder` | **undefined** | `wire.ts:275`, with `{fatal:true}` | ~60 lines of JS (the fatal flag is the work), or native |
| `queueMicrotask` | **undefined** | `index.ts:133` — **the implicit commit** | one line: `Promise.resolve().then(fn)` |
| `setTimeout` / `setInterval` | **undefined** | not used by binding or guests | none needed |
| `setImmediate` | **undefined** | `index.ts:3250` — the idle `app.post` drain | must be re-expressed on the occurrence loop |
| `structuredClone` | **undefined** | not used | none |
| `SharedArrayBuffer` | **undefined** | `runtime.ts` (the ready flag), `guests/js/stall.ts` | both are node-shaped; neither is needed on JSC |
| `Atomics` | **object**, but `Atomics.wait` throws | `stall.ts` | see below |
| `console` | **object** — but see below | `index.ts` (4 sites) | must be installed |
| `Proxy`, `Promise`, `DataView`, `BigInt`, `WeakRef`, `FinalizationRegistry` | **all present** | row handles, dialogs, wire | none |
| ES2022 `Array.prototype.at`, ES2024 `Object.groupBy` | present | — | the language level is current |

Two of those deserve their own note.

- **`Atomics.wait` cannot work.** `SharedArrayBuffer` is absent, and the
  measured error is exact: `TypeError: Typed array for
  wait/waitAsync/notify must wrap a SharedArrayBuffer.` So
  `guests/js/stall.ts`'s blocking sleep — "JS has no sleep: Atomics.wait
  on a word nobody notifies is the blocking primitive" — does not port.
  A native `kayaSleep(ms)` on the floor is the answer, and it is
  arguably the better spelling anyway since it is the same on every
  engine.
- **`console.log` exists and prints NOWHERE.** Measured: `typeof
  console.log === "function"`, and calling it produced no output on
  stdout or stderr. JSC's console routes to the Web Inspector. Since
  kaya's harness verdicts are the thing every lane greps for, the iOS
  bootstrap must install its own `console` over the native side's
  `writeSync`-equivalent. This is the same class as
  docs/js-plan.md §3's re-pointing of the worker's stdio, and for the
  same reason: **a verdict nobody can read is a lane that cannot fail.**

### 1.8 TypeScript, and the JIT

JSC does not strip TypeScript — there is no such API, and the language
level measured above is plain ECMAScript. §4 covers the options.

**The JIT.** Third-party iOS apps do not get the `dynamic-codesigning`
entitlement, so JavaScriptCore in an app process runs without its JIT;
Apple grants that entitlement only to system processes
(<https://saagarjha.com/blog/2020/02/23/jailed-just-in-time-compilation-on-ios/>,
and the WebKit engineer's summary at
<https://news.ycombinator.com/item?id=40726948>). A `WKWebView` gets JIT
because its JS runs out-of-process in a WebKit content process with the
entitlement; an in-process `JSContext` does not.

**Honest limit of what was measured here:** setting `JSC_useJIT=false`
was accepted by JSC's option parser (`JSC_dumpOptions=1` reported
`useJIT=false (default: true)`) but changed a 50M-iteration arithmetic
loop only from 349 ms to 373 ms and a typed-array loop from 333 ms to
343 ms. A real interpreter-only run would be several times slower, so
either the shipped framework does not honour the option or those loops
are memory-bound. **I could not tell those two causes apart on this
host, so no iOS performance number is claimed here.** The honest
statement is: the citations say iOS gets no JIT, and the size of that
penalty for kaya's workload is unmeasured. It is measurable — the iOS
lane could run the packing loop on a simulator and on the mac and print
both.

### 1.8b The run-loop caveat, and what it does NOT break

`JSContextRef.h` in the shipped SDK carries a warning worth reading
before designing the thread:

> "A JSContextGroup may need to run deferred tasks on a run loop, such as
> garbage collection or resolving WebAssembly compilations. By default, a
> JSContextGroup will use the run loop of the thread it was called on.
> **Currently, there is no API to change a JSContextGroup's run loop once
> it has been created.**"

(`JSVirtualMachine.h` says the same for the ObjC class.) kaya's app
thread on iOS is a plain worker thread with no `CFRunLoopRun` on it, so
the question is whether a VM created there is starved of its deferred
tasks.

**MEASURED: ordinary collection is fine.** Four million short-lived
objects allocated from a JSContext created on a run-loop-less pthread
moved RSS from **9.6 MB to 21.2 MB** — +11.6 MB, i.e. collected. GC runs
on the allocating thread; the run loop is for *deferred* work.

The honest residue: the header names **WebAssembly compilation** as the
other deferred task, and kaya uses no WebAssembly. So the caveat is real,
documented, and not load-bearing for this design — but the context must
be **created on the thread that will drive it**, which is a one-line
constraint worth writing into the bridge rather than discovering later.

### 1.9 Debugging

`JSGlobalContextSetInspectable` / `JSGlobalContextIsInspectable` are
public C API, `JSC_API_AVAILABLE(macos(13.3), ios(16.4))`, and
`JSContext.inspectable` is the ObjC spelling with the same availability
(<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSContextRef.h>,
<https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/API/JSContext.h>).
**MEASURED: the default is `false`** — a fresh context reported
`JSGlobalContextIsInspectable == false`. Since iOS 16.4 / macOS 13.4 an
app must opt in explicitly, even in debug builds
(<https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/>).
Once set, the context appears in Safari's Develop menu; on a device the
user must also enable Settings → Safari → Advanced → Web Inspector
(same source). React Native hit this exact change
(<https://github.com/facebook/react-native/issues/39488>).

For kaya: setting `inspectable = true` under the same condition that
already turns on the harness would give the iOS JS lane a real debugger,
which no other kaya binding has on a phone.

### What this means for kaya

The iOS port is smaller than it looks, and it is a *simplification* in
two places.

- **The native side is a sibling file, not a subsystem.** All 24 N-API
  calls have JSC equivalents at iOS 10 or earlier, except the BigInt
  spec-hash (iOS 18, ObjC-only — hand the hash over as two numbers
  instead) and the threadsafe-function trio, which JSC does not need.
  a `jsc.rs` beside crates/kaya/src/node.rs, same C-ABI Rust, no Swift.
- **The threading model gets simpler, and MUST.** kaya owns the thread on
  iOS, so the app thread runs the occurrence loop directly: no pump
  thread, no condvar, no threadsafe function. This is not optional
  polish — the lock is **measured** to drop around native callbacks, and
  a pump thread would re-enter JS mid-handler (`app:enter |
  pump:handler | app:leave`), breaking the implicit-transaction ruling.
- **The implicit transaction survives untouched** — measured
  `h0,commit0,h1,commit1,h2,commit2`. This was the biggest risk to the
  ruled semantics and it is clear.
- **The bootstrap owes the context five globals**: `TextEncoder`,
  `TextDecoder`, `queueMicrotask` (one line over `Promise`), a `console`
  that actually writes, and a native `sleep` to replace `Atomics.wait`.
  `setImmediate` is re-expressed on the occurrence loop.
- **ES modules are out**, on measured evidence (`JSScript.h` absent from
  the SDK; `evaluateJSScript:` is SPI; `import()` rejects). One classic
  script per guest, produced by a bundler, or a hand-rolled `require`.
- **The one trap that would ship silently** is the typed-array
  `byteOffset`: N-API adjusts the pointer, JSC does not. That is a
  `check-file-modes`-shaped guard waiting to be written — the two
  addons' byte-reading arms held to the same contract, with a watched
  negative on a `subarray`.

## §2 Android engines — and the policy question that reframes the ruling

### 2.0 Is JavaScriptCore REQUIRED on iOS? No. VERIFIED against the current agreement.

This belongs at the top of §2 because it changes what §2 is for. The
folk rule — "Apple only lets you run JavaScript through
JavaScriptCore" — is a memory of an agreement clause that **no longer
exists**.

**App Store Review Guideline 2.5.2**, quoted verbatim from
<https://developer.apple.com/app-store/review/guidelines/>:

> **2.5.2** Apps should be self-contained in their bundles, and may not
> read or write data outside the designated container area, nor may they
> download, install, or execute code which introduces or changes
> features or functionality of the app, including other apps.
> Educational apps designed to teach, develop, or allow students to test
> executable code may, in limited circumstances, download code provided
> that such code is not used for other purposes. Such apps must make the
> source code provided by the app completely viewable and editable by
> the user.

Read it for what it regulates: **downloading, installing, or executing
code that *introduces or changes* the app's features.** Code that ships
inside the bundle is not downloaded, is not installed, and does not
*change* the app's functionality — it *is* the app's functionality. And
2.5.2 does not name an interpreter at all.

The binding document is the **Apple Developer Program License
Agreement**, §3.3.1(B) "Executable Code". **MEASURED — the current
English PDF was downloaded and text-extracted on 2026-09-02** from
<https://developer.apple.com/support/downloads/terms/apple-developer-program/Apple-Developer-Program-License-Agreement-English.pdf>
(copy kept beside this report as `apple-pla-2026.pdf`, clause excerpt as
`apple-pla-3.3.1B.txt`). It reads, verbatim:

> Except as set forth in the next paragraph, an Application may not
> download or install executable code. Interpreted code may be
> downloaded to an Application but only so long as such code: (a) does
> not change the primary purpose of the Application by providing
> features or functionality that are inconsistent with the intended and
> advertised purpose of the Application (b) does not bypass signing,
> sandbox, or other security features of the OS; and (c) for
> Applications distributed on the App Store, does not create a store or
> storefront for other Applications.

**MEASURED: the strings "JavaScriptCore" and "WebKit" appear ZERO times
in the entire agreement** (`grep -c -i` over the extracted text of all
7,235 lines: 0 and 0).

The history makes the reading airtight rather than merely plausible. In
the **2014** iOS PLA the same clause read "Interpreted code may **only**
be used in an Application if all scripts, code and interpreters are
packaged in the Application and not downloaded" — so **bundling your own
interpreter was explicitly permitted even under the strictest wording
Apple ever published**, and the WebKit/JavaScriptCore exception applied
to *downloaded* code alone. Today's agreement has dropped the engine
restriction even for downloaded code.

That is the whole answer, in three parts:

1. **The old carve-out is gone.** The clause everyone remembers — "the
   only exception is scripts and code downloaded and run by Apple's
   built-in WebKit framework or JavaScriptCore" — is no longer in the
   agreement. The current text permits downloaded *interpreted* code
   subject to three conditions and names no engine.
2. **Bundled code is not even the regulated case.** The clause governs
   code that is *downloaded*. kaya's guests ship in the bundle.
3. **Therefore any interpreter may be embedded.** The evidence in
   practice is overwhelming and long-standing: React Native ships
   **Hermes**, a non-Apple JS engine, as its default iOS engine; Unity
   ships IL2CPP; countless games embed Lua; and kaya itself already
   ships **CPython** in its iOS bundle (docs/python-mobile-plan.md).
   kaya has already made this exact bet, on this exact platform, with a
   much larger interpreter. On QuickJS specifically, **Cash App's Zipline
   and WebF both ship it on iOS.**

**What this means for the ruling.** "On iOS it must run under
JavaScriptCore" is a *good engineering choice*, not a policy
requirement, and the maintainer should know which it is before deciding
Android. JSC on iOS is still very attractive on its merits — it is a
system framework, so it costs **zero bytes** in the bundle (against
CPython's ~20 MB), it is maintained and security-patched by Apple, and
it is the only engine that gets Safari Web Inspector debugging for free
(§1.9). But it is a *choice*, and it is the choice that forces two
engines (JSC on iOS, something else on Android) instead of one. §2's
engine survey and the "decisions" section below both hinge on that, so
it is stated first.

### 2.1 The engines, with sizes built and measured for Android arm64

beside this file. Sizes marked **[built]** were produced by compiling the

### 2.2 The three that are real

**QuickJS-ng** is the smallest by a wide margin — **762 KiB against
Hermes's 2.04 MiB and jsc-android's 9.70 MiB** — is the only one of the
three with a **real ES module loader** (`JS_SetModuleLoaderFunc`), is
ES2025-class so no downleveling is needed, builds for iOS and Android
from the same plain-C tree with no configuration, and has a live,
first-class Rust binding: **rquickjs** (MIT, crates.io 0.12.2 published
2026-07-27, pushed the day of this research), which its README says binds
**QuickJS-ng** specifically. For a Rust core that is the obvious route.
Its two real weaknesses: **no `Intl`** ("unlikely QuickJS will ever
support the Intl APIs"), and **no upstream debugger** — issue #119 open
since 2023-11-22, the working art out of tree with a custom TCP protocol
rather than the Chrome DevTools Protocol.

**Hermes** brings the single most interesting fact in the survey for
kaya: **`API/napi/` — a full Node-API v10 implementation**, whose README
says it "allows native addons written against the Node-API ABI to run on
Hermes without modification… covering all non-experimental APIs through
NAPI_VERSION 10", with a compatibility matrix that includes typed
arrays, promises, BigInt, finalizers, **thread-safe functions** and async
work. That is kaya's exact 24-function surface, for free. **The
caveat is dated and sharp**: its first commit is **2026-05-12**, it has
12 commits, it lives on the `static_h` dev branch only, and it is **not
in the stable branch** and has never shipped in a Hermes release or any
React Native version. Four months old. Hermes's other costs: it targets
**ES6** (§4.1 — `async` must be downleveled), has no runtime `import`,
and has no vendor-published standalone Android AAR or iOS xcframework
that is not React Native's, so kaya would either drag an RN-shaped
artifact in or run the two-stage build itself for four ABIs plus Apple.
Its one clear win over QuickJS is debugging: Hermes ships a real Chrome
DevTools Protocol implementation (`API/hermes/cdp/`).

**jsc-android** is the way to have *literally the same engine* on both
phones, which is the tidiest possible answer to "one JS
implementation". But it costs **9.70 MiB per ABI** (**19.17 MiB with
`Intl`** — measured, and notably worse than its own README's "about 6MiB
larger") — 13× QuickJS — and it is the least maintained thing in the
table: the last Maven publish was **2024-11-29** and the npm package's
last publish was **2023-02-05**. It is a community build out of a WebKit
branch, not a vendor artifact. Paying 13× the size for a two-year-stale
build of an engine, to get uniformity that a 24-function abstraction
already gives you, is a bad trade.

### What this means for kaya

**Android ships no embeddable system JS engine.** That is the structural
fact and it is the asymmetry with iOS: on iOS the engine is free (a
system framework, zero bytes, Apple-maintained); on Android every option
costs binary size and a maintenance relationship. So the two phones will
not have the same engine unless kaya pays 9.70 MiB for a stale
jsc-android — and it should not, because §3 shows the abstraction that
makes the engine interchangeable is 24 functions wide and mostly already
written.

Against kaya's own precedent this is cheap. **kaya already ships CPython
in both mobile bundles — ~20 MB on iOS and ~26 MB on Android**
(docs/python-mobile-plan.md §0). QuickJS-ng at 762 KiB is **1/34th** of
what kaya has already accepted for Python, on the same platform, for the
same reason. The size objection to JS on mobile does not survive contact
with what this project already does.

**The recommendation is QuickJS-ng on Android**, on four grounds that are
each independently sufficient: it is the smallest by 2.7×, it is the only
one with a module loader (so the bundling in §4 becomes optional rather
than forced), it is ES2025 so `async` needs no downleveling, and
rquickjs gives a Rust core a maintained binding. Hermes's Node-API is the
one thing that could change this answer — if it reaches a stable release
and ships in React Native, it becomes "kaya's existing addon runs
unmodified on Android", which is worth a great deal. **Today it is four
months old and on a dev branch, so it is a thing to watch, not a thing to
build on.**

## §3 The engine-neutral design

3.1-3.4 and 3.8 are the measurement of kaya's own tree, because the
answer turns out to be mostly already built. 3.5-3.7 are the survey of
how other projects solved the same problem.

### 3.1 The seam already exists and is already typed

`bindings/js/kaya/runtime.ts` opens with

    type Floor = {
      specHash(); capabilities(); run(); submit(records);
      blobRegister(bytes); occurrenceBlob(handle);
      assetOpen(name); assetBytes(h); assetLen(h); assetBlob(h);
      assetRelease(h); assetWhyNot(name);
      openPicked(h, mode); pickedRead(h); pickedWrite(h, bytes);
      startPump(cb); exit(code);
    };

**Seventeen methods. That is the entire engine contract**, and it is
already written down as a TypeScript type. Today it is satisfied by
`process.dlopen`; on another engine it is satisfied by an object the
host installs on `globalThis` before evaluating anything. Nothing above
it needs to know which.

Measured from the tree, `index.ts` (3,412 lines, the whole sugar tier)
reaches `runtime` through nineteen names, and only **four** of them are
engine-shaped:

| `runtime.*` name | uses in index.ts | engine-neutral? |
|---|---|---|
| `describe` | 22 | yes — pure JS |
| `registerBlob`, `submit` | 8 | yes — wrappers over Floor |
| asset calls (5), picked calls (3), `capabilityBits`, `CAP_AUX_WINDOWS`, `assetMissSentence` | 11 | yes — wrappers over Floor |
| **`IS_APP_THREAD`** | 3 | **no** — `!isMainThread` from `node:worker_threads` |
| **`surrenderMainThread`** | 1 | **no** — spawns a Worker, enters `kaya_run` |
| **`signalReady`** | 1 | **no** — `Atomics.notify` on a `SharedArrayBuffer` |
| **`startPump`** | 1 | **no** — a napi threadsafe function |

So the refactor is mechanical and small:

- **`kaya/wire.ts`** — already neutral. Imports nothing. (One caveat:
  `TextEncoder`/`TextDecoder`, §1.7.)
- **`kaya/index.ts`** — already neutral. Two shims (`queueMicrotask`,
  `setImmediate`) and it compiles anywhere.
- **`kaya/runtime.ts`** — split. The neutral two thirds (the `Floor`
  wrappers, `describe`, the spec-hash check) stay; the node third
  (`findLibrary`, `loadLibrary`, `surrenderMainThread`, `signalReady`,
  `IS_APP_THREAD`, the stdio re-point, `startPump`) becomes
  **`kaya/host-node.ts`**, chosen at load.
- **`crates/kaya/src/node.rs`** — gains a sibling, `jsc.rs` (and, if
  Android needs one, `quickjs.rs`), each ~600 lines of the same
  shape against a different C API.

### 3.2 Where the bootstrap differs, precisely

| Concern | node (today) | JSC on iOS | an embedded engine on Android |
|---|---|---|---|
| Who owns the process main thread | `kaya_run`, entered by `surrenderMainThread` | **the host already does** — SwiftUI's `swiftui_host::run` (`crates/kaya/src/capi.rs`) | the Activity / Compose |
| Where the guest's code runs | a `worker_thread` spawned on `process.argv[1]` | a thread the host starts, which creates the JSContext and evaluates the bundle | the same |
| `IS_APP_THREAD` | `!isMainThread` | always true — there is only the one context | the same |
| How the guest is found | `process.argv[1]` | a resource in the app bundle, named by `KAYA_SELFTEST` the way every other kaya guest is | an APK asset |
| Reaching libkaya | `process.dlopen` on the dylib | **no load at all** — the core is statically linked into the app executable (docs/python-mobile-plan.md D3) and the bridge is compiled in beside it | `libkaya.so` is already in `jniLibs` for the JNI tier |
| The occurrence pump | native thread + napi threadsafe function + condvar | **the app thread's own loop** — §1.5 | the same |
| `app.run()` | signals ready, main thread enters `kaya_run` | **parks as the occurrence consumer** — exactly docs/python-mobile-plan.md D2 | the same |
| stdout | `writeSync(1, …)` over the worker's stdio | a native `console` — JSC's prints nowhere (§1.7) | a native `console` over `__android_log_write` |

The row that matters is `app.run()`, and it matters because **kaya has
already ruled it, twice.** docs/go-mobile-plan.md §D5 ruled it for Go
and docs/python-mobile-plan.md §D2 generalized it: "**A guest's spelling
is identical on all five platforms**: `portfolio.py` ends in the same
`run()` everywhere, with no platform knowledge and no second entry
point… on the hosted platforms the HOST owns the loop, the guest's code
is already running on the app thread the host started, and `run()` parks
there as the occurrence consumer until the core shuts down." JS inherits
that ruling unchanged. There is nothing new to decide about the entry
point; there is only the work of spelling the existing ruling in a third
language.

### 3.3 The occurrence loop, per engine

This is question 3's sharpest sub-question and the answer differs by
engine in a way that is worth stating plainly.

- **node** — the JS thread is node's event loop, which kaya may not
  block. Hence the native pump thread and the threadsafe function, with
  a condvar making it one-at-a-time so the stall watchdog stays honest
  (docs/js-plan.md §3).
- **JSC** — kaya owns the thread. The loop is a plain `for(;;)` in
  native code calling `JSObjectCallAsFunction` per occurrence.
  **MEASURED working** (§1.5), and **measured to preserve the implicit
  transaction** (§1.6). No pump thread, and per §1.5 a pump thread would
  be actively wrong.
- **A single-threaded embedded engine (QuickJS and kin)** — same shape
  as JSC, and forced rather than chosen, since those engines have no
  cross-thread entry at all.

So the pump is **node's special case, not the general one**. That is a
pleasant inversion of the usual expectation and it means the mobile
work does not add a mechanism; it removes one.

### 3.4 The four guests that do not port, and the honest cost

38 of 42 guests import only `kaya-gui` and are engine-neutral source
today. The four that are not:

- `guests/js/clipboard.ts`, `filedialog.ts`, `save.ts` — `node:fs`,
  `node:os`, `node:path`, to write a scratch file into `tmpdir()`.
  Every other binding's version of these guests does the same thing in
  its own standard library, so the question "what is the portable
  spelling of *write these bytes to a temp file*" is not new to JS —
  but JS is the one language whose standard library is empty. The
  answer is a small `kaya.tempFile(name, bytes)` on the floor, which is
  also what the iOS and Android sandboxes need anyway (an app's temp
  directory is not `/tmp`).
- `guests/js/stall.ts` — `Atomics.wait` on a `SharedArrayBuffer`,
  measured impossible on JSC (§1.7). A native `sleep` on the floor.

Both are floor additions, not spelling changes, so the guests stay one
file each, shared verbatim — which is invariant 6's requirement.

### 3.5 How other projects solved "one JS API, several engines"

Full notes with every URL in `multi-engine-precedents.md` beside this
file. Two or three sentences each, plus the one that changes the answer.

**Node-API itself, on engines that are not node — THE PRECEDENT.**
**Bun implements the whole of Node-API on JavaScriptCore.** Bun's docs:
"Bun implements Node-API from scratch, so most existing Node-API
extensions work with Bun out of the box"
(<https://bun.com/docs/runtime/node-api>), and Bun's engine is JSC, not
V8 (<https://github.com/oven-sh/bun/blob/main/LICENSE.md>). The code is
`src/jsc/bindings/napi.cpp` (3,469 lines) plus
`src/runtime/napi/napi_body.rs` (5,352 lines, carrying the entire
threadsafe-function machinery); its four public headers are **copied
byte-identically from `nodejs/node`** with three documented divergences,
it declares `DEFAULT_NAPI_VERSION = 10` (current node's level), and it
vendors and runs **Node's own Node-API test suite** including the
threadsafe-function tests. **All 24 functions kaya uses are
implemented.** Bun itself is **MIT**. There are three more independent
implementations: **Deno** (`deno_napi`, V8), **emnapi** (Node-API in
WASM/Emscripten, MIT), and — see below — **Hermes**.

**React Native's JSI** (`facebook::jsi::Runtime`) is a C++ virtual
interface — `jsi::Value`, `Object`, `Function`, `HostObject`,
`HostFunction`, `ArrayBuffer` — with an engine plugged in behind it
(`JSCRuntime`, `HermesRuntime`, react-native-v8's `V8Runtime`), and
`CallInvoker` as the "run this on the JS thread" hook. It is an
**unstable C++ ABI** and it is not something a Rust core wants to depend
on. The right use of it is as a **worked example**: `JSCRuntime.cpp`
(1,616 lines, MIT) is the best available answer to "build a complete JS
object model over Apple's public JavaScriptCore C API", already debugged
on real devices.

**NativeScript** runs two separate runtimes (V8 on Android, and V8 on
iOS since they left JSC) and achieves one JS API by generating metadata
from platform headers. Its two lessons are both negatives, and both
quantified: **32 duplicated filenames between the two runtimes** is what
"we will keep them in sync" looks like after a decade, and **forking an
engine cost them ~3 person-months per upgrade**, which is why they left
JSC. kaya's culture (check-mirror, check-symbol-parity, check-verbs)
exists because of exactly that first failure.

**Capacitor** puts the JS in a WebView and crosses to native as JSON
over a message handler (`WKScriptMessageHandler` on iOS,
`@JavascriptInterface` on Android). Everything is async and everything is
JSON — no native pointer, no typed array, no synchronous call. For a
binding whose whole contract is "pack wire records into byte buffers and
submit them", that is the wrong shape at the first step. **But
Capacitor's *other* runtime is the most useful corroboration in this
report:** `@capacitor/background-runner` is "an event-based standalone
JavaScript environment for executing your Javascript code outside of the
web view", and it uses **JavaScriptCore on iOS**
(`RunnerEngine/Context.swift` holds `public let jsContext: JSContext`
built from a `JSVirtualMachine`) and a **vendored QuickJS on Android**
(`packages/android-js-engine/.../cpp/js-engine/src/quickjs/`)
(<https://github.com/ionic-team/capacitor-background-runner>). A team
shipping to millions of devices, with no attachment to either engine,
independently arrived at exactly the split §5's D1 and D2 recommend.

And the reason the WebView projects can never do what kaya needs is
architectural, not a matter of effort: **`WKWebView` runs page JS in a
separate WebContent process** (<https://docs.webkit.org/Deep%20Dive/Architecture/WebKit2.html>),
Apple has never exposed a `JSContext` for it, and `evaluateJavaScript`
with a completion handler is the only route. That is why Capacitor's
return path is a string splice. Android is the same in practice.

**Tauri** is WebView-based too (WKWebView / WebView2 / WebKitGTK) with
IPC over a custom protocol, and its 2.x mobile support keeps that model
on iOS and Android. It never embeds a bare JS engine. Same disqualifier
as Capacitor for kaya's purposes.

**Tencent ScriptX** (Apache-2.0) is the closest thing to a general
answer nobody talks about: one C++ API over V8, JSC, QuickJS,
SpiderMonkey and more. Unstable C++ ABI, like JSI.

### 3.6 The blocking-receive question, answered across five codebases

The charge asks how each engine gets an event from a native thread into
the JS thread. The survey's finding is a single sentence and it is the
most useful structural fact in this report:

> **Every implementation uses the same algorithm, and the only
> per-engine part is one function: "run this closure on the JS thread".**

| project | engine | queue + back-pressure | the wake |
|---|---|---|---|
| Node.js | V8 | `node_api_threadsafe_function.cc` | `uv_async_send` |
| Bun | JSC | `Mutex` + `Condvar` + `LinearFifo` | `VmHandle::post` → `el.wakeup()` |
| Deno | V8 | `Mutex` + `Condvar` | `sender.spawn(…)` |
| **Hermes** | Hermes | `std::mutex` + `condition_variable` + `queue` | **`host->post_task(host->data, tsfn, dispatch)` — a host-supplied function pointer** |
| emnapi | wasm | `pthread_mutex_t` + `pthread_cond_t` | `emscripten_proxy_async` |

And per engine, "can a native thread call a JS function directly?":

- **JavaScriptCore — yes**, and it is the outlier. **MEASURED in §1.5**:
  a native thread called a JS handler three times while the app thread
  was elsewhere, and the microtask drained per call. So on iOS the
  queue-and-wake machinery is not needed at all.
- **Hermes / JSI — no.** The JS thread must be handed a closure.
- **V8 — no.** The isolate is thread-confined.
- **QuickJS — no.** Strictly single-threaded per runtime; there is no
  cross-thread entry.

### 3.7 The design this points to

Hermes has already generalised the whole problem into eight fields, and
**kaya needs one of them**. `hermes_napi_host`
(<https://github.com/facebook/hermes/blob/static_h/API/napi/hermes_napi.h>)
is a struct of eight function pointers, and its README says "Fields left
as nullptr preserve default behavior". The one kaya needs is:

    void (*post_task)(void* loop_data, void* task_data, void (*callback)(void*));

That is the entire host-integration surface for a threadsafe function.
`hermes_napi_tsfn.cpp` is 550 lines of portable C++ over that single
pointer — no libuv, no V8, no JSC.

So the shape the whole survey converges on, for kaya:

1. **Keep Node-API as kaya's one JS-facing C ABI.** It is the only JS
   embedding ABI with (a) a written engine-independence charter, (b)
   four independent implementations across three engines, (c) a stable
   **C** ABI promise, and (d) headers shipped standalone. Nothing else in
   the scoreboard has more than one of those. JSI has (b) but a C++ ABI;
   `hermes_abi` is Hermes-only and its own README says "not supported for
   general use".
2. **On the three desktops, change nothing.** Node provides the
   implementation.
3. **On the phones, kaya writes a small N-API *provider* over the host
   engine** rather than porting its addon to a new API. `libkaya` keeps
   exporting `napi_register_module_v1` and keeps calling the same 24
   symbols; today it finds them by `dlsym` out of the node host, and on a
   phone it links them out of its own provider instead. **That is a
   smaller change than kaya's current dlsym trick, not a bigger one.**
4. **Size it honestly.** ~18 of the 24 are one-liners against JSC's
   public C API. `napi_value` representation is the one real design
   decision — Bun's bit-cast trick needs JSC internals Apple does not
   expose, so the public-API answer is `napi_value == JSValueRef` with a
   handle scope over `JSValueProtect`/`JSValueUnprotect`. And per §1.5,
   **the three threadsafe-function entries can be unimplemented on iOS**,
   because kaya's app thread calls JS directly.

**The caveat that keeps this honest.** Bun proves N-API-on-JSC works and
gives a reference implementation, but Bun's is written against JSC
*internals* (`JSC::JSValue`, `JSC::VM`, `WTF::Vector`) which Apple's
shipped framework does not expose — Bun links its own WebKit. So kaya can
reuse Bun's **design and its threadsafe-function code shape** (MIT), and
must re-derive the value/handle layer against `JSValueRef`. That
re-derivation is what `JSCRuntime.cpp` is a worked example of.

**And one thing to watch rather than build on:** the React Native
ecosystem is itself moving JSI → Node-API. Hermes's `API/napi/` is a
first-party Node-API v10 implementation "built directly on Hermes VM
internals (not JSI)". If it stabilises, Android becomes "kaya's existing
addon runs unmodified", which would be the best outcome available. As of
2026-09-02 it is 12 commits old, dev-branch only, four months of age.

### 3.8 What a guard for this would look like

Following invariant 3, the failure classes this port introduces and the
wall each one wants:

1. **The typed-array `byteOffset` divergence** (§1.2b) — the one that
   ships silently. A gate that reads every addon's byte-reading arm and
   requires the offset to be added where the engine does not add it,
   with a watched negative that submits a `subarray` and reads the
   wrong bytes. Same shape as `tools/check-file-modes.py`: a number that
   means different things on two sides of a boundary, with no compiler
   between them.
2. **Re-entrancy on JSC** (§1.5) — a gate holding the JSC bridge to
   having exactly one thread that ever calls into the context, and no
   `JSObjectCallAsFunction` from any other. The runtime half is
   `check-empty-child`'s shape: compile the bridge's own source against
   a probe and watch the re-entrant order (`app:enter | pump:handler |
   app:leave`) being refused.
3. **The missing globals** (§1.7) — a census: every non-ECMA-262 global
   the neutral layers name must be installed by every bootstrap. This
   one is cheap and catches the next `structuredClone` someone reaches
   for.
4. **The floor's parity** — `Floor`'s seventeen methods, present in
   every host. TypeScript gives this one for free if each host is
   declared as satisfying the `Floor` type, which is a *type* over a
   *generation* over a *check* — invariant 3's own preference order.

### What this means for kaya

The port is a **split, not a rewrite**. `wire.ts` and `index.ts` — 95% of
the binding — already run on a foreign engine today (measured: an esbuild
bundle of `todos.ts` executes under QuickJS-ng and fails only at
`runtime.ts`'s `dlopen` line). What has to be written is: the node third
of `runtime.ts` moved into `host-node.ts`, a `host-jsc.ts`/`host-qjs.ts`
beside it, and a thin per-engine value layer under `node.rs`'s existing
logic. The engine contract is already a written type — `Floor`, 17
methods — and the *native* contract is 24 functions kaya already counts.

Three things the survey settles that would otherwise be re-litigated:
**do not adopt JSI** (unstable C++ ABI, node exposes none, and you supply
the engine anyway); **do not build a WebView bridge** (the engine is in
another process, so `evaluateJavaScript`-a-string is the ceiling); and
**do not write a pump thread for iOS** (§1.5 — it is measured to break
the implicit-transaction ruling). The one abstraction worth copying
verbatim is Hermes's `post_task`: one function pointer, "run this closure
on the JS thread", which is all five surveyed threadsafe-function
implementations reduced to their only per-engine part — and which iOS
does not even need.

## §4 TypeScript on mobile without node

Full working notes, with 55 source URLs and every measurement's command,
are in `ts-without-node.md` beside this file. This section is the
distillate.

### 4.1 The premise that has to go, and exactly why

Today node 24 strips the guests' types at load and there is no build
step. That is a **node feature**, and specifically it is *blanking*: node
replaces type syntax with whitespace and emits no new code, which is why
`erasableSyntaxOnly` exists to keep the sources inside what blanking can
do (<https://nodejs.org/api/typescript.html>). No other engine has it.
So on iOS and Android something has to produce runnable JS.

Two independent constraints decide the answer, and neither is about
types:

1. **JSC has no module loader at all** (§1.4, independently verified by
   the same method: `grep -rn "module"` over the shipped SDK's public JSC
   headers returns nothing). So a guest must arrive as **one script**
   whatever else is true. Bundling is not optional on iOS.
2. **If Android uses Hermes, the guests must be *downleveled*, not just
   stripped.** Hermes's own current feature document
   (<https://github.com/facebook/hermes/blob/main/doc/Features.md>, last
   edited 2026-07-27) says it targets **ES6**, lists `async`/`await` and
   ES modules under **"In Progress"**, and excludes "other features added
   to ECMAScript after ES6". kaya's `tsconfig.json` targets es2022, and
   **all four of the JS binding's ruled sugar shapes are built on
   `async`** — the implicit transaction commits on a microtask,
   `await app.commit()` ends a batch early, every dialog answers a
   promise, and `guests/js/todos.ts` opens with
   `async function onAdd(): Promise<void>`. A *blanker* can never lower a
   coroutine; only a compiler can.

Constraint 1 alone kills "no build step on iOS". Constraint 2 kills the
two remaining no-build options on Android **if** Android is Hermes — and
evaporates if Android is QuickJS-ng, which is ES2023-class and has a real
module loader. **So the Android engine choice and the TypeScript
question are the same question.**

### 4.2 The options, measured on kaya's real tree

One 10.5 MB static Go binary, offline. **All 42 guests → 1.8 MB total, 52 kB each, 0.13 s.** `--target=es2015` for Hermes lowers `async`→generators for **+4% bytes and no extra time** |

### 4.3 The finding that dates option (e)

**TypeScript 7.0 shipped 2026-07-08 as a Go binary and has no
programmatic API**
(<https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/>):
"TypeScript 7.0 does not yet ship with an API. We expect TypeScript 7.1
to ship with a new (and different) API." The npm package's unpacked size
fell from 23.6 MB to **2.50 MB** because the JavaScript compiler is gone.

`ts-blank-space` depends on the `typescript` package's **JavaScript**
parser (range `5.1.6 - 6.0.x`), and so does `ts.transpileModule`. So
option (e) means shipping a **frozen TypeScript 6 JS compiler inside
every mobile app bundle**, on a package line Microsoft has stopped
developing. That is a real, dated liability, not a hypothetical one.

### 4.4 Which option keeps "one guest file per scene, shared verbatim"?

The invariant (CLAUDE.md #6) is *"Scene scripts are shared verbatim"* and
in practice the JS guests have been held to the stronger reading: the
file on disk is the file that runs.

- **Strictly** — the `.ts` file *is* what the engine runs on all five
  platforms — only **(e)** and **(f)** qualify, and **both die on
  Hermes**, and **(e)** costs 1–2 s of phone startup per launch plus a
  frozen compiler.
- **In the sense kaya already lives by everywhere else** — the *source*
  is one unedited file shared by every platform, and what differs is a
  **derived artifact** — **(a)** qualifies, and the relationship is
  exactly the one kaya already has with `libkaya`, the SwiftUI
  interpreter and the Compose interpreter. `tools/build-id.py --verify`
  already exists to police precisely this: "A built artifact carries the
  id of the sources it came from. Anything a lane runs or ships gets
  `--verify`'d first."

There is a third fact worth putting beside those. Measured: an esbuild
IIFE bundle of `todos.ts` **runs under QuickJS-ng today**, parsing and
executing in 0.08 s (the engine's own baseline), and fails at exactly one
place — `Dynamic require of "node:fs" is not supported`, i.e.
`bindings/js/kaya/runtime.ts`'s `dlopen` layer. That is the **native
bridge kaya has to replace on mobile regardless**, and it has nothing to
do with TypeScript. It is independent confirmation of §3.1's boundary:
strip the host layer off and the other 95% of the binding already runs on
a foreign engine.

One correction to a common belief, since it came up while researching
option (f): **Svelte did not move back to TypeScript.** They moved TS →
JSDoc in Svelte 4 (PR #8569, 2023-05-09), and the "reconsider" issue
(#16647, 2025-08-19) was **closed as not planned**; the compiler source
is still `.js` + `.d.ts`.

### What this means for kaya

**esbuild, option (a).** One nixpkgs attribute already in kaya's pinned
nixpkgs, one static binary, no network, 0.13 s for all 42 guests, 52 kB
per shipped app, and it is the same answer React Native reached for these
same engines. It is forced on iOS by the missing module loader anyway, so
the only question it really settles is whether to *also* use it on the
three desktop lanes.

And the answer to that should be **no**: keep node's type stripping on
the desktops. The desktops lose nothing today, the no-build-step property
that the ruling bought stays real where it is testable fastest (the inner
loop), and the bundle becomes a mobile-lane artifact like every other
mobile artifact. The cost of that choice is honest and should be stated:
**the desktop lanes then run the source and the mobile lanes run a
bundle**, so a bundler bug is invisible to three of five lanes. The wall
for that is the one kaya always builds — the mobile bundles carry a
build id derived from the guest sources and the esbuild version, and the
lane refuses a stale one, exactly as it already refuses a stale
`libkaya`.

## §5 Decisions the maintainer must make

Eight rulings, each with the options, what the evidence says, and a
recommendation in plain words. They are ordered so that an earlier answer
constrains the later ones.

### D1 — Is JavaScriptCore on iOS a requirement, or a choice?

**Options.** (a) It is Apple policy, so it is settled. (b) It is a choice
kaya is making on the merits.

**The evidence.** It is (b), and this is verified rather than
remembered (§2.0). The current **Apple Developer Program License
Agreement** §3.3.1(B) says an app "may not download or install executable
code. Interpreted code may be downloaded to an Application but only so
long as such code: (a) does not change the primary purpose… (b) does not
bypass signing, sandbox, or other security features… (c) … does not
create a store or storefront". **MEASURED: the strings "JavaScriptCore"
and "WebKit" appear zero times in the entire agreement.** The old
"only exception is WebKit or JavaScriptCore" carve-out is gone. And the
clause governs *downloaded* code; kaya's guests ship in the bundle.
Review Guideline 2.5.2 names no interpreter either. React Native ships
Hermes on iOS as its default engine; **kaya already ships CPython in its
own iOS bundle.**

**Recommendation: keep JavaScriptCore on iOS, but as an engineering
choice made with open eyes.** It wins on merits that have nothing to do
with policy: it is a system framework so it costs **zero bytes** (against
Hermes's 2 MiB or CPython's 20 MB), Apple maintains and security-patches
it, it is a modern full-featured engine so nothing needs downleveling,
and it is the only option that gets **Safari Web Inspector debugging**
for free (§1.9). What it costs is that iOS and Android then run different
engines — which §3 shows is a 24-function difference, most of it already
abstracted.

### D2 — Which engine on Android?

**Options.** QuickJS-ng · Hermes · jsc-android · V8 · a headless WebView
· androidx.javascriptengine.

**The evidence.** The last two are structurally disqualified: a WebView
must live on the **UI thread**, which is the one thread kaya's app thread
is defined not to be, and `androidx.javascriptengine` **cannot call
native code at all**. V8 is **21.97 MiB measured** with dead Android wrappers.
jsc-android costs **9.70 MiB per ABI** (19.17 with `Intl`) and its last
Maven publish was **2024-11-29**. QuickJS-ng, **built for arm64 with this
repo's own NDK on 2026-09-02, is 762 KiB stripped / 379 kB in-APK** — 2.7×
smaller than Hermes, 13× smaller than jsc-android — is MIT, releases
roughly monthly, is ES2025-class, is the **only** candidate with a real
module loader, and has a live Rust binding (`rquickjs`, MIT, 0.12.2,
2026-07-27) that targets QuickJS-ng specifically.

**Recommendation: QuickJS-ng.** There is independent corroboration for
the whole shape: **`@capacitor/background-runner` runs JavaScriptCore on
iOS and a vendored QuickJS on Android** — the same split, chosen by a
team shipping at scale with no stake in either engine (§3). For scale:
kaya already accepts ~26 MB of
CPython in the Android bundle; QuickJS-ng is **1/34th** of that. The two
things it gives up are `Intl` (which kaya does not use) and an upstream
debugger (issue #119 open since 2023-11-22; the working art is out of
tree on a custom TCP protocol, not CDP). **Watch Hermes**: its
first-party Node-API v10 implementation would make kaya's existing addon
run unmodified, but as of today it is 12 commits old, on the `static_h`
dev branch, never shipped in a release. Revisit if it stabilises.

### D3 — How does `libkaya` reach the engine on a phone?

**Options.** (a) Write an **N-API provider** over JSC and over QuickJS, so
`crates/kaya/src/node.rs` is unchanged and keeps calling the same 24
symbols. (b) Write a **per-engine floor implementation** — `jsc.rs`,
`quickjs.rs` — that exposes the 17 `Floor` methods directly, with no
N-API in the picture. (c) Adopt JSI.

**The evidence.** (c) is out: JSI is an unstable **C++** ABI, node
exposes no JSI, and adopting it would mean rewriting a working binding
and losing the desktops. Between (a) and (b): Bun proves (a) is possible
(§3), and Hermes may hand it to kaya for free on Android. But Bun's
implementation is written against JSC **internals** that Apple does not
expose, so on iOS kaya would be re-deriving the value and handle-scope
layer anyway — and it would be emulating N-API semantics (handle scopes,
`napi_env` lifecycle, pending-exception state) that kaya controls both
sides of and does not need.

**Recommendation: (b), with the logic factored out.** `node.rs` today
mixes two things — the 17 floor methods' *logic* (which is
engine-neutral Rust: read arguments, call `capi`, build a result) and the
*value plumbing* (which is N-API). Split those, and each engine costs a
thin value/call layer (~200–300 lines) rather than a second 600-line
file. **Appendix A of `multi-engine-precedents.md` already maps all 24
calls onto Apple's public JSC C API**, and §1.2 of this report confirms
every one is available at iOS 10 or earlier. Keep N-API as the *desktop*
implementation and as the shape of the thinking; do not build an
emulator for it.

### D4 — The threading model on iOS

**Options.** (a) Mirror node: a native pump thread hands occurrences to
JS one at a time. (b) The app thread runs the occurrence loop itself.

**The evidence — this one is measured, and it is not close.** §1.5: JS
execution in one JSContext is serialised by the VM lock (4 threads take
3.92× one thread), **but the lock is dropped around a native callback**
(4 threads blocked 20 ms in native take 29 ms, not 88 ms). The hazard
reproduced directly: an app thread running
`order.push('app:enter'); blocking(); order.push('app:leave')` with a
pump thread firing 30 ms in produced **`app:enter | pump:handler |
app:leave`** — a handler ran inside another handler's continuation. On
node that cannot happen. It would interleave two implicit transactions,
mis-own a row handle, and corrupt `_drainPosted`.

**Recommendation: (b), and treat (a) as forbidden rather than merely
unchosen.** The node pump exists only because node's event loop owns the
worker's JS thread; on iOS kaya owns the thread outright. The loop is a
plain `for(;;)` calling `JSObjectCallAsFunction` per occurrence, and
**§1.6 measured that this preserves the implicit transaction exactly**
(`h0,commit0,h1,commit1,h2,commit2`). The stall watchdog stays honest for
the same reason it does on node — a wedged handler never returns. **This
deserves a guard** (invariant 3): the JSC bridge holds to exactly one
thread ever entering the context, with the re-entrant order above as the
watched negative.

### D5 — TypeScript on the mobile lanes

**Options.** (a) esbuild bundle per guest, on the build host. (b) ship
`ts-blank-space` + `typescript` inside the app and strip on device.
(c) rewrite the guests as plain `.js` with JSDoc types. (d) `tsc` emit
plus a bundler.

**The evidence.** (b) and (c) are the only ones that keep the strict
reading of "the file on disk is what runs" — and **both are already dead
on two counts**. First, JSC has no module loader at all (§1.4, verified
against the shipped SDK), so a guest must arrive as one script on iOS
whatever else is true. Second, if Android were Hermes, `async` would need
**lowering**, and a blanker never emits new code. On top of that, (b)
costs **3.59 MB of script and +0.38 s of engine load per process on a
desktop CPU — likely 1–2 s on a phone, per launch** — and pins kaya to a
**frozen TypeScript 6 JavaScript compiler**, since TypeScript 7.0 shipped
2026-07-08 as a Go binary **with no programmatic API**. (c) costs the
guests their TypeScript syntax and turns every signature into a 3–5 line
comment block, in files this project deliberately keeps terse.

**Recommendation: (a), esbuild, and only on the mobile lanes.**
**VERIFIED independently: `esbuild` resolves to `0.27.2` at kaya's own
locked nixpkgs rev `391b592e`** — so it is one line in `flake.nix`, not a
new pin or a network fetch. One 10.5 MB static Go binary, fully offline. **Measured on the real tree: all 42 guests →
1.8 MB total, 52 kB each, 0.13 s**; `--target=es2015` lowers
`async`→generators for +4% bytes and no extra time. Keep node's type
stripping on the three desktops so the inner loop keeps its no-build-step
property. The weaker invariant this keeps — *the source guest is one
unedited file shared by all five platforms, and what differs is a derived
artifact* — is the exact relationship kaya already has with `libkaya`,
the SwiftUI interpreter and the Compose interpreter, and
`tools/build-id.py --verify` already exists to police it.

### D6 — What the bootstrap owes a bare engine

**Not really a choice, but it must be ruled because it is a surface.**
§1.7 measured that a fresh JSContext has **no** `TextEncoder`,
`TextDecoder`, `queueMicrotask`, `setImmediate`, `structuredClone` or
`SharedArrayBuffer`, and that its `console` **exists and prints
nowhere**. kaya's neutral layers name five of those.

**Recommendation: put them on the floor, not in a polyfill grab-bag.**
`queueMicrotask` is one line over `Promise.resolve().then`. `TextEncoder`
/ `TextDecoder` are better as native calls than as JS — the core already
does UTF-8 validation, and `{fatal: true}` is the behaviour that matters.
`console` must be installed over the native writer, for the reason
docs/js-plan.md §3 already re-points the worker's stdio: **a verdict
nobody can read is a lane that cannot fail.** And add a native
`sleep(ms)`, which replaces `Atomics.wait` in `guests/js/stall.ts` and is
the better spelling on every engine anyway. A census gate — every
non-ECMA-262 global the neutral layers name is installed by every
bootstrap — is cheap and catches the next `structuredClone` someone
reaches for.

### D7 — The four guests that touch node

`clipboard.ts`, `filedialog.ts` and `save.ts` import `node:fs`/`os`/`path`
to write a scratch file into `tmpdir()`; `stall.ts` uses `Atomics.wait`.
The other **38 of 42 import only `kaya-gui`** and are already neutral
source.

**Recommendation: add `kaya.tempFile(name, bytes)` to the floor** rather
than shimming `node:fs`. The phones need it regardless — an app's temp
directory is not `/tmp` — and it keeps each guest one file, shared
verbatim, which is invariant 6's actual requirement. `stall.ts` takes the
native `sleep` from D6.

### D8 — Do the phone lanes carry JS legs, and how many?

docs/js-plan.md §5 records "The iOS and Android lanes carry no JS legs —
node does not run on the phones (ruled desktop-first)". That premise is
what this research retires.

**Recommendation: follow the Python precedent exactly, and prove the one
unproven thing first.** docs/python-mobile-plan.md §D6 step 0 is the
model: before building anything on top, it proved `dlopen(NULL)` +
`dlsym` on a real simulator and got a byte-identical spec hash back. The
JS analogue is a probe on a booted simulator that creates a JSContext on
a background thread, installs one native function, round-trips a
`Uint8Array` **with a non-zero `byteOffset`**, and reads
`kaya_spec_hash` back — the last of which also nails the §1.2b trap
before any code depends on it. Then one scene, one lane, then the fan-out.
Start narrow: iOS first (the engine is free and the bridge is smaller),
Android after the engine ruling settles.

### The trap to write down before anything else

Independent of every ruling above: **N-API's
`napi_get_typedarray_info` returns a byte pointer already adjusted by
`byte_offset`; JSC's `JSObjectGetTypedArrayBytesPtr` returns the
buffer base.** Measured, §1.2b. A faithful transliteration of `node.rs`
compiles, runs, and submits the wrong bytes for every `subarray` — and
`wire.ts` uses `subarray` and constructs offset `DataView`s in four
places. This belongs in `docs/traps.md` whether or not the port is built,
because it costs a session to find and nothing to write down.
