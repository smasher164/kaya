SUMMARY
=======

TIER: SYNTHESIZED, and every stamped row is realized. kaya's GTK table
is not a toolkit table — crates/kaya/src/gtk.rs:1125 records that
GtkColumnView was measured and rejected (a GtkListItem OWNS its child,
so a widget kaya's stamp already parented fails
gtk_widget_set_parent's parent==NULL assertion). What the backend builds
instead (gtk.rs, GtkTable / reflow_table / table_rows) is a plain
GtkBox: a composed header GtkBox, a GtkSeparator, then ONE GtkBox per
stamped row, plus one horizontal GtkSizeGroup per column holding every
cell in that column. Nothing recycles.

Two shells, two different walls. Both are the existing non-virtualized
For; they fail for different reasons and both numbers matter.

A. THE LANE'S OWN SHAPE (shell=bare — guests/python/table.py declares no
   window size)
   degraded at: NEVER. The last passing run is 2.38s.
   choke at:    N = 1361 rows. Sharp and deterministic —
                1355/1358/1360 pass (1360 three times, 2.04-2.38s),
                1361/1362 fail twice each, 1363/1364/1365/1366/1370/
                1400/2500 all fail first try.
   failure mode: CRASH — the X server refuses, the guest dies at ~0.6s
                with no verdict, exit 1. Verbatim:

     (python3:329): Gdk-WARNING **: The program 'python3' received an X
     Window System error.
     This probably reflects a bug in the program.
     The error was 'BadAlloc (insufficient resources for operation)'.
       (Details: serial 261 error_code 11 request_code 12 (core
        protocol) minor_code 0)

   Cause, MEASURED not inferred: the For's natural height becomes the
   TOPLEVEL's height. xwininfo on a live leg at the last passing count:

     N=1360  Window id: 0x600004 "kaya milestone 2"  Width: 540
             Height: 32753

   32753 is 14px under X11's 16-bit 32767 ceiling; one more 24.1px row
   crosses it and ConfigureWindow (request_code 12) answers BadAlloc.
   PINNING THE WINDOW DOES NOT HELP: shell=sized (1600x1000 declared)
   fails at 2500 with the identical BadAlloc, because GTK will not
   present a toplevel below its minimum and the un-virtualized For's
   minimum is the sum of every row's.

B. THE COMPARABLE SHAPE (shell=scroll — pinned window, the For inside
   kaya.scroll(grow=1), which is what an app showing a long table would
   write, and the only shell whose numbers mean the same thing as the
   other four platforms')
   degraded at: N ~= 1950 rows (first N over 5s launch-to-verdict).
                1850: 4.60s, 4.15s | 1900: 3.86s, 4.12s
                1950: 5.01s, 7.28s | 2000: 5.50s, 6.05s, 6.96s
   choke at:    N = 6000 rows stable (2 of 2 runs fail); N = 5500 is the
                FIRST failure seen, but it is 1 of 3 (100.21s capped,
                then 56.69s and 40.49s passing). N = 5000 passes twice
                (41.74s, 47.64s). 7500 / 10000 / 20000 all fail.
   failure mode: MY 120s CAP, not the harness's retry window and not a
                crash. Verbatim, the driver's own line:

     no verdict line before the 120s cap; SIGKILLed

                At 6000 the assertion itself still PASSED — the log
                holds "KAYA_SELFTEST: OK (77987.99)" at 103.63s — and it
                was the process exit that never came, because
                GtkStage::finish hops request_exit to the main thread
                and queues behind the same layout work. From 7500 up
                there is no verdict line at all inside 120s.
                THE RETRY WINDOW CANNOT FIRE HERE: harness::POLL_DEADLINE
                is 15s, but a GTK expect BLOCKS in a hop to the main
                thread, so a single poll can outlast the deadline and the
                deadline is never reached. (The watched negative at the
                top of this file is what a real retry-window timeout
                looks like: 15.09s and a FAILED verdict.)

MECHANISM — it is NOT row realization, and it is NOT the stamp/model
path. It is the synthesized TABLE tier's per-column size groups.

  1. The guest-side model build (python objects + the wire records for
     every insert) is 40ms at 2500 rows and ~90ms at 5000 — under 0.25%
     of wall. The stamp/model path is not where the time is.
  2. Essentially all of the wall CPU is inside the guest process, i.e.
     GTK, and none of it is X protocol or rendering (cpu_probe.py):
       N=2500  wall 13.5s  guest_cpu 13.3s  xvfb_cpu 0.0s
       N=5000  wall 69.1s  guest_cpu 68.9s  xvfb_cpu 0.0s
  3. At a FIXED row count, quartering the cells per row (one Total cell
     instead of four) cuts the time 4.6-7x — 2500: 7.32s -> 1.59s;
     5000: 41.7s -> 6.53s — while guest_build is unchanged (42ms, 83ms).
     The cost tracks CELLS, not rows or inserts.
  4. THE DECIDING PERTURBATION: the same rows and the same four labels
     per row through a plain For with NO declared columns
     (KAYA_CHOKE_TABLE=0) builds no GtkTable and therefore no
     GtkSizeGroups. Same widget count, same model, same inserts — and it
     is LINEAR and 14-47x faster:

       N       table (4 cols)      plain For (4 labels)
       2500    7.32s               0.52s
       5000    41.7 / 47.6s        1.01s
       10000   >120s, no verdict   1.95s
       20000   >120s, no verdict   4.22s
       40000   —                   10.36s
       80000   —                   32.98s

     40000 realized row widgets and 160000 labels cost the plain For
     10.4s. The table cannot finish 10000 rows in 120s.

  So the choke is quadratic work inside the TABLE path, not the cost of
  realizing rows. The shape that fits is gtk.rs's reflow_table (line
  1322): on every applied batch it removes every member from each
  column's GtkSizeGroup and re-adds every cell, and a size group
  resolves each add and remove against all its current members —
  O(cols x N^2) for one pass over N rows. NOT ISOLATED BY PERTURBATION
  (the repo was read-only for this run), so that last sentence names the
  candidate the numbers point at; what would isolate it is one run with
  the size-group membership loop skipped.

CAVEAT ON THE ABSOLUTE SECONDS: the sibling platform measurements ran on
this host at the same time (two Android emulators, an iOS simulator, the
Windows UTM VM, the macOS lane). Host load average was 3.9-6.8
throughout, and that is why the 5000-6000 band is wide and why 2250
(9.84s) once came in slower than 2500 (7.32s). The ORDERING and the
SHAPES above are stable across repeats; a quiet host would move the
choke up somewhat, not change which mechanism it is.
