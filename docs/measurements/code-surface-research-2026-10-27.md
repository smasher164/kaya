# Code surface research: line-number gutter, monospaced role, minimap

Research date 2026-10-27. Every claim carries a URL. "Analysis:" marks my own inference, not a source's claim.

**Summary.**
- Gutter: no native text control on any lane has one. macOS has a hook (NSRulerView as `verticalRulerView`) that works with TextKit 2 if the code never touches `.layoutManager` and sets `clipsToBounds = true` (Sonoma default change). GTK has one (`gtk_text_view_set_gutter` + `get_line_yrange`, the GtkSourceView recipe). iOS, WinUI and Compose need a sibling/overlay view placed from line geometry and redrawn on scroll; WinUI RichEditBox's TOM API (`Paragraph`/`Window` units, `GetRect`) is workable, TextBox's is thin. Every editor surveyed numbers logical lines, blanks wrapped rows, aligns to the first row, tints the current number, reserves 2-5 digits.
- Monospaced role: SF Mono via `monospacedSystemFont` (macOS 10.15 / iOS 13, never bundled); GTK `.monospace` class (libadwaita 1.7+ maps it to the user's `monospace-font-name`, Adwaita Mono since GNOME 48, and ALSO sets its size); WinUI has no resource, use "Cascadia Mono, Consolas"; Compose `FontFamily.Monospace` (Droid Sans Mono).
- Minimap: built into none of the five controls; GtkSourceView's GtkSourceMap is the only toolkit-shipped one. Zed and GtkSourceMap both render a second view of the same buffer at a 1-2 pt font with a viewport slider; VS Code rasterizes downsampled glyphs to a canvas. The scroll/viewport/set-offset APIs exist on every lane (C2).
- D (fonts): listing APIs exist everywhere (Android only as files, API 29+); pickers exist natively on macOS, iOS and GTK only; OS text scaling (Dynamic Type, sp, TextScaleFactor) does not reach custom-drawn gutters automatically.

## A. Line-number gutter

### A1. macOS (NSTextView in NSScrollView, TextKit 2)

**The native hook is NSRulerView.** NSRulerView is "a ruler and the markers above or to the side of a scroll view's document view"; it is installed as the scroll view's `verticalRulerView` with `hasVerticalRuler` / `rulersVisible` (https://developer.apple.com/documentation/appkit/nsrulerview). Subclasses override `drawHashMarksAndLabels(in:)`, which "is invoked by `drawRect:`" and is the documented place "to customize the appearance of the hash marks" (https://developer.apple.com/documentation/appkit/nsrulerview/drawhashmarksandlabels(in:)). The ruler is laid out by the scroll view beside the clip view, so it occupies its own column (the text does not scroll under it) and scrolls only by redrawing; set `ruleThickness` for width.

**Works with TextKit 2.** No Apple-documented recipe exists; the only answer to "What is the recommended approach to rendering text with line numbers in TextKit 2?" on the Apple forums is from Marcin Krzyzanowski (STTextView's author): subclass NSRulerView as `verticalRulerView`, override `drawHashMarksAndLabels(in:)`, and place labels with `textLayoutManager.enumerateTextLayoutFragments(from:options: .ensuresLayout)`, reading each fragment's `layoutFragmentFrame` plus its first `textLineFragments` entry's `locationForCharacter(at: 0)`; redraw on `NSView.frameDidChangeNotification` and `NSText.didChangeNotification`. Two later replies (2021, 2024) confirm it works, including wrapping and scrolling. It numbers once per layout fragment (= paragraph), drawing only sub-line 0, so wrapped continuations are blank (https://developer.apple.com/forums/thread/683064).
- Analysis: enumerating `from: nil` with `.ensuresLayout` forces layout of the whole document and defeats TextKit 2's viewport laziness. STTextView's production code instead takes only the fragments currently in the viewport (`textViewportLayoutController.viewportRange`) and computes the first visible line number by counting `textContentManager.textElements(for: documentStart..<viewportStart)` (https://github.com/krzyzanowskim/STTextView/blob/main/Sources/STTextViewAppKit/STTextView+Gutter.swift). For a stock NSTextView, enumerate from the viewport's start location (or `textLayoutManager.textViewportLayoutController.viewportRange`) and count paragraphs before it.
- Do not read `NSTextView.layoutManager` from gutter code: touching it drops the view to TextKit 1: Steve Troughton-Smith (2026-02-09) traced a bug to "NSTextView downgrading from TextKit 2 to TextKit 1 if you access .layoutManager on macOS 26", not triggered by apps built with an older SDK; the same post collects reports that the cases forcing a fallback "are not documented, and will vary from release to release" (https://mjtsai.com/blog/?p=48928). CotEditor's ruler reads `textView.layoutManager` (https://github.com/coteditor/CotEditor/blob/main/CotEditor/Sources/Document%20Window/Text%20View/LineNumberView.swift), i.e. it is TextKit 1 prior art and would force kaya's view into compatibility mode if copied.

**Known issue, macOS 14 Sonoma clipsToBounds.** `NSView.clipsToBounds` now defaults to `false` for apps linked against the macOS 14 SDK (it was `true` on 13 and earlier); a view that fills its `dirtyRect` can paint outside its bounds, and Apple says to fill `bounds` and use `dirtyRect` only "to determine what to draw, not where to draw it" (https://developer.apple.com/documentation/appkit/nsview/clipstobounds; https://developer.apple.com/documentation/macos-release-notes/appkit-release-notes-for-macos-14). The concrete symptom with line-number rulers: "NSTextView Contents Disappear When Ruler shown" on Sonoma/Sequoia (Noodlesoft-style ruler); Apple DTS pointed at clipsToBounds and the fix was `scrollView.verticalRulerView.clipsToBounds = YES` (https://developer.apple.com/forums/thread/767825). Noodlesoft's original ruler: https://www.noodlesoft.com/blog/?p=137. CodeEditSourceEditor's gutter also sets `clipsToBounds = true` (https://github.com/CodeEditApp/CodeEditSourceEditor/blob/main/Sources/CodeEditSourceEditor/Gutter/GutterView.swift).

**Ruler thickness.** CotEditor (NSRulerView subclass) sets `ruleThickness = max((max(digits, 3) + 2) * charWidth, 32)` with `minimumNumberOfDigits = 3`, measuring the width of the glyph "8" (https://github.com/coteditor/CotEditor/blob/main/CotEditor/Sources/Document%20Window/Text%20View/LineNumberView.swift). NSRulerView also has `requiredThickness` (ruleThickness + reserved marker/accessory space); STTextView's 2023 ruler used it ("Use ruler requiredThickness which has all thickness in it", commit 34fb7779, https://github.com/krzyzanowskim/STTextView/commit/34fb7779).

**How open-source editors do it**
- STTextView (TextKit 2, its own NSView, not NSTextView): had an NSRulerView subclass `STLineNumberRulerView` until 2024, then "Remove ruler, introduce working gutter with line numbers" (https://github.com/krzyzanowskim/STTextView/commit/bd3b8251). The gutter is now a plain `STGutterView` added with `enclosingScrollView.addFloatingSubview(gutterView, for: .horizontal)` (stays put horizontally, moves vertically with the document), containing one `STGutterLineNumberCell` NSView per visible logical line, rebuilt in `layoutGutter()`; numbers only "the first line fragment or extra line fragments"; the cell frame is the union of all the paragraph's line fragments with the text centred on the first line's midY; width grows to fit (`minimumThickness = 35`); font is `monospacedDigitSystemFont` condensed; optional selected-line highlight and selected-line text colour (https://github.com/krzyzanowskim/STTextView/blob/main/Sources/STTextViewAppKit/STTextView+Gutter.swift, https://github.com/krzyzanowskim/STTextView/blob/main/Sources/STTextViewCommon/Utilities/STGutterCalculations.swift, https://github.com/krzyzanowskim/STTextView/blob/main/Sources/STTextViewAppKit/Gutter/STGutterView.swift). The same Gutter folder exists for UIKit (https://github.com/krzyzanowskim/STTextView/tree/main/Sources/STTextViewUIKit/Gutter).
- CodeEditSourceEditor (on CodeEditTextView, a custom CoreText layout manager, not TextKit): `GutterView: NSView` "sits on top of the text view so text scrolls underneath the gutter if line wrapping is disabled"; reserves "at least 3 digits", widens when the digit count grows and tells its delegate to update the text view's leading inset; draws numbers with CTLineDraw right-aligned, offset to the first line fragment; tints numbers of selected lines and draws a selected-line band so it is "inline with the line itself" (https://github.com/CodeEditApp/CodeEditSourceEditor/blob/main/Sources/CodeEditSourceEditor/Gutter/GutterView.swift).
- CotEditor (TextKit 1): NSRulerView subclass, redraws on the clip view's `NSView.boundsDidChangeNotification`, forwards `scrollWheel` to the text view, bolds selected line numbers, honours Increase Contrast, supports vertical text (https://github.com/coteditor/CotEditor/blob/main/CotEditor/Sources/Document%20Window/Text%20View/LineNumberView.swift). A standalone extraction: https://github.com/brutella/TextViewLineNumbers.
- ChimeHQ: no public gutter package was found (`ChimeHQ/Gutter` returns 404 on the GitHub API); TextViewPlus and Neon carry no gutter or ruler files (checked via the repos' trees). Xcode's own editor is closed source; nothing primary to cite.

**Accessibility.** AppKit defines the roles `NSAccessibility.Role.ruler` ("The ruler role") and `.rulerMarker` (https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/role/ruler). CotEditor overrides `accessibilityLabel()` on its NSRulerView to "Line Numbers" (source above), i.e. the ruler is one AX element; no project found exposes each number as an element. STTextView's cells and CodeEdit's gutter declare no accessibility (grep of the sources above). Analysis: VoiceOver users get line numbers from the text view itself (AXInsertionPointLineNumber / line-based parameterized attributes), so a gutter that is a single labelled or ignored element is the norm.

### A2. iOS (UITextView)

UITextView has no gutter, ruler or line-number API (none in https://developer.apple.com/documentation/uikit/uitextview). The open-source editors do not use UITextView at all:
- Runestone is its own UIScrollView-based text view (README lists "Line numbers" as a feature, https://github.com/simonbs/Runestone). Its `LayoutManager` keeps a `gutterContainerView` whose frame is pinned to `viewport.minX` with height = `contentSize.height`, so it scrolls vertically with the content and stays fixed horizontally; one reusable `LineNumberView` (a right-aligned UILabel) per visible document line, dequeued per line id; the text's x origin is shifted by `gutterWidthService.gutterWidth`; a selected-line band is drawn in the gutter; all gutter views have `isUserInteractionEnabled = false` (https://github.com/simonbs/Runestone/blob/main/Sources/Runestone/TextView/Core/LayoutManager.swift, https://github.com/simonbs/Runestone/blob/main/Sources/Runestone/TextView/Gutter/LineNumberView.swift, https://github.com/simonbs/Runestone/blob/main/Sources/Runestone/TextView/Gutter/GutterWidthService.swift).
- STTextView's UIKit target uses the same cell-per-line gutter as its AppKit one (https://github.com/krzyzanowskim/STTextView/tree/main/Sources/STTextViewUIKit/Gutter).
- Analysis for a stock UITextView: reserve space with `textContainerInset.left` (https://developer.apple.com/documentation/uikit/uitextview/textcontaininset), add a gutter subview inside the text view (it is a UIScrollView, so a subview at y in content coordinates scrolls with the text) and keep its x at `contentOffset.x`, and place numbers from `textLayoutManager.enumerateTextLayoutFragments` over the viewport as on the Mac. Accessibility: UIKit's `UIAccessibilityReadingContent` (`accessibilityLineNumber(for:)`, `accessibilityContent(forLineNumber:)`) is the line-number story for VoiceOver, independent of any gutter (https://developer.apple.com/documentation/uikit/uiaccessibilityreadingcontent); the gutter should be `isAccessibilityElement = false`.

### A3. GTK4 (GtkTextView in GtkScrolledWindow)

**`gtk_text_view_set_gutter(view, win, widget)`** "Places @widget into the gutter specified by @win"; `win` must be `GTK_TEXT_WINDOW_LEFT/RIGHT/TOP/BOTTOM`; passing NULL removes the gutter (https://docs.gtk.org/gtk4/method.TextView.set_gutter.html). From the source (GTK 4.24.0): the widget is wrapped in a private `GtkTextViewChild` parented to the text view; the left border's width is the child's measured natural horizontal size (`gtk_widget_measure(left_child, HORIZONTAL, ...)`), so the gutter widget sizes itself and the text area shifts right by that width; on every allocation the text view calls `gtk_text_view_child_set_offset(left_child, xoffset, yoffset)` with its current scroll offsets, i.e. the gutter is fixed horizontally and does NOT scroll its contents itself: it must redraw from the current scroll position (https://gitlab.gnome.org/GNOME/gtk/-/blob/4.24.0/gtk/gtktextview.c, lines ~4386-4400, 4661-4713, 4815-4818; https://gitlab.gnome.org/GNOME/gtk/-/blob/4.24.0/gtk/gtktextviewchild.c).

**Getting y positions.**
- `gtk_text_view_get_line_yrange(view, iter, &y, &height)`: "the y coordinate of the top of the line containing @iter, and the height of the line"; buffer coordinates, convert with `gtk_text_view_buffer_to_window_coords()` (https://docs.gtk.org/gtk4/method.TextView.get_line_yrange.html). The "line" is the buffer line (paragraph); its height covers all wrapped display lines: GtkSourceView calls `get_line_yrange` once per buffer line and separately computes `first_height` for the first display line when wrapping is on (https://gitlab.gnome.org/GNOME/gtksourceview/-/blob/master/gtksourceview/gtksourcegutterlines.c, lines ~166-257).
- `gtk_text_view_get_line_at_y(view, &iter, y, &line_top)`: "the GtkTextIter at the start of the line containing the coordinate @y", y in buffer coordinates (https://docs.gtk.org/gtk4/method.TextView.get_line_at_y.html).
- `gtk_text_view_get_visible_rect()` gives the viewport in buffer coordinates; GtkSourceGutter uses it with `get_line_at_y` at its top and bottom to find the first and last visible lines (https://gitlab.gnome.org/GNOME/gtksourceview/-/blob/master/gtksourceview/gtksourcegutter.c, lines ~765-786).
- Redraw trigger: GtkSourceGutter binds to the view's `vadjustment` (left/right gutters) or `hadjustment` (top/bottom) and queues a draw on `value-changed` and `notify::upper` (gtksourcegutter.c lines ~193-230, 498-506).

**GtkSourceView's renderer.** GtkSourceView installs its gutters with `gtk_text_view_set_gutter` (https://gitlab.gnome.org/GNOME/gtksourceview/-/blob/master/gtksourceview/gtksourceview.c, lines ~5376, 5393). `GtkSourceGutterRendererLines`:
- numbers buffer lines (`line + 1`), i.e. logical lines; wrapped continuations are blank;
- is created with `alignment-mode = GTK_SOURCE_GUTTER_RENDERER_ALIGNMENT_MODE_FIRST` (gtksourceview.c line ~3046); the enum's doc: CELL "The full cell", FIRST "The first line", LAST "The last line", "when a cell spans multiple lines (due to text wrapping)" (https://gitlab.gnome.org/GNOME/gtksourceview/-/blob/master/gtksourceview/gtksourcegutterrenderer.h);
- width: digits of `gtk_text_buffer_get_line_count`, minimum 2 digits, `gtk_widget_queue_resize` when the count changes; natural = text width + 2*xpad (https://gitlab.gnome.org/GNOME/gtksourceview/-/blob/master/gtksourceview/gtksourcegutterrendererlines.c, lines ~140-166, 441-443). The base class doc: "if the buffer contains 100 lines, the gutter renderer will always set its width such as three digits can be printed, even if only the first 20 lines are shown" (gtksourcegutterrenderer.c lines ~48-56);
- the cursor's line number uses the style scheme's current-line-number colour and optionally bold (`current_line_bold`), and redraws on cursor moves when `highlight-current-line` is set (gtksourcegutterrendererlines.c lines ~42-44, 179-181, 478-492);
- draws digits as cached Pango glyphs into a `gsk_text_node` at `y + baseline` of the aligned cell (lines ~451-520).
- Public reference docs: https://gnome.pages.gitlab.gnome.org/gtksourceview/gtksourceview5/class.Gutter.html and https://gnome.pages.gitlab.gnome.org/gtksourceview/gtksourceview5/class.GutterRendererText.html.

**Accessibility.** None of gtksourcegutter.c, gtksourcegutterrenderer.c, gtksourcegutterrendererlines.c or gtksourcegutterlines.c sets an accessible role, label or property (grep for `accessib` over the four files is empty; sources above). The gutter widget is a child of the GtkTextView, so it is in the accessible tree as a generic widget unless the app marks it. Analysis: give a custom gutter `GTK_ACCESSIBLE_ROLE_PRESENTATION` or a label ("Line numbers"); screen readers read the current line from the text view's own GtkAccessibleText.

### A4. WinUI 3 (TextBox, RichEditBox)

Neither control has a gutter, margin or line-number API (members listed at https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.textbox and https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.richeditbox). No Microsoft sample pairs either with a line-number column (searched; none found). The ingredients:

- **The scroller.** Both default templates host the text in a `ScrollViewer x:Name="ContentElement"` (with `AutomationProperties.AccessibilityView="Raw"`) (https://github.com/microsoft/microsoft-ui-xaml/blob/main/controls/dev/CommonStyles/TextBox_themeresources.xaml line ~337; https://github.com/microsoft/microsoft-ui-xaml/blob/main/controls/dev/CommonStyles/RichEditBox_themeresources.xaml line ~94). Reach it with `GetTemplateChild`-equivalent `VisualTreeHelper` lookup after `Loaded`/`OnApplyTemplate`; subscribe to `ScrollViewer.ViewChanged` and read `VerticalOffset`, `ViewportHeight`, `ExtentHeight`; `ChangeView(null, y, null)` sets it (https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.scrollviewer.viewchanged, https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.scrollviewer.changeview). Analysis: the template part name is a template convention, not an API contract; a retemplated control can lack it.
- **TextBox geometry.** `GetRectFromCharacterIndex(charIndex, trailingEdge)` returns the edge rect of a character; "the width of the rectangle that's returned is always 0" (https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.textbox.getrectfromcharacterindex). Analysis: numbering logical lines means splitting `Text` on '\r' (TextBox normalises newlines to CR) and asking the rect of each visible line's first character; there is no API for line count, first visible line, or display-line enumeration, so finding the visible range takes a binary search over line-start indices by rect.Y. The rect's coordinate space is the control's (the sample transforms it with `TextBox.TransformToVisual`), and it already reflects the scroll offset, so after `ViewChanged` it must be re-queried.
- **RichEditBox geometry.** `ITextRange.GetRect(PointOptions, out Rect, out int hit)` "Retrieves the bounding rectangle that encompasses the text range on the screen" (https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.text.itextrange.getrect); `PointOptions.ClientCoordinates` (256) returns client instead of screen coordinates; `NoVerticalScroll`, `IncludeInset` also exist (https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.text.pointoptions). `TextRangeUnit.Paragraph` = text terminated by an end-of-paragraph mark (the logical line); `TextRangeUnit.Line` = "A single line of text on a display" (the display line); `TextRangeUnit.Window` = "The characters between the upper-left and lower-right corners of the window" (the visible range) (https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.text.textrangeunit). So with RichEditBox: take `Document.GetRange(0,0)`, `Expand(TextRangeUnit.Window)` for the visible span, step it by `Paragraph`, `GetIndex(TextRangeUnit.Paragraph)` for the number, `GetRect(ClientCoordinates)` for its top. Analysis: this is the richer API of the two (it is the RichEdit/TOM object model).
- **Prior art.** WinUIEdit (BreeceW) is a WinUI 3/UWP port of Scintilla, drawing with Direct2D (`scintilla/winui/SurfaceD2D.cxx`); line numbers come from Scintilla's margins (`MarginView.cxx`), not from any XAML text control; "currently not production ready" (https://github.com/BreeceW/WinUIEdit). Scintilla margins: `SCI_SETMARGINTYPEN(margin, SC_MARGIN_NUMBER)`, `SCI_SETMARGINWIDTHN` (https://www.scintilla.org/ScintillaDoc.html#Margins). It has its own automation peer (`EditorBaseControlAutomationPeer`, same repo).
- AvaloniaEdit's `LineNumberMargin` (XAML-family prior art, port of AvalonEdit): a separate control beside the TextView, numbers `VisualLine.FirstDocumentLine.LineNumber` (logical lines), places it at `GetTextLineVisualYPosition(line.TextLines[0], VisualYPosition.TextTop)` (top of the first wrapped row), re-renders on the TextView's `VisualLinesChanged`, width measured from a string of '9' x max digits with `MinWidthInDigits = 2` (https://github.com/AvaloniaUI/AvaloniaEdit/blob/master/src/AvaloniaEdit/Editing/LineNumberMargin.cs).

Analysis for kaya: a sibling Canvas (or a single custom-drawn element) to the left of the control in a Grid, laid out from `ViewChanged` + `TextChanged` + `SizeChanged`, with positions from `GetRect`/`GetRectFromCharacterIndex`. Give it `AutomationProperties.AccessibilityView="Raw"` (or a name "Line numbers") so Narrator does not read every number.

### A5. Android (Jetpack Compose BasicTextField / TextField)

No gutter or line-number parameter on either (signatures in https://github.com/androidx/androidx/blob/androidx-main/compose/foundation/foundation/src/commonMain/kotlin/androidx/compose/foundation/text/BasicTextField.kt and https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/TextField.kt).

- **Scroll state is public on the TextFieldState overloads.** `BasicTextField(state: TextFieldState, ..., onTextLayout: (Density.(getResult: () -> TextLayoutResult?) -> Unit)? = null, ..., scrollState: ScrollState = rememberScrollState())`; doc: "scrollState to manage scroll. If [lineLimits] is [SingleLine], the text field scrolls horizontally. Otherwise, it scrolls vertically" (BasicTextField.kt lines ~145-180). Material 3's `TextField(state: TextFieldState, ...)` has the same `onTextLayout` and `scrollState` parameters (TextField.kt lines ~207-227), and the String-value overloads are marked "Use the TextField(state: TextFieldState, ...) overload instead" (lines ~365, 527). The older value/onValueChange `BasicTextField` takes `onTextLayout: (TextLayoutResult) -> Unit` and no scroll state (BasicTextField.kt lines ~782-826); its scroller (`TextFieldScrollerPosition`) is internal (https://github.com/androidx/androidx/blob/androidx-main/compose/foundation/foundation/src/commonMain/kotlin/androidx/compose/foundation/text/TextFieldScroll.kt).
- **Line geometry.** `TextLayoutResult.lineCount`, `getLineStart(lineIndex)`, `getLineTop/getLineBaseline/getLineBottom(lineIndex)`, `getLineForOffset(offset)`, `getLineForVerticalPosition(y)` (https://github.com/androidx/androidx/blob/androidx-main/compose/ui/ui-text/src/commonMain/kotlin/androidx/compose/ui/text/TextLayoutResult.kt lines ~381-492; reference https://developer.android.com/reference/kotlin/androidx/compose/ui/text/TextLayoutResult). These are display (visual) lines: logical numbering needs a check that the character before `getLineStart(i)` is '\n' (or i == 0), counting newlines in the text before the first visible line. Coordinates are in the text layout's space, unscrolled.
- **Drawing in sync (analysis, from the parameters above):** two shapes work. (1) Keep the field scrolling and draw the gutter from `scrollState.value` (pixels) plus `getLineTop(i)` / `getLineBaseline(i)`; put the gutter in the `decorator` (`TextFieldDecorator`, which receives `innerTextField`) inside a Row so it shares the field's bounds, and read `scrollState.value` inside a draw lambda (`Modifier.drawBehind`/`drawWithCache`) so scrolling only re-draws, not re-composes. (2) Give the field unbounded height inside an outer `Modifier.verticalScroll(sharedState)` Row with the gutter as a sibling column; simpler, but then the field loses its own scrolling-to-cursor behaviour and lays out the whole text.
- **Prior art.** sora-editor's `CodeEditor extends View` is a full custom editor that draws its own line numbers on a Canvas in `EditorRenderer.drawLineNumber`, only for `rowInf.isLeadingRow` (the first visual row of a logical line), i.e. logical numbering with wrapped rows blank (https://github.com/Rosemoe/sora-editor/blob/main/editor/src/main/java/io/github/rosemoe/sora/widget/EditorRenderer.java lines ~843, 934; https://github.com/Rosemoe/sora-editor/blob/main/editor/src/main/java/io/github/rosemoe/sora/widget/CodeEditor.java line ~187). It does not use EditText or Compose text fields.
- Accessibility: a Compose gutter drawn with `drawBehind` produces no semantics nodes; a gutter of `Text` composables should be wrapped in `Modifier.clearAndSetSemantics {}` (https://developer.android.com/reference/kotlin/androidx/compose/ui/semantics/package-summary#(androidx.compose.ui.Modifier).clearAndSetSemantics(kotlin.Function1)) so TalkBack does not walk every number.

### A6. Editors' line-number semantics

| Editor | Numbers | Wrapped rows | Vertical placement | Current line | Width | Scroll |
|---|---|---|---|---|---|---|
| VS Code | model (logical) line | blank: `_getLineRenderLineNumber` returns '' when the view line's first position maps to model column != 1 | one div per view line, same line height as the text row | `active-line-number` class, theme colour `editorLineNumber.activeForeground`; modes on/off/relative/interval | `editor.lineNumbersMinChars` default 5 (min 1, max 300); `digitCount = max(digits(lineCount), minChars)` | vertical with the text, never horizontal |
| Zed | buffer row | blank: number comes from `row_info.buffer_row`, which is set only on a buffer row's first display row (`wrapped_buffer_row` for continuations is used only in relative "wrapped" mode) | drawn at `ix * line_height - scroll_top % line_height` | `editor_active_line_number` theme colour | `gutter.min_line_number_digits` default 4 | vertical only |
| GtkSourceView | buffer line | blank (one cell per buffer line) | `ALIGNMENT_MODE_FIRST`: aligned to the first display line | current-line-number colour, optional bold | min 2 digits, grows with `get_line_count` | vertical only |
| AvaloniaEdit | `DocumentLine.LineNumber` | blank (one per VisualLine) | `VisualYPosition.TextTop` of `TextLines[0]` | not in LineNumberMargin | `MinWidthInDigits` default 2 | vertical only |
| CodeEditSourceEditor | line index | blank (one per text line) | first fragment, baseline from ascent | selected lines tinted + band | min 3 digits | gutter floats over text |
| STTextView | paragraph | blank (cell spans the paragraph, number centred on first row) | first line fragment midY | optional highlight colour | min thickness 35 pt, grows | vertical only |

Consensus: number logical lines, leave wrapped continuations blank, align the number with the FIRST row of its line (same baseline when the gutter font size matches), tint the current line's number, reserve a minimum digit count (2-5) and grow with the digit count of the total, keep the gutter fixed horizontally while it scrolls vertically with the text. Gutter numbers use tabular (monospaced) digits: STTextView uses `monospacedDigitSystemFont`, CotEditor draws digit glyphs at the advance of "8", GtkSourceView caches digit glyphs.

## C. Minimap

### C1. How the editors build one

- **VS Code.** On by default (`editor.minimap.enabled: true`, `size: 'proportional'`, `side: 'right'`, `showSlider: 'mouseover'`, `renderCharacters: true`, `maxColumn: 120`, `scale: 1`) (https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/config/editorOptions.ts lines ~3487-3495). Settings text: `renderCharacters` "Render the actual characters on a line as opposed to color blocks"; `scale` "Scale of content drawn in the minimap: 1, 2 or 3"; `size` proportional ("same size as the editor contents (and might scroll)"), fill ("stretch or shrink ... to fill the height of the editor (no scrolling)"), fit ("shrink as necessary to never be larger than the editor"); `maxColumn` limits columns; `showSlider`; MARK:/region section headers (lines ~3505-3585). Rendering: a `<canvas>` filled through two `ImageData` buffers (minimap.ts lines ~440-530); characters 32..126 come from a char sheet drawn once from the editor's font into a canvas and downsampled to 1x2 px per character at scale 1 ("draws data into a canvas and then downsamples the characters as necessary", minimapCharRendererFactory.ts lines ~12-17, 50-108; `BASE_CHAR_HEIGHT = 2, BASE_CHAR_WIDTH = 1`, minimapCharSheet.ts), coloured by token colour; with renderCharacters off it draws blocks. The slider is the viewport: `sliderTop = scrollTop * computedSliderRatio` and dragging maps back by dividing by the ratio (minimap.ts `MinimapLayout`, lines ~214-411). It renders view lines (wrapped rows), reading `getMinimapLinesRenderingData(start, end)` from the view model. Sources: https://github.com/microsoft/vscode/tree/main/src/vs/editor/browser/viewParts/minimap.
- **Zed (2025).** PR #26893 "editor: Add minimap", merged 2025-05-07: "a second instance of the editor will appear to the left of the scrollbar. This instance is not interactive ... it is otherwise just a zoomed-out version of the main editor instance. A thumb shows the line boundaries of the main viewport ... Clicking on a section of code in the minimap will jump the editor to that code. Dragging the thumb will act like the scrollbar", explicitly "closely following the design from Visual Studio Code" (https://github.com/zed-industries/zed/pull/26893). In code: `Editor::new_internal(EditorMode::Minimap { parent }, self.buffer.clone(), None, Some(self.display_map.clone()), ...)` shares the buffer AND the display map (folds, wraps), clones the scroll state, and sets `.ZedMono` at `MINIMAP_FONT_SIZE = 2px`, weight BLACK (https://github.com/zed-industries/zed/blob/main/crates/editor/src/editor.rs lines ~322, 9011-9063); layout in `layout_minimap` (element.rs lines ~1581-1671). Default `minimap.show: "never"`, `thumb: "always"`, `max_width_columns: 80`, `display_in: "active_editor"` (https://github.com/zed-industries/zed/blob/main/assets/settings/default.json lines ~694-741).
- **Sublime Text.** Closed source. Settings: `draw_minimap_border` "draw a border around the minimap's region corresponding to the the view's currently visible text"; `always_show_minimap_viewport` "always show rectangle on minimap highlighting current document position" (default false: hover only) (https://docs.sublimetext.io/reference/settings.html). Some themes ignore the viewport setting (https://forum.sublimetext.com/t/always-show-minimap-viewport-always-true-using-monokai-pro/75707).
- **Xcode (11+).** Toggled from the Editor Options button > Minimap (https://help.apple.com/xcode/mac/current/en.lproj/dev79c94bf05.html); ⌃⇧⌘M; introduced in Xcode 11; hovering shows the symbol under the pointer (https://sarunw.com/posts/xcode-shortcuts-for-navigation/); `// MARK:` comments appear as bold headings in it (https://www.dice.com/career-advice/wwdc-2019-xcode-11-powerful-swift). Closed source.
- **GtkSourceView's GtkSourceMap (the one minimap that ships in a toolkit library).** "Widget that displays a map for a specific GtkSourceView ... maps the content of a GtkSourceView into a smaller view"; it IS a GtkSourceView subclass connected with `gtk_source_map_set_view()`; default font "Monospace 1" (1 pt), and "When FontConfig is available, GtkSourceMap will try to use a bundled 'block' font" (https://gnome.pages.gitlab.gnome.org/gtksourceview/gtksourceview5/class.Map.html; https://gitlab.gnome.org/GNOME/gtksourceview/-/blob/master/gtksourceview/gtksourcemap.c lines ~40-110). It binds the view's `buffer`, `indent-width`, `tab-width` (lines ~1066-1094), and computes the slider from both views' vadjustments: `slider_y = (visible_begin / view_height) * map_height - (child_value - child_lower)` (lines ~331-381). Its notes record that a second text view was the fastest option, faster than cairo-scaling a render (lines ~63-101). It needs GtkSourceView, not a plain GtkTextView.
- **CodeEditSourceEditor.** `MinimapView` holds its own layout manager over the same text storage with a custom `MinimapLineRenderer` that lays every line fragment out 2-3 px tall and draws "small bubbles in place of text"; a draggable `documentVisibleView` box; listens to the editor's clip view `NSView.boundsDidChangeNotification` (https://github.com/CodeEditApp/CodeEditSourceEditor/blob/main/Sources/CodeEditSourceEditor/Minimap/MinimapView.swift, https://github.com/CodeEditApp/CodeEditSourceEditor/blob/main/Sources/CodeEditSourceEditor/Minimap/MinimapLineRenderer.swift).

Two architectures, then: (a) a second text view on the same text storage at a ~1-2 pt font (Zed, GtkSourceMap, CodeEdit), which inherits wrapping and colours for free; (b) a custom raster of downsampled glyphs or blocks (VS Code), which needs per-line text and colours.

### C3. Is a minimap built into any of the native controls?

No. None of NSTextView/NSScrollView, UITextView, GtkTextView, WinUI TextBox/RichEditBox, or Compose BasicTextField/TextField offers one (their API surfaces cited in A1-A5). The only shipped implementation in a platform toolkit's ecosystem is GtkSourceView's GtkSourceMap, which requires GtkSourceView rather than GtkTextView. Analysis for kaya: architecture (a), a second read-only view of the same text at a 1-2 pt font plus a viewport slider driven by the scroll APIs above, is carriable on macOS, iOS and GTK with shared storage, and on Android/Windows with a mirrored copy; WinUI is the weakest lane (no shared document, TextBox has no visible-range API).

- **Zed:** `buffer_font_family: ".ZedMono"` with its own `buffer_font_size` (default 15), separate from `ui_font_family` (https://github.com/zed-industries/zed/blob/main/assets/settings/default.json lines ~31, 41, 59).
- **GNOME Text Editor:** `use-system-font` default true, "Whether the default system monospace font should be used" (i.e. it follows `monospace-font-name` including its size); `custom-font` default 'Monospace 11' otherwise; `line-height` 1.2; and, relevant to A and C, `show-line-numbers` default false and `show-map` ("an overview map of the file", GtkSourceMap) default false (https://gitlab.gnome.org/GNOME/gnome-text-editor/-/blob/main/data/org.gnome.TextEditor.gschema.xml lines ~55-155).
- **Xcode:** font and size per syntax category under Settings > Themes; built-in themes must be duplicated to edit (https://troz.net/post/2016/configuring-xcode/; https://developer.apple.com/forums/thread/31419). Closed source.
- **Apple platforms:** HIG: "Using text styles with the system fonts also ensures support for Dynamic Type and larger accessibility type sizes (where available)"; under macOS: "macOS doesn't support Dynamic Type" (https://developer.apple.com/design/human-interface-guidelines/typography). On iOS `UIFont.preferredFont(forTextStyle:)` returns "the system font for the specified text style with scaling for the user's selected content size category" (https://developer.apple.com/documentation/uikit/uifont/preferredfont(fortextstyle:)), and `UIFontMetrics` scales custom fonts, including a monospaced system font (B).
- **Android:** "Starting in Android 14, the system supports font scaling up to 200%" with a nonlinear curve; "always specify text sizes in sp units"; do not compute with `Configuration.fontScale`/`scaledDensity` (https://developer.android.com/about/versions/14/features#non-linear-font-scaling).
- **Windows:** Settings "Make text bigger" resizes text "ranging from 100% (the default size) up to 225%"; "WinUI apps support text scaling by default"; "DirectWrite, GDI, and XAML SwapChainPanels do not natively support text scaling"; custom surfaces handle `UISettings.TextScaleFactorChanged` (https://learn.microsoft.com/en-us/windows/apps/design/input/text-scaling); per control `IsTextScaleFactorEnabled` "whether automatic text enlargement, to reflect the system text size setting, is enabled" (https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.control.istextscalefactorenabled; factor in https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.uisettings.textscalefactor). Analysis: a gutter or minimap drawn by kaya on WinUI is a custom surface and must apply TextScaleFactor itself, or the line numbers will not track the text.
- **WCAG 1.4.4 Resize Text:** "Except for captions and images of text, text can be resized without assistive technology up to 200 percent without loss of content or functionality" (https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html).

Analysis for kaya: the editors split into absolute sizes the user sets in the app (VS Code, Zed, Xcode) and sizes taken from the OS monospace setting (GNOME Text Editor). A monospaced ROLE that keeps the textarea's own (OS-scaled) size and only swaps the face is the choice that respects Dynamic Type / sp / TextScaleFactor on every lane; the one trap is libadwaita's `.monospace` class, which also sets `font-size` (B).
