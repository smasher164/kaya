FAILURE MODE — MY CAP, NEVER THE RETRY WINDOW, AND WHY
-------------------------------------------------------
harness::POLL_DEADLINE is 15s, but no run above can reach it. Every harness
read on this backend goes through WinUiStage::on_ui_read
(crates/kaya/src/winui/mod.rs:12894), which enqueues onto the
DispatcherQueue and then does a bare `rx.recv()` — no timeout. While the UI
thread is still draining the transaction the read does not return, and
harness::poll only consults its deadline AFTER the closure returns. So the
scene cannot fail by retry-window expiry while the UI thread is busy: it
waits, and something outside has to end it. On the real lane that something
is wait-exit.ps1's 290s leg deadline (run_one_suite in
tools/deploy-win.py); here it is my 120s cap.

There is no harness failure sentence to quote, because the harness never
got to write one. The verbatim tail of every capped transcript is the step
log for the FIRST assertion (printed just before the read blocks), then my
kill:

  513 KAYA_HARNESS: +0ms ExpectColumns(Target { kind: Column, index: 0, id: None, keys: None }, "Date|Ticker|Side|Total")
  WALLMS=121371
  EXIT=1

(EXIT=1 is my `taskkill /f /im python.exe`, not the guest's own code. Not a
crash: no WerFault, no dump, no 0xC0000409 — the process was alive and
working when I killed it.)

TIER
----
SYNTHESIZED, and it realizes every row. There is no native table control
anywhere in the WinUI backend — no ItemsRepeater, no ListView, no
ItemsControl in crates/kaya/src/winui/mod.rs. A table IS the For's Grid
with a header Grid and a rule appended in front of the rows
(mint_table_header / reindex's `head = 2`), each row is its own Grid, and
each cell is a TextBlock. At N=11500 that is 11,500 row Grids and 46,000
TextBlocks, all live.

MECHANISM — ROW-WIDGET REALIZATION, AND MORE PRECISELY THE RE-INDEX
--------------------------------------------------------------------
Not the stamp/model cost. Three independent pieces of evidence:

1. THE GUEST-SIDE HALF IS LINEAR AND NEGLIGIBLE. Encoding the records and
   submitting the transaction, measured in the guest itself:
     N=500 2ms | 1000 5ms | 2500 20ms | 5000 63ms | 10000 209ms | 20000 902ms
   At N=10000 that is 209ms of 77,580ms — 0.3%. Everything else is the UI
   thread applying the batch.

2. THE SHAPE CONTROLS AGREE (see CONTROLS above). A For with a header, the
   same For without one, and the same widgets built live in the build
   closure with no collection at all, all cost the same at the same widget
   count. So it is neither the table's measure/stamp pass nor the For's
   stamping — the cost tracks the WIDGET COUNT.

3. THE SCALING IS QUADRATIC. UI-side apply, doubling N:
     500 0.305s -> 1000 0.885s (2.90x) -> 2500 4.57s -> 5000 18.78s (4.11x)
     -> 10000 77.25s (4.11x). log2 of 4.11 is 2.04.

WHAT IN THE CODE PRODUCES AN N^2: `ApplyOp::AddChild`
(crates/kaya/src/winui/mod.rs:11231) ends every single child append with
`reindex(core, parent)`, and `reindex` (line 1763) CLEARS the parent Grid's
whole RowDefinitions collection, rebuilds one RowDefinition per existing
child, and then re-stamps `Grid::SetRow` on every existing child. Appending
N rows to one container is therefore sum(k=1..N) = N^2/2 RowDefinition
constructions plus N^2/2 attached-property writes, every one of them a
WinRT interop round trip. The measured constant backs it: 2*T/N^2 is
1.46us at N=2500, 1.50us at N=5000 and 1.55us at N=10000 — one flat
per-iteration cost across a 16x span of total time, which is what a COM
call pair costs on this VM. Above ~10k rows it steepens a little further
(11000 lands at ~112s where N^2 alone predicts ~93s), consistent with the
working set of ~46,000 live TextBlocks starting to bite.

So a row-virtualization slice on this platform has two distinct wins
available, and the second is the cheaper one: realize fewer rows, and stop
re-indexing every sibling on every append.
