================================ SUMMARY ================================
PLATFORM  macOS, SwiftUI interpreter.
TIER      NATIVE. macOS always takes the NSTableView tier (tools/check-table-tier.sh
          holds the rule). Confirmed by measurement, not by reading: the sample of a
          100000-row leg shows KayaNativeTable.body.getter on the main thread.
GUEST     Python. The lane runs the table scene in all eight languages; python is the
          one the maintainer named, and guests/python/table.py is the shape copied.
          Numbers are comparable within macOS, not across languages: at large N a
          large share of the wall is the Python guest building its own dataclass rows
          (see note 2), which a Rust guest would not pay.

------------------------------------------------------------------------
PART A: the natural guest. Every row inserted inside the build closure, so
        the whole table is ONE transaction and therefore ONE apply batch.
        This is what guests/python/table.py does, scaled up.

  DEGRADED (first N over 5s launch-to-verdict):  NEVER REACHED.
        The failure arrives at 0.30s. Every passing N is under 0.31s.
  CHOKE (first N that fails):  N = 161.
        N=160 passes 3/3 (0.18s, 0.19s, 0.20s). N=161 fails 3/3.
  FAILURE MODE: CRASH. SIGABRT (rc -6), before the harness script even starts
        (no "KAYA_HARNESS: epoch" line, no verdict list, nothing to retry).
        Not a retry-window timeout, not my cap.
  FAILURE SENTENCE, verbatim (N=161):

        thread '<unnamed>' (126288515) panicked at crates/kaya/src/capi.rs:2936:5:
        kaya: apply batch of 65944 bytes exceeds the pump buffer of 65536
        note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
        fatal runtime error: failed to initiate panic, error 5, aborting

  MECHANISM: neither stamp cost nor realization. A FIXED 64 KiB WIRE BUFFER.
        swift/KayaSwiftUI.swift:2991, kayaStartCommandPump: `let cap = 64 * 1024`.
        crates/kaya/src/capi.rs:2937 asserts the resolved batch fits it.
        The batch size is exactly  256 + 408*N  bytes for this 4-column row, and
        that model reproduces EVERY observed number (N=161 -> 65944, N=500 ->
        204256, N=999 -> 407848), so the wall is at floor((65536-256)/408) = 160.
        Rows per batch scales as 65280 / (bytes per row): a wider row chokes
        sooner, a narrower one later, but no table of any realistic width gets
        past a few hundred rows in one transaction.
        A row-virtualization slice does NOT move this wall by itself. Whatever
        virtualizes the VIEW still has to get the model over a 64 KiB pipe.

------------------------------------------------------------------------

        rows arrive 100 per transaction (chained app.post, the binding's own
        out-of-band transaction). Chunk size proven not to matter, note 1.
        This is the stamp/model + realization baseline.

  DEGRADED (first N over 5s):  N = 30000.  (5.45s, 5.42s, 5.13s over three runs.)
        N=28000 straddles the line (3.36s, 5.09s, 3.56s) under concurrent load.
  CHOKE (first N that fails):  N = 43750, failed 2/2.

        First N failing on every repeat: 45000 (9.70s, 10.05s, 10.04s, 3/3 fail).

        The table is PARTIALLY STAMPED when the window runs out, and the harness
        says so by naming the row it actually found. Same mode all the way up:
        N=200000 still fails this way, at 17.13s, with no crash and no cap-kill.
  FAILURE SENTENCE, verbatim (N=45000, pass c):

        KAYA_SELFTEST: FAILED (row#last ordered "2026-12-20|TK399|SELL|6427.63", wanted "2026-12-04|TK499|SELL|6649.63")

  MECHANISM: STAMP/MODEL, not row-widget realization. Four pieces of evidence.

  note 1 - PER ROW, NOT PER BATCH. N=20000 held fixed, rows-per-transaction
        varied 25/50/100/150 (800 down to 134 batches): wall 2.94 / 3.04 / 3.03 /
        2.96s, submit_done 0.77 / 0.78 / 0.76 / 0.77s. Batch count is irrelevant.

  note 2 - WHERE THE TIME GOES. `sample` of a 100000-row leg
        (sample-100000.txt, hot frames quoted below):
          MAIN THREAD 5523 of 5746 samples inside the SwiftUI view-graph update.
            ~2380 (41%) in kayaTableGeometryGeneration(_:)
                 (swift/KayaSwiftUI.swift:7701) - a RECURSIVE HASH OF THE WHOLE
                 TABLE SUBTREE, re-run per body evaluation, reached from both
                 KayaNativeTable.body.getter and KayaRender.widget.getter. At
                 100k rows that is ~500k nodes hashed per evaluation.
            ~2120 (37%) in SwiftUI per-child observation bookkeeping:
                 ForEachChild.updateValue -> ObservationCenter.invalidate ->
                 ObservationTracking._installTracking -> registerTracking, and
                 ObservationGraphMutation.apply -> ObservationTracking.cancel.
            ~0 in NSTableView row-view creation.
          PUMP THREAD 5240 of 5746 parked in kaya_next_commands; only 452 inside
                 Scene::apply. THE CORE IS NOT THE LIMIT.
          PYTHON APP THREAD fully busy in dict_vectorcall / dict_merge /
                 clone_combined_dict_keys and frame teardown - the guest building
                 its own Txn dataclasses. That is submit_done, and it is a real
                 share of the wall at large N (4.55s of 9.65s at N=50000). It is
                 a Python-guest cost, not a kaya cost.
          Physical footprint 1.3 GB at 100000 rows (~13 KB per row).

  note 3 - WHY THE EDGE IS QUANTIZED. The step deadline is 5.0s on macOS
        (swift/KayaSwiftUI.swift:5253) but it is checked AFTER the attempt returns
        (line 7375: `failures.count > failuresBefore, parts[0].hasPrefix("expect"),
        Date() < stepDeadline`). Each attempt is one DispatchQueue.main.sync that
        queues behind a full main-thread update pass, 2-3s at these sizes. So an
        attempt that STARTS at 4.9s runs to completion and passes at 7.2s or 9.6s,
        which is why passes at 6.5-9.6s are legitimate and why 44000 can pass
        while 43750 fails.

  note 4 - THE CONTROL, and it is the one that names the tier's value. The SAME
        rows, cells, keys and chunking on a PLAIN For (rows(), no header bar, so
        no native table):
              N=2500   8.89s   PASS      (table tier: 0.44s)
              N=5000  35.04s   PASS      (table tier: 0.71s)
              N=10000 120s     CAP-KILL  (table tier: 1.18s)
              N=20000 120s     CAP-KILL  (table tier: 2.89s)
        The 20000-row plain For was sampled before killing: 3.4 GB footprint, main
        thread 2995/2995 samples in Update.dispatchActions ->
        _AppearanceActionModifier.MergedCallbacks.updateValue -> Update.enqueueAction
        -> _ArrayBuffer._consumeAndCreateNew -> swift_arrayInitWithCopy/retain, i.e.
        every row's appearance action enqueued into a repeatedly-regrown array.
        THAT is row-widget realization, and it is ~50x more expensive at N=5000 and
        chokes at 4-9x fewer rows. The native NSTableView tier already removes it.
        What is left in the table numbers is the model side.

  ASIDE, worth its own ledger line: a hung main thread DEFEATS the harness step
        deadline outright. The plain-For legs at 10000 and 20000 printed no verdict
        at all and had to be killed by my own cap, because the deadline is only
        consulted after the main.sync returns and it never returned. The same
        harness that reddens legibly for a slow scene says nothing for a wedged one.
