ANDROID / COMPOSE — non-virtualized For row-count choke baseline
================================================================
Measured 2026-08-24. Repo NOT edited: the guest was built from a copy of
the tracked tree under this scratchpad and installed under its own
applicationId (dev.kaya.choke), so the lane's dev.kaya.rusthost was
never touched.

SETUP
-----
Device      : emulator-5560 (AVD "kaya", android-35 google_apis arm64-v8a,
              headless, -gpu swiftshader_indirect, 320dp phone), one member
              of the standing four-phone pool the matrix leaves warm.
              Not booted by me, not killed by me; the tablet at 5562 and
              the other three phones were never addressed.
Guest       : the RUST guest on the COMPOSE interpreter — the language and
              tier of the lane's `table-compose` leg, which is the lane's
              first table leg. (The lane also runs table-jvm and table-go;
              all three render through the same KayaCompose realization,
              so the tier under test is the same.)
Scene       : a 4-column table (Date, Ticker, Side, Total) — one
              collection, declared with
              items.rows(tx).columns(["Date","Ticker","Side","Total"],
              Sort::none()) and a 4-label row template, grown. Every
              string is synthesized in the guest from a counter
              (total = "%07d.00" % i); no asset reads, no I/O.
              Row count from KAYA_ROWS, carried as an intent extra
              (MainActivity maps KAYA_* extras onto the environment).
Script      : inline via KAYA_SELFTEST_SCRIPT, one step:
                  expect label#last "<%07d.00 of N-1>";
              the LAST row's Total cell, so a pass proves the whole stamp
              reached the scene tree.
Watched neg : at N=20, asking for the SECOND-to-last row's value failed
              with `label#last reads "0000019.00", wanted "0000018.00"` —
              the assertion is live and lands on row N-1, not on the
              template or the header.
Wall time   : host-side, from `am start -W` to the logcat line matching
              KAYA_SELFTEST: (OK|FAILED) — or to the guest process dying,
              or to a 120s cap, whichever came first.
Tier        : SYNTHESIZED, and it realizes every row. KayaCompose.kt
              contains no LazyColumn/LazyRow/`items(` of any kind (grep:
              zero hits); a For is a plain Column of composed rows.

THERE ARE TWO WALLS, AND THE FIRST ONE IS NOT THE RENDERER
----------------------------------------------------------
Wall 1 (the one the guest as specified actually hits): the interpreter's
pump buffer is 64 KiB (KayaCompose.kt: `ByteArray(64 * 1024)`), and a
table stamped in ONE transaction puts every row in ONE batch. The core
asserts the batch fits and aborts the process when it does not.
Wall 2 (what a row-virtualization slice would actually be beating): with
the inserts split across transactions so no single batch exceeds 64 KiB,
the app dies of a Java-heap OutOfMemoryError inside the Compose runtime.

SUMMARY
-------
TIER: synthesized, realizes every row (no lazy list anywhere in
      KayaCompose.kt).

CHOKE (the guest as specified, one transaction):
      N = 157 rows. FIRST FAILING N; 156 passes.
      Mode: CRASH — an abort in the core on the interpreter's pump thread.
      Sentence, verbatim:
        kaya: apply batch of 65568 bytes exceeds the pump buffer of 65536
      (crates/kaya/src/capi.rs:2936; the buffer is KayaCompose.kt's
      `ByteArray(64 * 1024)`. The SwiftUI interpreter sizes its buffer the
      same, `let cap = 64 * 1024`, so this wall is not Android's alone.)

CHOKE (inserts chunked so no batch exceeds 64 KiB):
      N = 4000 is the first N that ever fails; N = 5000 is the first that
      fails on every attempt. 3500 passed 7/7.
      Mode: CRASH — java.lang.OutOfMemoryError, process killed. Verbatim:
        FATAL EXCEPTION: main
        java.lang.OutOfMemoryError: Failed to allocate a 24 byte
        allocation with 90640 free bytes and 88KB until OOM, target
        footprint 201326592, growth limit 201326592; giving up on
        allocation because <1% of heap free after GC.
      The fatal throw lands on `main` or on `kaya-compose-pump`, and the
      crash sites recorded by ActivityManager are Compose runtime
      internals: DerivedState.kt:336, SnapshotState.android.kt:27,
      SlotTable.kt:2862, ObjectIntMap.kt:673, plus Arrays.java (array
      growth).

DEGRADED BAND (first N over 5s launch-to-verdict):
      One transaction: NEVER — the app is still finishing in 1.0s at
      N=156 and is dead at 157.
      Chunked: first individual sample over 5s at N=3900 (5.1s; median at
      that N is 4.7s); the median first crosses 5s at N=4500 (5.7s), which
      is inside the failure band. So on this platform there is no slow
      band before the choke: the table is comfortable (<5s) right up to
      the row count that kills the process.

NO ANR. Not once, at any N, in either regime: zero "ANR in dev.kaya.choke"
lines across every captured buffer. Both walls kill the process outright
before the input dispatcher can time anything out.

MECHANISM IMPLICATED
--------------------
Wall 1 is TRANSPORT, not the For: a fixed 64 KiB pump buffer against
416 bytes of wire per stamped row.

Wall 2 is ROW-WIDGET REALIZATION, on three pieces of evidence:
  1. ~52 KB of Java heap per row, linear from N=20 to N=3500, against
     ART's 192 MB growth limit — 12.5 MB + 52 KB * N hits the limit at
     roughly 3,500-4,500 rows, exactly where the deaths start. Five model
     objects per row cannot account for 52 KB; composition state can.
  2. The fatal allocations are inside Compose's snapshot/slot machinery
     (DerivedState, SnapshotState, SlotTable, ObjectIntMap) — the
     composition, not the guest's model and not the Rust core.
  3. Wall-clock is linear in ROWS and flat in BATCHES: 0.8s fixed plus
     ~1.0 ms/row, and changing the transaction count at N=3000 by 6x
     (120 transactions vs 20) moves nothing (3.7s either way).

WHAT COULD NOT BE MEASURED
--------------------------
Splitting model cost from composition cost by building the table and
mounting something else is refused by the core, by design:
  kaya: widget WidgetId(1) (Some(Row)) was created by this transaction
  and is not reachable from any mounted root — it will render NOWHERE
  while still answering every harness read, so a scene asserting on it
  passes against an invisible widget.
(crates/kaya/src/scene.rs:2437.) So the 52 KB/row figure is model mirror
plus composition together; the crash sites are what attributes it.
