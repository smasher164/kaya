platform: iOS Simulator, kaya-sim-2 (3CD1C302-C686-4EC4-A10E-EE94FFE7C3A2,
          iPhone 11 Pro, iOS 26.5). ONE pool device; it was booted before

TWO WALLS, and the first one is not about rendering at all
----------------------------------------------------------
WALL 1 — THE PUMP BUFFER, at 161 rows in ONE transaction.
swift/KayaSwiftUI.swift's kayaStartCommandPump allocates `let cap = 64 *
1024` and hands it to kaya_next_commands; capi.rs:2936 asserts the batch
fits. A stamped 4-column row costs 408 bytes on the wire (measured
exactly: batch = 256 + 408N), so N=160 fills the buffer to the byte
(65536) and N=161 aborts the process:

  thread '<unnamed>' panicked at crates/kaya/src/capi.rs:2936:5:
  kaya: apply batch of 65944 bytes exceeds the pump buffer of 65536
  fatal runtime error: failed to initiate panic, error 5, aborting

No verdict line and no harness step — the app is gone before the scene
starts. This is the wall the NATURAL spelling hits: every kaya guest and
example, guests/swift/table.swift included, declares its collection and
inserts its rows inside one build closure. It is a property of the
SwiftUI interpreter (mac and iOS share that constant), not of the device.

WALL 2 — the rendering wall, reachable only by chunking the inserts so
no single batch exceeds 64 KiB (150 rows per transaction here). The core
refuses to defer the mount — scene.rs:2437's orphan barrier: "widget
WidgetId(1) (Some(Row)) was created by this transaction and is not
reachable from any mounted root" — so the only legal chunking is: mount
an empty table first, then insert. Every chunk therefore lands in a
mounted tree, which is a property of this design, not a choice of this
harness.

SUMMARY
-------
DEGRADED AT (first N over 5s launch->verdict): N=3000 (6.2s). 2500 sits
  on the line: 4.2s, 4.2s under load ~4, 5.2s under load ~5.2.
CHOKE AT: N=20000. It failed 4 of its 5 capped runs; the fifth (the
  session's first, on the least loaded machine) passed at 27.2s, and an
  un-capped diagnostic finished at 144.2s. N=15000 passed three times
  (87.2 / 85.2 / 75.2s). N=40000 is killed outright.
  AND ABOVE IT, THE NATURAL SPELLING'S WALL IS 161: without chunking,
  the process aborts at 161 rows in one transaction, which is the number
  an app author actually meets.
FAILURE MODES, distinguished:
  - 161 rows, one transaction: ABORT, verbatim —
      "kaya: apply batch of 65944 bytes exceeds the pump buffer of 65536"
      "fatal runtime error: failed to initiate panic, error 5, aborting"
  - 20000 and 30000 rows, chunked: MY 120s CAP. The process is alive,
    ~4-5 GB resident, the harness has printed "+0ms expect label#last",
    and no verdict has been reached. Not the expect-retry window: the
    step's 15s deadline is only consulted after a FAILED attempt, and
    each attempt blocks inside DispatchQueue.main.sync while the main
    thread realizes rows, so the retry never gets to time out.
  - 40000 rows, chunked: KILLED by the OS. No verdict line, no .ips
    crash report (every SIGABRT above wrote one), so SIGKILL — the
    simulated device's memory ceiling, reached at ~4.5 GB.
TIER: synthesized (compact phone). The iPad pool device would take the
  native tier; not measured here — one pool phone only, as charged.

MECHANISM: ROW-WIDGET REALIZATION, not stamp/model cost.
  Evidence 1 (the A/B that isolates the view layer): the same 5000 rows,
  the same node count, the same guest work (guest-chunks 939ms vs 927ms)
  — but with the column headers declared (synthesized table tier)
  wall=13.2s / peak 1526 MB, and with them off (the generic KayaFlex
  container path) wall=34.2s / peak 1692 MB. The model side is identical
  to the millisecond while the wall moves 2.6x, so the wall is being
  spent in the view layer. Both paths realize every row; neither is lazy.
  Evidence 2 (memory is per realized row, not per apply): 5000 rows in
  34 transactions peaks at 1315 MB; the same 5000 rows in 200
  transactions peaks at 1292 MB. Six times the batches, the same memory
  — so the ~250-300 KB/row is the realized row's view machinery, not
  churn from re-applying.
  Evidence 3 (when the memory arrives): at N=40000 the guest had
  submitted every row while RSS was 107 MB; the climb to 1.28 GB ->
  3.2 GB -> 4.37 GB -> 4.54 GB and the kill all happened in the ~35s
  AFTER the guest was done, i.e. during interpreter apply + realization.
  Time scaling: wall minus the 1.15s launch floor is 0.05s @500, 3.05s
  @2500, 10s @5000, 36s @10000, 82s @15000, 143s @20000 — about N^1.85,
  superlinear in rows.

A SECOND, SEPARATE SCALING BUG, guest side (Swift binding):
  guest-chunks — the guest's own submit time, before the core or the
  interpreter sees anything — is 0.25s @2500, 0.94s @5000, 3.6s @10000,
  14.1s @20000, 57.7s @40000: quadratic in rows. It is
  KayaAppTx.insertRecordRaw -> KayaApp.modelSet
  (bindings/swift/KayaApp.swift:1078), which does
  `instances[at].entries.firstIndex(where: { $0.key == key })` — a
  linear scan of every entry inserted so far, on every insert, plus a
  copy-out/copy-back of the instances array. Row virtualization would
  not touch this; it is the binding's own model bookkeeping, and the
  other seven bindings want the same look (invariant 1). At 20000 rows
  it is 14s of the 144s wall; at 40000 it is 58s.
